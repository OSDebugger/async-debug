# 前端展示设计方案

## 一、结论

本文档给出 Async Inspector 面板（VS Code 插件里展示异步执行链的视图）的展示设计方案。核心结论一句话：面板从"多次快照拼接出的树"改为"聚焦当前活跃路径、按程序组织的树"。每次调试停止时，面板醒目展示当前程序的完整异步逻辑执行链——从根任务一路到当前断点；已经跑完的程序整棵折叠为一行，可随时展开回看。节点紧凑成一行，用颜色区分内核/用户空间、行尾标注所在核，poll 次数等细节在选中节点时才展开。数据层面如实区分两类能力：单线程链的展示由现状快照直接支撑，多线程聚合、准确的空间标记等需要扩展快照数据契约。

## 二、问题的根源

先说清面板面对的对象。我们调试的异步操作系统里，任务是协程（coroutine）——可以挂起、之后从挂起点恢复继续执行的执行单元。协程挂起时，它的物理栈（CPU 实际使用的函数调用栈）被整个弹出，执行位置和局部变量都存进协程环境结构体里，栈上不留痕迹；恢复时再从 poll 入口（协程被轮询推进的入口函数，运行时每推动协程执行一段，直到它再次挂起等待）重新建立调用栈。因此跨越挂起点的调用链在物理栈上无处可寻，传统调试器的调用栈视图回答不了"这个任务是怎么一步步执行到当前位置的"。

ARD 的解法是跟踪协程的 poll 入口和调用点，把这条逻辑执行链重新拼出来（机制详见《多核跟踪设计方案》§1）。GDB 侧的 Python 跟踪脚本为每个线程维护一份影子栈——当前协程嵌套关系的链；调试停止时输出快照，即影子栈加上物理栈上尚未覆盖的尾部同步帧（当前协程 poll 内部正在执行的普通函数调用），拼成"从根到当前"的一条完整链。

现状面板拿到快照后做了一件事：把每次快照的链按协程编号（cid，调试器为每个协程实例分配的顺序编号）合并进一棵树，只增不减。cid 的语义应当以一条任务执行流为单位：执行流是从根任务的起点到任务结束的完整执行过程，每条执行流从自己的起点开始一套编号。问题由此而来。其一，合并忽略了线程号，两个核上的链被混进同一棵树；其二，现状实现把编号序列按程序名分桶维护（内核算一个程序名，每个用户程序各一个），不同程序之间的编号空间互相重叠，两条不相干的链会因为编号相同被错误合并——而按执行流语义，同一程序的两次运行也应是两套编号，编号重叠的范围本就在执行流之间，不止程序之间；其三，停止次数越多节点越多，树无限膨胀、不可读。而比这三个表现更深一层的问题是：快照本身是一条**活跃路径**（从根任务到当前执行点的那条链），不是完整树。把多次快照的历史路径画进同一棵树之后，历史路径看起来像并发分支——"这个协程下曾经出现过两个子协程"被误读成"它同时有两个子协程"。这就是树不合理、节点爆炸的根源。

## 三、展示语义：聚焦当前活跃路径

由此确定展示设计的第一原则：**面板聚焦当前活跃路径**。树的语义是"边 = await 关系"（父子关系表示"父协程在 await 点上等待子协程完成"），节点是协程实例，链尾是物理栈上的同步帧；完整树（包括曾经 await 过但已完成的子协程、挂起中的其他子协程、spawn 创建关系）是长期方向，现状数据里没有这些边，不混入活跃路径展示。

用户的核心交互场景随之清晰。用户在某个 await 点上打断点，程序停在该处时：影子栈给出从根任务到当前协程的逻辑段，物理栈尾部给出当前协程内部到断点处的物理段，两段相接就是**当前所处程序的完整异步逻辑执行链**。面板要做的是把这条链在树里醒目点亮：根任务到断点处的每个节点加粗高亮、连成一条清晰的路径，链尾节点就是断点所在位置，点击即跳转源码（源码跳转已实现，依次回退三层：节点持久化的源码位置、旧数据按 cid 在最近快照里回退、同步节点的地址问 GDB 反查行号）。程序跑完之后，它的执行流整棵折叠收纳，不再占据当前视野。

这里要如实说明一个现状边界：快照只包含当前选中线程的链，所以现状下"活跃路径"严格说是"当前线程的活跃路径"。all-stop 模式（GDB 的一种执行模式，任一核停下时全部核停下）下所有核都停着，逐个线程读影子栈在技术上可行，多线程快照聚合是数据契约的扩展方向（《多核跟踪设计方案》§7 已定方向），落地后每个线程各有一条活跃路径，当前线程的路径最醒目，其余线程的路径次一级显示。

## 四、布局与工具栏

面板整体保持"左树区 + 右侧栏"的两栏结构，演化集中在树区的内部组织和工具栏的语义上。

**树区**从"一棵无名大杂烩树"改为"按程序分区的树列表"。顶部按程序划分区块：内核执行流区块（收纳内核自己发起的后台任务链，根是内核启动任务）、每个用户程序各一个区块，各自以程序的根任务为根。内核与用户**不拆树**——同一条链里内核帧与用户帧天然交织（用户协程 poll 内部发起系统调用、进入内核函数，再返回用户代码），拆开反而切断因果；用节点颜色区分特权级空间即可。当前正在执行的程序区块置顶高亮，跑完的程序折叠为一行。

**侧栏**继续承担配置职责：Trace Root 区展示当前已设置的跟踪根函数，白名单区（要跟踪的函数名单）保留分组勾选、Apply、Trace、Locate 的现状交互。节点详情不占侧栏，改为在树区内选中节点时内联展开（见下节），把侧栏宽度全部留给配置内容。

**工具栏三个按钮的去留**需要逐个论证，因为这涉及新交互模型下的语义划分。

Reset 保留，语义是**彻底清空、不可逆**。它做两件事：清空面板上所有程序树，同时向 GDB 发送 `ardb-reset` 清掉跟踪脚本侧的协程表、影子栈等跟踪状态。它与"折叠"必须严格区分：折叠是收纳——程序跑完后它的树收成一行，历史数据还在，展开即可回看；Reset 是从头开始，之前的跟踪记录全部丢弃。这个区分是用户对面板形成正确心智模型的关键，Reset 按钮的文案或提示应明确传达"清空"而非"收起"。

Gen Whitelist 保留。白名单生成是调试流程的入口步骤，与展示设计正交，维持现状。

Snapshot 保留，但语义重新定义。现状下每次调试停止都会自动抓取快照，手动按钮近乎冗余。多线程快照聚合落地后，它成为"主动抓取全线程快照"的入口——用户想主动刷新所有核的状态时使用，不必等待下一次停止事件。在聚合落地前的过渡期，它作为手动兜底：entry 停止（调试刚启动时的合成停止）和被单步序列（调试器跨特权级过渡时逐条单步执行指令的那段过程）静默吞掉的停止之后，自动快照没有触发，用户可手动刷新。按钮文案可以考虑改为"刷新快照"以传达新语义。

布局示意：

```
┌─ 工具栏：Reset │ Gen Whitelist │ Snapshot（刷新快照）──────────────┐
├─ 树区：异步执行流 ─────────────────────────┬─ 侧栏 ────────────────┤
│  ▾ 用户程序 fib（当前活跃，置顶）           │ Trace Root            │
│   └─ main::{{closure}}  KERN  #1  ← 根任务 │  （已跟踪根函数列表）   │
│      └─ child_task::poll  USER  #1         │ Whitelist             │
│         └─ sys_write 同步帧  KERN  #1      │  ▾ crate 分组勾选 …    │
│            └─ ● 断点处  USER  #1  ← 当前点 │                        │
│  ▸ 用户程序 shell（已结束，折叠）           │                        │
│  ▾ 内核执行流（根：内核启动任务）           │                        │
└────────────────────────────────────────────┴───────────────────────┘
```

## 五、节点与活跃路径的视觉设计

节点设计的目标是紧凑：一行一个节点、小字号，细节信息不常驻。具体样式：

**一行构成**：类型徽章（ASYNC/SYNC 小徽章，红/绿区分）+ 函数名 + 行尾的核标注。空间归属不走文字徽章，改走更强的视觉通道——节点左边框用空间色：内核橙、用户蓝、无法判定灰，类型徽章保留现状的小号文字形式。现状的 KERN/USER 文字徽章渲染代码保留，但边框着色可以让用户扫一眼边框颜色就读出链上哪里跨进了内核、哪里回到了用户，这正是"同一条链里空间交织"场景下最需要的信息。

**核标注**：行尾显示该协程所在核的编号（如 `#1`），数据来自快照的 `thread_id`（GDB 线程号，QEMU 下每个 hart——RISC-V 对硬件线程的称呼——暴露为一个线程）。跨核迁移过的协程标注核集合（如 `#1 #2`），表示该协程曾先后出现在这两个核上。

**活跃路径**：当前快照路径上的节点加粗，从根到当前点的连线（竖线）加深加粗，链尾节点（当前断点处）加一个醒目的当前点标记（如 ●）。不在当前快照路径上的历史节点降低对比度——颜色淡化、字体变细，与活跃路径形成明确的视觉层级，杜绝把历史误读成并发分支。

**选中展开详情**：点击节点展开内联详情区，不常驻。详情内容按紧凑列表排列：poll 次数（该协程被轮询推进的累计次数）、state（协程环境结构体的状态字段）、地址、源码位置（file:line，点击跳转编辑器）、出现过的核集合。再次点击收起，或选中其他节点时切换。

## 六、树的组织与历史收纳

**程序为根**。树的合并键从"cid"改为复合键，精确的键是(执行流, cid)：编号只在一条执行流内唯一，必须带上执行流标识才算真正唯一。执行流标识现状数据里没有，程序名是当前可用的近似——同一程序两次运行时，(程序, cid) 退化为近似键，两次运行的编号仍会混淆，这是近似键的已知边界。程序名来自 hook 断点（命中时执行一小段脚本的断点，脚本读出"这次启动的是哪个用户程序"）维护的当前程序记录；快照带上程序名字段后（见下节），每条链能精确归入自己的程序树，跨程序的编号冲突消失。

**历史收纳与折叠**。折叠的粒度是程序树：程序跑完，整棵树收成一行，显示程序名、节点数或最后活跃位置，带展开箭头。展开后历史路径仍以淡化样式呈现，与活跃路径严格区分。折叠动作有两个来源：手动折叠（点击程序区块的折叠箭头）现状即可实现；自动折叠依赖"程序已结束"的信号，这个信号现状数据里没有——用户程序在 QEMU 里跑完退出的路径目前没有 hook 覆盖，需要在退出路径上设跟踪点（数据契约扩展，见下节）。扩展落地前，手动折叠承担主要职责。

**多程序并存时的树间关系**：各程序树并列、各自独立，树与树之间没有父子关系——用户程序链里的内核帧留在用户程序树内（如系统调用路径上的内核函数帧），只有内核自己发起的后台任务链才归入内核执行流树。当前活跃程序区块置顶高亮，已结束程序折叠沉底。同一个程序先后多次运行的两次执行流归入同一棵程序树（以程序为账本的组织原则，见《多核跟踪设计方案》§4），多次运行的历史路径靠淡化区分代际。

## 七、数据支撑与契约扩展

这一节如实区分：哪些展示能力由现状数据直接支撑，哪些需要扩展快照数据契约。

**现状数据直接支撑的能力**：

| 展示能力 | 支撑数据 | 现状限制 |
|---|---|---|
| 单线程活跃路径展示 | 快照 path 链（影子栈 + 物理栈尾部） | 快照只含当前线程，其余核的链取不到 |
| 源码跳转 | 节点 file/line 字段 + 三层回退 | 已修好，无限制 |
| poll 次数、state 详情 | 节点 poll/state 字段 | 无 |
| 所在核标注 | 快照 thread_id 字段 | 该字段现状存在但被合并逻辑忽略，前端改用它即可 |
| 手动折叠、历史淡化 | 前端状态，不依赖新数据 | 无 |
| 程序归树 | TS 端当前断点组（一个程序专属的一组断点和符号文件，组名即程序名） | 同一时刻只有一个用户程序在跑时才可靠，与《多核跟踪设计方案》§6 的现状边界一致 |
| 核集合标注 | 前端跨快照收集同一 cid 出现过的 thread_id | 精确性依赖 (执行流, cid) 复合键，程序名近似下仍有编号冲突风险 |
| 空间染色 | TS 端按节点地址区间推测（gdbDebugSession.ts:2017-2031） | 异步节点的地址是协程环境指针而非当前指令地址，分类不可靠，只能对同步帧准 |

**需要扩展的数据能力**：

1. **快照多线程聚合**。把快照从"一条链"扩展为"每个线程一条链的列表"，每条链附带线程号、所属程序、全局事件序号（用于对账先后顺序）。这是《多核跟踪设计方案》§7 已经定下的契约方向，本节只确认它对展示的意义：all-stop 下每次停止都能同时看到所有核的活跃路径，当前线程最亮、其余线程次一级。Python 侧已按程序分账本维护跟踪状态，快照补上程序名字段的成本不高，是这条扩展的第一步。
2. **执行流标识**。cid 的语义单位是任务执行流，每条执行流从根任务起点开始一套新编号。cid 的本意是协程实例在一条执行流内的标识——跟踪脚本用它把多次 poll 命中认成同一个协程、累计 poll 次数、维护影子栈，这些用途只需要流内唯一；执行流结束后实例全部消亡，编号重启不违反其本意，跨流唯一反而没有用处。快照需要携带执行流标识（如每次任务启动分配一个递增的执行流号），前端才能区分同一程序的两次运行、并以 (执行流, cid) 作合并键。现状实现按程序名分桶维护编号，同一程序多次运行的编号接着上一次继续，与执行流语义不完全一致，是 Python 侧跟踪状态维护层面的现状。
3. **空间标记由 Python 端准确提供**。poll 断点命中时，跟踪脚本明确知道该符号属于内核还是用户程序，空间标记应在那里生成、随快照下发，取代 TS 端的地址推测。异步节点的 addr 字段仍保留（环境指针本身对详情展示有用），但不再承担空间判定的职责。
4. **程序结束信号**。用户程序退出的路径需要挂 hook 或等价的跟踪点，产生"程序已结束"事件，驱动自动折叠。
5. **根任务识别**。树的根语义是程序的根任务（如 main 的协程），现状实现取"链上最外层协程"近似——多数情况下成立，但影子栈的近似维护不保证它恒等于根任务。快照元数据给出根任务 cid 可以消除这个近似。
6. **创建关系（spawn）**。并发任务挂 main 之下需要"谁 spawn 了谁"的创建关系数据，现状跟踪没有记录。这属于完整树方向，不在本次展示设计范围。

## 八、参考工具与借鉴取舍

**tokio-console**（tokio 官方诊断工具）采用任务列表 + 详情两栏布局，列表项带状态徽章、详情展示 poll 次数。借鉴它的"总览与详情分离"：树区是总览，详情在选中节点时内联展开。不采用它的常驻详情栏，因为 VS Code 面板宽度有限，常驻详情会挤压树区，而活跃路径需要完整可见。状态徽章和 poll 计数直接吸收进节点徽章与展开详情。

**async-inspect**（跨 await 点还原逻辑栈的工具）提供 blocked-at 源码定位和时间线视图。blocked-at 对应我们的节点源码位置跳转——节点点击直达"这个协程当前卡在哪个 await 点"，这正是第三节核心交互场景的最后一跳；时间线视图对应数据契约扩展后的全局事件序号——将来可以按事件序列回看路径的演化，本次设计先不展开。

**Await-Tree**（RisingWave 生产环境使用的文本逻辑树）证明了"节点 = 任务、边 = await 关系"的树语义是异步系统可观测性的通用表达。我们采用它的树语义，但要说明数据差距：Await-Tree 依赖运行时框架提供完整树，而 GDB 方案只有路径并集，完整树是长期方向。它的文本形式也说明一点：树的可读性来自结构语义正确，而不是装饰，这支撑我们把视觉设计的主要精力放在活跃路径的区分上。

**inspect-embassy**（GDB 后端重建 await 链的 TUI——终端界面——工具）与我们的数据来源同源，它的链式展示验证了"GDB 数据天然是链"——这正是"面板聚焦当前活跃路径"原则的旁证，树只是在链的历史并集上组织的容器。

**BugStalker**（带 async backtrace 命令的调试器）把"还原跨挂起点的调用关系"命名为 async backtrace。我们的活跃路径本质就是一条异步 backtrace，借用这个概念可以帮用户把新视图与熟悉的调用栈视图联系起来：面板树区的活跃路径，就是普通调用栈在协程世界的对应物。

**Chrome DevTools 的 async stack trace** 处理异步帧与同步帧混排：异步帧在调用栈中单独标注、可折叠展开。借鉴其混排与折叠交互：ARD 的链上异步节点与同步帧天然混排，历史 await 段折叠后显示为可展开的摘要，展开时恢复淡化样式，与 DevTools 中异步段的收展体验一致。
