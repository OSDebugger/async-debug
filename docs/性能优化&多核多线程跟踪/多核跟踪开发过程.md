# 多核跟踪开发过程

日期：2026-10-28
范围：perf/symbol-resident-multicore 分支，af82767（10-19）至 c53857c（10-28），共 22 个提交

## 结论

多核跟踪不是一次设计出来的，而是三个阶段的叠代：**性能优化（10-19）→ 数据面多核化（10-20）→ 控制面真机适配（10-21）**，最后是健壮性收尾（10-28）。每个阶段的改进都来自前一个阶段暴露的问题：性能优化是为了让"切换程序"足够快，数据面多核化是为了让跟踪状态按程序隔离，控制面适配则是 SMP 真机实测逼出来的——调度锁死锁、断点防重入失效、边界函数复用，三个问题都在真机上才现形。最终的设计方案记录在[多核跟踪设计方案.md](多核跟踪设计方案.md)，本篇按 commit 时间线还原开发过程。

## 前因：一次内核↔用户往返要 689ms

多核并行的前提是调试器能频繁切换跟踪目标——内核和用户程序之间来回切换，每次都要卸旧断点、换符号表、装新断点。但切换本身很慢：符号卸载 226.9ms、符号加载 133.6ms、重插断点 52ms×2、状态恢复 152.7ms，合计约 689ms。切换慢，多核并行就无从谈起。

10-19 的八个 commit 解决的就是这件事（详见[性能优化报告.md](性能优化报告.md)）：

- af82767、1fe0d27：grouped 白名单按符号组合缓存——白名单重建从"每次全量"变成"命中缓存直接复用"
- c17d76f：组切换跳过冗余白名单重建（四种情况各扫一遍的逻辑合并为一次判断）
- 2df10b1：地址表带锚点校验复用——同名符号的地址不必每次重新解析
- d25b4a4：组切换后按保存地址重装 callsite 断点
- ce702e7：callsite 助记符支持 RISC-V（jal/jalr）并按白名单过滤
- 5d96f47：审查修复——成功标志改用 captureConsoleOutput、restore 失败自愈、jalr 真实格式解析

这轮优化的副产品是**符号常驻的支撑设施全部建成**（名字键地址表、按 crate 分组的白名单缓存、锚点校验），下一阶段直接站在它上面。

## 阶段一：数据面多核化（10-20）

### 先写设计文档，用实验查证关键事实（da79f9e）

动手写代码之前，我先把"多核并行调试"这件事的关键前提在真机上查证了一遍，共十条，其中五条直接决定了架构：

1. **GDB Inferior 方案不可行**：GDB 多目标调试要求每个目标独立连接，QEMU gdbstub 只支持单连接——"一个核一个 GDB 会话"的路线死了。
2. **用户程序虚拟地址区间完全重叠**：hello_world 和 pipetest 都是 musl 静态链接、同基址。给 A 设的断点，B 执行到同地址时必然命中——这不是巧合，是结构性必然。
3. **`info symbol <地址>` 在符号常驻后完全歧义**：两个符号表同时挂着时，GDB 对同一地址返回多个"符号+偏移"答案，不仲裁不报错。所以符号查询必须走自己的名字键地址表，GDB 查询只留兜底。
4. **QEMU gdbstub 无 non-stop**：all-stop（任一核停止则全机冻结）是唯一停止模型。这恰好符合"命中就全部暂停"的目标。
5. **QEMU 断点按虚拟地址对全部 vCPU 生效**：断点插入会传播到所有核，命中通道的隔离必须由调试器自己做——在 stop 回调里核对命中核的当前程序。

文档里还定下两条原则。**执行流归因原则**：执行流按执行上下文（当前页表+特权级）归因、按程序分桶，代码来源（哪个 ELF）不参与归因——用户程序调内核、共享运行时代码，一律记入"执行者"的流。**本轮范围声明**：本轮交付单线程、并发、单程序多核（smp 下同一程序的多任务，CFS 调度下的主要形态）；并行多用户程序为下一轮专项。

### 四个 feature 落地设计（10-20 下午）

**符号文件常驻（230e8ac）**。符号表永久加载、永不卸载，切组只做断点插拔。符号加载的 133.6ms 从此只付一次。

**跟踪状态按程序分桶（67d063d）**。白名单、地址表、协程表、影子栈每程序一份独立账本，切换程序只是换"当前账本"指针，O(1)。这条是查证第 8 条的直接推论：每个用户程序有独立地址空间，跨程序协程键碰撞真实可能，按程序分桶后表间天然隔离。

**按 vCPU 判定当前程序（fb6ab47）**。停下的核属于哪个程序？读命中 vCPU 的 PC：落在内核区间就是 kernel，落在用户区间就取事件驱动的当前用户程序——hook 断点（挂在内核"启动用户程序"的必经函数上、带一小段脚本的断点，命中时读出这次启动的是哪个程序）读出的名字。

**断点按程序归属 + stop 门控（2a75005）**。每个跟踪断点记上"我属于哪个程序"，stop 回调里核对：归属为空（内核断点）放行；否则必须等于当前激活程序，交叉命中（A 的断点被 B 踩中）静默继续。这就是**零错记**原则的落地——多核下记错比记漏严重得多，记漏一次只是少个点，记错一条链会污染整棵树。

随后是 vCPU 程序扫描与活跃集合差异插拔基础设施（b51ca1d），为"每核一组"的下一步铺路。

### 真机暴露的第一个误判：停靠 hart 的复位向量（b73508b）

真机会话里发现：QEMU 启动后，还没上线的 hart 停在 RISC-V 复位向量区（地址 < 0x2000）。这个地址不属于内核区间，也不属于任何用户程序，但旧逻辑把它归给了"当前用户程序"——记错账。修复：PC 分类增加第三类 `unknown`（内核区间 → kernel；复位向量区 → unknown；其余 → 用户程序）。这是零错记原则的第一次真机检验。

### 审查修复（6a78553）

代码审查发现三个问题：首次激活程序桶时要把激活前的全局状态播种进去（否则 launch 模式白名单被清空）；save 之前先激活目标程序（防止把错程序的状态写进槽里）；`_breakpoint_allowed` 两侧程序名要归一化（`/pipetest` 与 `pipetest` 应视为同一程序）。

## 阶段二：控制面真机适配（10-21 凌晨）

数据面就绪后，控制面在真机上集中暴露问题。这一夜的时间线最能说明"适配 → 发现问题 → 改进"的过程：

### 00:33 单步锁定：初版假设（5788179）

特权级过渡期间要逐条单步，只希望当前核动。加了 `set scheduler-locking on`（GDB 的调度锁：控制单步/继续时放行哪些核），当时注释写的是"continue 不受 scheduler-locking 影响"。

### 01:54 假设被推翻：on 模式死锁（6564c62）

SMP=2 真机实测：on 模式的语义是**continue 也只放行当前线程**——从核被永久冻结在复位向量，内核忙等 hart 上线，整个系统死锁。改 `step` 模式：单步锁当前线程、continue 放行全部核。两个需求（过渡期只走当前核、平时全部核跑）都满足。

### 02:27 状态机第一版适配（f058c6b）

在 step 调度锁之上，补三个机制：

- **单步序列线程锁定**：过渡处理的单步序列开始时，锁定发起过渡的线程（`singleStepThreadId`），序列期间收到任何别的线程的停止事件一律静默——disable 掉它踩中的断点、发 continue 放行全部核。锁定在过渡判定完成、开始切组之前解除。
- **外来停止静默**：上面说的静默处理。all-stop 下没有更好的原语（continue 放行全部核、si 只走当前线程，"锁定线程保持单步"与"其他核自由运行"互斥）。
- **断点防重入**：静默继续前把踩中的断点临时禁用，记入待恢复清单；下次停止不是这些断点时自动重新启用。否则程序前进一条指令又停在同一断点，无限循环。

同一个 commit 还修了一个真机问题：smp=2 下 K→U 过渡被劫持（另一个核的停止事件插进来），导致组切换永不执行。

### 02:54 防重入失效：断点号在哪记录（110fdda）

真机上发现防重入刷屏仍无法打破。排查根因：MI 层把停止事件分流到五个通道——breakpoint / step-end / step-other / signal-stop / stopped，**断点命中走的是 breakpoint 事件**，而断点号此前只在 stopped 事件里记录——防重入逻辑拿到的断点号永远是空（日志里 `bkpt=-`）。修复：抽一个 `recordStopContext` 函数，在五个停止事件里统一记录线程号+断点号+恢复时机。

### 03:13 user_return 复用：sepc 分类（ad02117）

真机上又发现一种假过渡：内核里"返回用户态"的必经函数 user_return 被复用了——内核自己的任务切换也走它（把当前任务挂起、切到另一个内核任务）。两种情形都命中 K→U 边界断点，但只有前者是真过渡。区分办法是读 sepc（RISC-V 的异常返回地址寄存器，sret 跳哪里看它）：sepc 指向用户地址 = 真过渡，进入状态机；sepc 指向内核地址 = 内核任务切换，静默继续。前提是用户地址区间配置正确，否则所有 K→U 边界都被误判成内核任务切换，调试器永远进不了用户态。

## 阶段三：健壮性收尾（10-28，40c13ab）

10-28 在服务器真机（QEMU + 内核 + release 编译的用户程序）上继续调试时，集中修了四类问题：

- **release 行表缺失**：release 优化后函数边界信息不全，next/step 报 "Cannot find bounds of current function"——降级为指令级单步（exec-next-instruction）
- **console 输出恒为空**：原 getConsoleOutput 拿不到输出，审查发现后改用 captureConsoleOutput
- **节点源码跳转**：树节点持久化源码位置，点击跳转三层回退（持久化位置 → 最近快照按 cid 找 → addr 问 GDB）
- **tsDiag 排障通道**：setBreakpoints、切组、断点重插全程落盘 temp/ardb_ts_diag.log——排查"为什么停在这"类问题时，日志能还原当时的断点状态

## 结论

从这条时间线能得出四条结论：

1. **零错记是第一原则**。断点归属门控、程序名归一化、复位向量归类 unknown、sepc 分类，四次修复全是同一件事：宁可漏记，不可错记。多核下错记的代价是污染整棵执行树，漏记只是少一个点。

2. **机制与核数无关**。全部适配机制操作的都是 GDB 动态报上来的线程号（谁停止记谁、谁发起过渡锁谁），代码里没有写死 2 核。QEMU 换 `-smp 4` 无需改扩展代码；但三个已知边界会随核数放大：单份状态机同一时刻只跟踪一个过渡、全局单一"当前用户程序"、快照只读当前线程。

3. **单例假设是当前架构的边界**。状态机单份、当前程序全局一份——它们支撑了单程序多核（本轮范围），也划出了并行多用户程序的边界。下一步"每核一组"需要从内核任务结构读出每核的用户程序名。

4. **真机实测是主要驱动**。控制面的全部改进都来自 SMP=2 真机实测：on 模式死锁、断点号记录错位、user_return 复用、复位向量误判，没有一个是在本机模拟中能发现的。

## 完整设计方案

完整方案见[多核跟踪设计方案.md](多核跟踪设计方案.md)，骨架如下：

**三层架构**：调试适配器（TS，执行控制+状态机+断点组）→ GDB + Python 跟踪脚本（白名单、callsite 断点、影子栈、快照）→ QEMU 虚拟机（SMP，每 hart 一个 GDB 线程，all-stop）。

**执行控制（§3）**：step 调度锁（单步锁当前线程、continue 放行全部）；单步序列线程锁定（过渡期间外来停止静默）；静默继续时临时禁用断点防原地重入，下一次非该断点的停止时自动恢复。

**过渡与程序判定（§4）**：四状态状态机（内核态 / 内核单步到用户 / 用户态 / 用户单步到内核）；K→U 边界按 sepc 分类（用户=真过渡，内核=内核任务切换静默继续）；U→K 的 PC 已在内核时零步直接切组；跟踪状态按程序分桶，切换只换指针。

**异步跟踪（§5）**：白名单+地址表回答"跟踪谁"；callsite 断点回答"谁调用了谁"；每线程影子栈维护当前协程链（近似维护：出栈靠同 cid 再入栈截断和物理栈检测两条启发式）；快照把逻辑链与物理栈尾部拼接成完整链。

**正确性设计（§6）**：断点归属对账（跟踪断点记程序名，命中时核对，交叉命中静默跳过）；每线程影子栈隔离；两个已记录的隐患——前端合并忽略线程号、快照只读当前线程。

**现状缺口与走向（§7）**：过渡期间外来停止的呈现（状态机加"挂起"状态，continue 路由到序列恢复）；并行多用户程序（每核一组，读每 vCPU 任务结构）；快照聚合数据契约（每线程一条链+全局事件序号）。
