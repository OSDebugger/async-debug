# ARD 调试器多核跟踪设计方案
---

## 一、背景与目标

我们要调试的对象是一个异步操作系统：内核用协程实现（每个任务是一个可挂起、可恢复的执行单元），用户程序同样用异步方式写。调试它时，真正关心的问题是：**这个异步任务是怎么一步步执行到当前位置的？**

这个问题在传统调试器里回答不了。协程挂起时，它的执行栈被整个弹出——执行到哪了、局部变量是什么，都存进协程环境结构体，栈上什么都不留；恢复时再从 poll 入口重新建立这条调用栈。所以跨越挂起点的调用链在物理栈（CPU 实际使用的那个栈）上留不下痕迹——物理栈只反映"当前这次 poll 的内部调用"，之前的执行是历史，栈上早已消失【这就是rust async的无栈协程】。我们的调试器通过跟踪协程的 **poll 入口**（协程第一次被轮询推进时登记、之后每次推进计数）和**调用点**（被跟踪函数里"调用别的函数"的位置），把这条**逻辑执行链**重新拼出来。

当系统跑在多核上时，拼接的难度上了一个台阶，因为出现了三个新问题：

- **事件交错**：处理一次特权级过渡，调试器要"单步一步 → 等程序停 → 检查到哪了"反复几轮。双核时 1 号核正在单步，2 号核可能先撞上断点停住；all-stop 模式下 2 号核一停，两个核都停，调试器收到的停止事件是 2 号核的断点命中而不是 1 号核单步完成，过渡流程就被中途打断；
- **断点误触发**：不同用户程序加载在重叠的虚拟地址区间（比如代码都从 0x10000 开始）。给 A 的函数 foo（在 0x12000）设的断点，B 执行到自己地址空间里同为 0x12000 的位置也会停——但那里是 B 的代码。调试器必须分辨这次停下的是不是断点的主人，否则会把 B 的执行误记为 A 的【和Qmeu的调试机制有关：设置断点不改变内存指令，而是通过比对虚拟地址判断断点；虚拟地址的比对不区分页表】；
- **状态归属**：一个任务可以先跑在 1 号核上、之后被调度到 2 号核继续跑。协程链按线程各记一份，这个任务的 poll 历史就散在两个线程的链里，而它的协程编号（cid）在两条链里是同一个。取快照时如何把这些散落片段认出是同一段执行历史，而不是两条不相干的线？

本方案的目标，就是在多核环境下正确地恢复出异步逻辑执行流。

## 二、总体架构

调试器分三层，每层解决一类问题：

```
┌─ 调试适配器（TypeScript，跑在 VS Code 里）──────────────────┐
│   执行控制：什么时候单步、什么时候继续、调度锁怎么设          │
│   状态机：  识别内核↔用户的特权级过渡，驱动断点组切换         │
│   断点组：  每个程序一组断点 + 一份符号文件                   │
└──────────────────────┬──────────────────────────────────────┘
                       │ GDB/MI 协议（机器接口）
┌─ GDB + Python 跟踪脚本 ─────────────────────────────────────┐
│   白名单与地址表：决定"跟踪哪些函数、它们在内存哪里"          │
│   CallSite 断点： 在调用指令上记录"谁调用了谁"               │
│   影子栈：        每线程一份，维护当前协程链                 │
│   快照生成：      把逻辑链和物理栈尾部拼成一条完整链          │
└──────────────────────┬──────────────────────────────────────┘
                       │ GDB 远程调试协议
┌─ QEMU 虚拟机（SMP=2，两个核/hart）──────────────────────────┐
│   hart 0：内核协程 + 用户程序 A                              │
│   hart 1：内核协程 + 用户程序 B（或同一个用户程序）          │
└─────────────────────────────────────────────────────────────┘
```

数据流是单向闭环：程序执行触发断点停止 → 停止事件从 QEMU 传到 GDB → 调试适配器根据状态机做决策（单步还是继续）→ 下发命令 → 程序继续跑。跟踪记录**不是每次停止都写**，而是在被跟踪的 poll 断点、调用点断点命中时才更新；普通断点停下时，看到的是上一次跟踪事件留下的状态。

## 三、多核执行控制设计

多核调试首先要解决执行控制：哪些核继续运行、哪些核停止。这一层的三个设计决策都来自实际调试中遇到的问题。

**决策一：调度锁用 step 模式，而不是 on 模式。**

调试器跨特权级过渡时需要"一条指令一条指令"地走（单步），此时只希望当前核动。GDB 的调度锁（scheduler-locking）用于控制单步和继续时放行哪些核，它有两种模式，语义差别在"继续运行"的处理上：`on` 模式下，不光单步只放行当前核，**连"继续运行"也只放行当前核**——其他核会被永久冻结。实测时其他核被冻结在启动点，内核一直等待它们上线，整个系统死锁。`step` 模式则正好：单步只走当前核，而"继续运行"放行全部核，两个需求都能满足。

**决策二：单步序列锁定线程，外来停止静默继续。**

特权级过渡的处理过程是"命中边界断点 → 单步若干步 → 检测到已经到达另一边 → 切换断点组"。这段过程必须连贯，任何中途插进来的停止都会打乱它。多核下另一个核随时可能撞上断点停下来，如果调试器跟随它的停止事件处理，正在进行的过渡处理会被中断，无法完成。

解法是给每段单步序列记一个归属线程：序列开始时锁定发起过渡的那个线程，序列期间收到任何**别的线程**的停止事件，一律静默处理、不进入任何停止处理逻辑。这里有三点需要具体说明：

静默处理的范围是**不区分断点类型的**——别的线程因边界断点、用户断点或任何原因停下，一律静默。它发生的时间窗口仅限单步序列期间，即过渡处理的几条指令的执行时间，窗口外一切照常。窗口内的代价是真实的：恰好被踩中的用户断点，用户看不到它停下，而且这个断点会被临时禁用（见决策三）、直到下一次非该断点的停止才恢复。

为什么不让外来停止把单步序列暂停、放行后再恢复？障碍在 all-stop 模式的执行控制原语上：continue 放行全部核，锁定线程一旦被放行就失去单步节奏，恢复无从谈起；si 只走当前线程一条指令、其他核冻结。"锁定线程保持逐条单步"与"其他核自由运行"在 all-stop 下是互斥的。GDB 的 non-stop 模式（每个线程独立运行/停止）能同时满足两者，但那需要整个执行模型随之改造，作为远期选项。

静默处理的具体动作是发 continue。由于调度锁为 step 模式，continue 会放行**全部核**，锁定线程也被放行。于是锁定线程从"每步 si、每步检查"变成自由运行，直到撞上下一个断点才停——过渡检测随之从"步步检查"退化为"等锁定线程下一次停止时再做检查"。判定正确性不变（锁定线程下一次停止时检查流程照常执行），但逐条单步的粒度丧失了。这是当前实现的一个已知取舍，改进方向见 §7。

线程锁在**过渡判定完成、开始切组之前**解除，而不是切组完成后。原因：锁的语义是"单步序列进行中"，过渡一旦判定完成（已确认到达另一边），单步序列的使命即结束；切组本身是一串不等停的命令（清旧断点、插新断点），中间没有等待停止事件，锁无处生效；若锁保持到切组结束，切组期间其他核的正常停止也会被吞掉，反而扩大误吞范围。

**决策三：静默继续要临时禁用断点，防止原地重入。**

决策二存在一个问题：如果外来停止恰好命中断点，直接继续运行的话，程序前进一条指令后又会停在同一个断点上，反复循环。所以静默继续之前先把这个断点**临时禁用**，记到"待恢复"清单里；下次停止时只要不是这些断点之一，就自动把它们重新启用。这样既避免了反复停止，又不会丢失用户设置的断点。

## 四、特权级过渡与程序判定设计

这一层回答两个问题：**系统现在在"内核"还是"用户"？** 以及 **当前跑的是哪个程序？** 前者驱动断点组切换，后者决定跟踪状态记到哪个账本。这两问的答案来源不同，先说清楚再讲机制：内核/用户的区分看 PC 落在哪个地址区间（内核在高地址区、用户程序在低地址区）；"是哪个用户程序"则不看 PC——用户程序名来自 **hook 断点**（挂在内核"加载并启动用户程序"的必经函数上、带着一小段脚本的断点；命中时脚本读出这次启动的是哪个程序，把这个名字记为全局的"当前用户程序"）。为什么不能看 PC？因为不同用户程序的地址区间是重叠的，同一个地址值分不出是 A 还是 B。

**状态机**只有四个状态：内核态、内核单步到用户（过渡中）、用户态、用户单步到内核（过渡中）。驱动它的是边界断点——在内核"返回用户态"的必经之路和用户"发起系统调用"的必经之路上各设一个断点，命中就代表可能发生过渡。

过渡并不总是"逐条单步"。三条路径各有各的处理：**K→U** 方向在边界命中时先读 sepc（RISC-V 的"异常返回地址"寄存器，sret 返回指令跳到哪里看它）——它已经指向用户地址，说明 sret 即将真的返回用户态，一步即可判定到达，无需逐步单步；**U→K** 方向如果 PC 已经落在内核地址，说明边界函数被复用于内核内部调用（如系统调用分发函数被内核自己调用），直接切组，零步；只有 PC 还在用户侧的过渡路径才逐条单步、每步检查"到没到"。

**K→U 边界按 sepc 分类**来自双核实测中发现的一种情况。内核里"返回用户态"的那个函数（user_return）实际上被复用了：内核自己的任务切换也走它——把当前任务挂起、切到另一个内核任务继续跑。这两种情形都会命中 K→U 边界断点，但只有前者才是真正的特权级过渡，后者只是内核内部换了个任务。区分办法就是上面说的 sepc：指向用户地址区间是真过渡，进入状态机；指向内核地址区间（或读不到）按内核任务切换处理，静默继续。需要说明的前提是用户地址区间配置必须正确，否则所有 K→U 边界都会被误判成内核任务切换，调试器永远进不了用户态。

**跟踪状态按"程序"组织，而不是按进程或线程**。理由：一个异步任务的执行链可能跨核、跨线程，但它的代码永远属于某个程序（某份地址空间）。所以每个程序各有一份独立的跟踪账本——白名单、地址表、协程表——程序 A 的记录永远不会写进程序 B 的账本。切换程序只是把"当前账本"这个指针换一下，这一步开销恒定、与账本大小无关（注意：完整的一次切换还包括清旧断点、插新断点，那部分开销与断点数量成正比；符号文件已常驻、不随切换装卸）。这是本方案最重要的组织原则：**执行流的账，记在执行流所属的程序名下**。

## 五、异步跟踪设计

这一层负责记录协程的执行流。它有三个互相配合的部件。

**白名单与地址表**回答"跟踪谁"。异步程序里真正值得跟踪的函数只有两类：异步 poll 函数和少数同步辅助函数。白名单就是这份函数名单，地址表是"函数名→内存实际地址"的映射（打断点必须知道地址）。白名单的生成和缓存已经做了专门优化（详见组会汇报），这里不展开。

**CallSite 断点**回答"谁调用了谁"。在每个被跟踪函数内部，凡是一条调用指令（RISC-V 上叫 jal/jalr，x86 上叫 call）都可能引出协程的下游逻辑，在这些位置打断点就能记录调用关系。为了减少对程序运行的干扰，只对"调用了白名单函数"的调用指令设断点；间接调用的目标要到运行时才知道，所以全部设置、命中时再判断是否关心。

**影子栈**是核心数据结构，这里要如实说明它的维护方式。每个线程维护一份自己的"当前协程链"，每个协程分配一个编号（cid），并记录它的 poll 函数和协程环境指针（协程状态的存放地址，可以用来读它的状态字段）。入栈发生在协程的 poll 断点命中时。出栈没有直接的事件：GDB 的"函数返回断点"（FinishBreakpoint，能在函数返回时触发）在 RISC-V 上无法使用；于是出栈依靠两条启发式规则——同一个 cid 再次入栈时，把链截断到它为止（说明它又活跃了，它之上的都该出栈）；另外检测栈顶协程的 poll 函数已经不在物理栈上时，弹出一层。因此影子栈是**近似维护**的：可能短暂保留已经返回的协程，快照给出的链在大多数时刻精确，但不承诺逐时刻严格。

**快照**把逻辑链与物理栈尾部拼成一条完整的链。取快照时输出两部分：当前线程的影子栈（逻辑链，即协程嵌套关系），再加上物理栈上尚未被影子栈覆盖的尾部——正常运行时，这部分是"栈顶协程的 poll 函数之上更内层的同步帧"（当前正在执行的那个同步函数调用）；当影子栈为空（比如还没走到第一个 await 点）时，整段物理栈都作为尾部输出。两部分首尾相接，就是"从根任务一路到当前位置"的完整混合链。快照里每个节点还带上地址区间分类（内核/用户）供前端着色——注意对影子栈里的协程节点，这个地址是协程环境指针，只有物理栈的同步帧节点才是当前指令地址（PC）。

## 六、多核下的正确性设计

多核环境下"记错"的代价比"记漏"严重得多——记漏一次只是少一个点，记错一条链会污染整棵树的合并结果。所以这一层的设计原则是：**零错记，宁可漏记**。

**断点归属对账**。不同程序的地址区间重叠，给程序 A 设的断点可能被 B 命中。处理办法是给跟踪断点记上"我属于哪个程序"，命中时查"现在执行的是谁"——不是归属程序就静默跳过，既不记录也不影响执行。要如实说明现状边界：这个对账依赖全局唯一的"当前用户程序"名字，**同一时刻只有一个用户程序在跑时是可靠的**；两个用户程序同时跑在不同核上时，全局名字只可能是其中一个，另一个程序的命中要么被错记、要么被漏记。并行多用户程序的完整对账是下一节的设计走向，不是现状。

**每线程影子栈隔离**。协程链按线程分开记：1 号核上的链和 2 号核上的链各自独立维护。一个任务跨核迁移时，新旧两个线程的链里都可能短暂保留它的记录（这是影子栈近似维护的代价），但记入的账本始终是它实际执行过的线程。

**两个如实说明的现存隐患**。其一，前端面板在合并快照时目前**忽略了线程号**，把所有线程的链混进同一棵树，而不同程序的用户协程 cid 是各自从 1 开始编号的——两条不相干的链可能因为 cid 相同被错误合并（内核的协程编号也是独立的序列，同样从 1 开始）。其二，快照只包含"当前选中的那个线程"的链。这一点要澄清：**并不是 all-stop 模式做不到**——all-stop 下所有核都停着，其他线程的链存在于 GDB 进程中，逐个读出来在技术上是可行的；限制来自快照命令的实现只读当前线程。这两个隐患分别对应下一节的两条设计走向。

## 七、现状缺口与设计走向

**过渡期间外来停止的呈现**。现状对单步序列窗口内的外来停止静默吞掉（见 §3 决策二）。改进方向：外来停止正常发 stopped 事件呈现给用户；用户 continue 时，调试器先恢复单步序列（切回锁定线程、逐条 si 直到过渡判定完成），再放行全部核。期间外来核保持冻结，用户按 continue 后表现为一次短暂停顿（远程单步往返，几十毫秒量级）。状态机需要增加"挂起"状态，continue 等执行请求需要路由到序列恢复流程。具体行为留待实测验证。

**并行多用户程序**是下一步要解决的主要问题。现状已经能扫描"每个核在内核态还是用户态"，但用户程序名依赖 hook 设置的全局变量，同一时刻只有一个"当前组"生效。设计走向是把"当前组"改成"每核一组"：每个核记一个自己正在执行的程序，边界命中和归属对账都按核各自的组来处理。这里有一个必须解决的数据来源问题：每核的用户程序名从哪里来？PC 分不出用户程序，全局 hook 变量只有一个——需要读取每个 vCPU 的当前任务结构（从内核数据结构里读出该核正在跑的任务属于哪个程序），这是这项设计的关键前置工作。符号文件方面目前已经全部常驻、不随切换装卸，为这一方向做好了准备。

**快照聚合的数据契约**先定下来，面板视觉设计另行讨论。多核快照应为一张列表：每个线程一条链，附带线程号、所属程序、以及**全局事件序号**（用于对账先后顺序；现状只有每个协程自己的 poll 计数，跨协程的全局计数器需要新增，由谁递增、存在哪个账本里也是设计点）。前端拿到这份列表后可以按线程分组、按程序着色。这样即使当前停的是 1 号核，用户也能看到 2 号核最近一次停止时留下的链。

**已知的性能余量**：符号文件加载约 130 毫秒/次（目前只在首次加载时付出）；特权级过渡的单步只发生在 U→K 的用户侧路径上，步数取决于边界函数内的指令数，K→U 方向基本一步、U→K 的 PC 已在内核路径零步。

## 术语表

| 术语 | 解释 |
|---|---|
| 白名单 | 要跟踪的函数名单（异步 poll 函数 + 同步辅助函数） |
| 地址表 | "函数名 → 内存实际地址"的映射表，打断点必需 |
| CallSite | 函数内部的一条"调用别的函数"的指令位置 |
| 影子栈 | 每线程一份的当前协程嵌套链，由 poll 命中维护、启发式出栈 |
| cid | 协程编号，调试器为每个协程实例分配的标识，按程序各自从 1 开始 |
| 断点组 | 一个程序专属的一组断点 + 符号文件，切换组 = 切换跟踪目标 |
| 边界断点 | 设在"内核↔用户必经之路"上的断点，驱动状态机 |
| hook 断点 | 带一小段脚本的断点，命中时执行脚本；用于读出"这次启动的是哪个程序" |
| 特权级过渡 | 程序在内核态与用户态之间的切换过程 |
| sepc | RISC-V 的"异常返回地址"寄存器，sret 指令跳到哪里看它 |
| hart | RISC-V 对硬件线程（核）的叫法 |
| all-stop | GDB 模式：任一核停止时全部核停止 |
| 调度锁（scheduler-locking） | GDB 设置：控制"继续/单步时哪些核可以跑" |
| 交叉命中 | A 程序的断点被 B 程序命中（地址区间重叠所致） |
| 符号文件 | 记录"函数名对应哪个地址"的调试信息文件 |
