# K3 内核态远程调试复现手册

照着这份手册做，你能在 K3 真板上复现 async-os 内核态协程测试的远程调试，并在 Async Inspector 面板里看到异步逻辑执行流。

手册只覆盖内核态。用户态协同跟踪还在修，不在这里。所有地址、哈希、版本号都经过实测。

## 1. 这份手册固定的是什么

我们把“内核态单独调试能跑通”这一刻的完整状态冻结下来。后面继续适配用户态时，随时能回到这个状态复现。

冻结的东西分两边：

| 仓库 | 分支 | 冻结点 | 说明 |
|------|------|--------|------|
| async-os-original | `feat/k3-port` | commit `31a327d`，tag `k3-kernel-debug-baseline` | 内核源码基线 |
| async-debug | `feat/k3-board-adapter` | tag `k3-kernel-debug-baseline` | 调试器、启动脚本、OpenOCD 配置、本手册 |

内核源码基线落在一个独立 worktree 里：`/home/iris/data/async-os-original-k3-baseline`，HEAD detached 在 `31a327d`。调试用的固件和构建产物都在这个 worktree 的 `artifacts/` 下。

为什么单独开 worktree：主工作区 `async-os-original` 的 HEAD 已经走到 `154eebc`（用户态支持改动）。身份校验脚本要求工作区 HEAD 和构建时的 commit 一致。主工作区对不上，基线 worktree 对得上。所以内核态调试认基线 worktree 的产物，F5 的源码窗口开主工作区（两边的 `coroutine_test/src/main.rs` 逐字节相同，断点不会错位）。

两个 tag 是本地标记。OS 基线 commit `31a327d` 已在远程 `feat/k3-port` 历史里，按哈希 checkout 即可。async-debug 的快照 commit 目前只在本地，跨机器复现要先推送 `feat/k3-board-adapter` 分支和 tag。

## 2. 整套调试通路是怎么工作的

### 2.1 三根线和四个角色

板子和电脑之间接三根线，各管一件事：

- **USB-TTL 串口线**（`/dev/ttyUSB0`）管“说话”。板子启动的每一行日志从这走，U-Boot 命令也从这发。
- **USB 下载线**管“搬东西”。板子进下载模式后，BootROM 只认这根线喂过来的固件。
- **J-Link（JTAG）**管“踩刹车”。它能随时停住 CPU、读寄存器、下断点。VS Code 的断点最终都靠它。

电脑上四个角色接力：

```
VS Code 扩展 ardb（你操作的面板）
  → gdb-multiarch（加载 Python 跟踪插件）
    → OpenOCD（localhost:3333，把 GDB 协议翻译成 JTAG）
      → J-Link → K3 芯片调试模块 → 板上内核
```

串口和下载线由启动状态机脚本驱动，不在调试协议路径上，但启动流程离不开它们。

### 2.2 JTAG 为什么特殊

K3 的 JTAG 信号和 TF 卡槽的引脚复用。默认这组引脚给 TF 卡用，JTAG 是关的。引脚对应关系：

| TF 卡（MMC1）引脚 | JTAG 信号 |
|------|------|
| DAT0 | TCK |
| DAT1 | TMS |
| DAT2 | TDO |
| DAT3 | TDI |

只有 **debug 版 FSBL** 跑起来后，才会把这组引脚切给 JTAG，串口打印 `Debug JTAG enabled on MMC1 pins`。在此之前 J-Link 看到的是“全 1”，正常。所以 OpenOCD 必须等 debug FSBL 跑过之后再起，起早了扫描失败，而且失败后它拒绝一切后续连接。

物理上，TF 槽插一张调试扩展卡，卡上引出 JTAG 接口接 J-Link。套件自带这张卡和仿真器。

### 2.3 Host-DWARF：板上跑瘦镜像，符号留电脑

板上运行 release 构建的内核镜像，不带调试信息，小而快。电脑端加载**同一次构建**产出的 ELF，带完整符号和源码行号。两边身份必须一致，否则断点对不上。

判断是否同一次，靠 `manifest.json`：记录构建时的 git commit、ELF 和 bin 的 sha256、关键源文件的 sha256。attach 前校验脚本逐项比对，不一致就拒绝连接。

### 2.4 启动链和两个暂停点

板子每次上电走五级接力：

```
BootROM → Debug FSBL → OpenSBI → U-Boot → booti → async-os
```

调试流程在两个地方暂停：

**P1：booti 前。** U-Boot 已经把内核和 DTB 装进内存，停在命令行。状态机在这等你创建 release 文件才继续。此时 JTAG 已通、内核镜像已在内存、CPU 空闲。全部调试准备在这个窗口完成：起 OpenOCD、预埋 P2 触发。

**P2：rust_entry。** 内核入口函数。我们在 CPU 调试模块里预埋一个硬件执行触发，地址指向 `rust_entry`。内核启动后踩中它，CPU 自己冻住。这就是 QEMU `-S` 参数在真板上的等价物。

P2 用硬件触发而不是软件断点，原因有两个。一是 booti 瞬间 J-Link 常因电源浪涌掉线，触发写在 CPU 内部，掉线后内核仍会自停，重插 USB、重新 F5 就能接管，不用重刷板子。二是 P1 阶段 MMU 没开，软件断点写不进内核虚拟地址，硬件触发不写内存，只设触发寄存器，不受影响。

`_start` 汇编先建页表、开 MMU，再跳到虚拟地址的 `rust_entry`。所以触发地址用虚拟地址，内核开 MMU 后踩中。本基线的 `rust_entry` 首条指令在 `0xffffffc14000406e`（`addi sp,sp,-32`）。**这个地址随构建变化**，每次重编译都要从 ELF 重新解析，方法见第 6 节。

### 2.5 异步逻辑执行流跟踪

调试器给出两种视图：物理栈显示 CPU 跑到哪条指令，协程树显示异步逻辑执行流。

Python 插件静态扫 ELF 符号表，按 crate 生成白名单。你勾选要观察的 crate，插件给这些异步函数埋两类探针：poll 入口断点、await 调用点断点。运行中维护一棵带 CID 编号的协程树。每次暂停产出一份快照，显示哪个协程 poll 了哪个、await 关系是什么。面板左侧的 Logical Call Tree 就是这棵树。

启动瞬间还没有协程，快照走物理栈兜底，你会看到 `rust_entry` 这样的 SYNC 节点。等协程跑起来，树里才出现带 CID 的异步节点。

### 2.6 内核态用户态协同调试

这是下一步的目标，这里只说清楚概念。内核和用户程序地址空间不同、符号文件不同。调试器把它们分成断点组，同一时刻只激活一个组。特权级边界有两个边界断点：`user_return`（内核→用户）、`user_task_top`（用户→内核）。命中后状态机自动切换断点组再继续，对你透明。`init_user` 上的 hook 断点读用户程序名，决定切到哪个组。

本手册的内核态调试只用 `kernel` 组，不触发组切换。

## 3. 准备

### 3.1 硬件和接线

需要：K3 COM260 板、调试扩展卡、J-Link、USB-TTL 串口线、USB 下载线、12V 电源。

接线要点：

- 调试扩展卡插 TF 槽，J-Link 接卡上的 JTAG 口。
- 串口线接 12Pin 排针的串口引脚，电脑端识别为 `/dev/ttyUSB0`。
- USB 下载线接板子 USB-C 数据口。注意 USB-C **不能给板子供电**，供电走 12V 圆孔。
- 电源功率要够。实测 12V/1.5A 适配器会让 PMIC 闭锁（灯灭、风扇不转），建议 12V/5A。

进下载模式：完全断电，短接 12Pin 排针的 **10 号针 FORCE_RECOVERY** 到地，再上电。BootROM 读到这个 strap 就进 USB 下载模式。**此时风扇不转、灯灭是正常的**，下载模式切断了 3.3V 供电链，不是板子坏了。

### 3.2 软件工具

实测通过的版本：

| 工具 | 版本 | 用途 |
|------|------|------|
| gdb-multiarch | 15.1 | GDB 中间人 |
| OpenOCD | 0.12.0 | JTAG 翻译层 |
| fastboot | 34.0.4 | USB 下载 |
| minicom | 发行版自带 | 串口终端 |
| python3 | 3.x | 状态机、校验脚本 |
| VS Code + `code` CLI | 发行版自带 | 扩展宿主 |

Ubuntu 上装：`sudo apt install gdb-multiarch openocd fastboot minicom`。

重新构建内核还需要 Rust 工具链和 `riscv64-unknown-elf` binutils（`rust-objcopy` 等）。只用现成产物复现调试的话，不必装 Rust。

## 4. 一次调试会话

八个步骤。顺序有讲究，尤其是 OpenOCD 必须在 P1 之后起。

**第 0 步：准备。** 确认三根线接好。VS Code 里停掉所有旧调试会话（红色方块）。开扩展宿主窗口，打开主仓库：

```bash
code --new-window --extensionDevelopmentPath=/home/iris/data/async-debug /home/iris/data/async-os-original
```

**第 1 步：进下载模式上电。** TF 槽插调试卡，短接 12Pin 的 10 号针 FORCE_RECOVERY，断电再上电。风扇不转正常。

**第 2 步：跑状态机（终端 1）。**

```bash
cd /home/iris/data/async-debug/testcases/k3-async-os
K3_PAUSE_BEFORE_BOOTI=1 K3_ASYNCHOS_TIMEOUT=600 ./boot_golden_flow.sh --uart /dev/ttyUSB0
```

脚本自动走：USB 下载 FSBL → 等 SPL → 等 OpenSBI → 等 U-Boot → fastboot 传内核到 `0x140000000`、DTB 到 `0x138000000`。等到这行出现：

```
[PAUSE] before booti: kernel+dtb staged, U-Boot at prompt.
```

状态机到 P1 会自己删掉上次残留的 release 文件，不用手动清。

**第 3 步：起 OpenOCD（终端 2）。**

```bash
cd /home/iris/data/async-debug/testcases/k3-async-os
./start_openocd.sh
```

看到这行才算成功：

```
Examined RISC-V core; found 4 harts
```

报 `No J-Link device found` 就拔插 J-Link 的 USB 线再试。报 `JTAG scan chain interrogation failed: all ones` 说明起早了，FSBL 还没复用引脚。

**第 4 步：预埋 P2 硬件触发（终端 3）。** 用 gdb 连一次 OpenOCD，停住 CPU，设触发，放行：

```bash
gdb-multiarch -batch \
  -ex 'set confirm off' \
  -ex 'file /home/iris/data/async-os-original/apps/coroutine_test/coroutine_test_riscv64-k3.elf' \
  -ex 'target remote :3333' \
  -ex 'monitor halt' \
  -ex 'monitor bp 0xffffffc14000406e 4 hw' \
  -ex 'monitor resume' \
  -ex 'detach' -ex 'quit'
```

看到 `breakpoint set at 0xffffffc14000406e` 即成功。地址必须和你 ELF 里的 `rust_entry` 一致，重编译后要重新解析（第 6 节）。

**第 5 步：放行 booti。**

```bash
touch /tmp/k3_pause_release_booti
```

U-Boot 执行 booti，内核启动，踩中 `rust_entry` 触发，CPU 冻住。

**第 6 步：F5 接管。** 在扩展宿主窗口的“运行和调试”面板选 `K3 async-os Host-DWARF (JTAG+OpenOCD)`，按 F5。扩展连上 OpenOCD，内核停在 `rust_entry`。

**第 7 步：下断点，看异步流。** 见第 5 节。

**第 8 步：收工。** 顺序固定：VS Code 停止调试 → Ctrl+C 停 OpenOCD → 板子断电。不要在调试会话还连着时直接拔电源。

## 5. 看到异步逻辑执行流

F5 停在 `rust_entry` 后，按这个顺序操作面板：

1. **Gen Whitelist**：扫 ELF 符号表，按 crate 列出可观察函数。
2. 勾选要观察的 crate，勾 **Async only**（只装异步函数探针），**Apply Whitelist**。
3. 选一个 async 函数点 **Trace**，设为观察根节点。
4. 在 `apps/coroutine_test/src/main.rs` 的 await 点附近下普通断点。这个测试的逻辑是：主协程锁住 Mutex，spawn 一个子协程去抢同一把锁，主协程 sleep 后放锁，子协程拿到锁，主协程 join 子协程。合适的断点位置是 `let res = j.await.unwrap();` 这一行，或 `for` 循环里的 `println!`。
5. **Continue**。内核从 `rust_entry` 往下跑，协程测试执行，命中断点。
6. 命中后看面板：左侧 **Logical Call Tree** 出现带 CID 的协程节点，这就是内核态异步快照。History 看执行历史，Snapshot 看当前暂停快照。

coroutine_test 的预期输出（串口）：先 `Mutex locked: 23`，子协程等锁，主协程放锁后子协程 `spawn Mutex locked: 34`，然后 `res 32`，最后循环打印 `for test preempt 0..99`。断点命中时面板的协程树应当反映出主协程和 spawn 子协程的 await 关系。

## 6. 身份校验与重建

### 6.1 校验

attach 前跑校验，确认工作区和构建产物身份一致：

```bash
python3 testcases/k3-async-os/verify_k3_workspace.py --workspace /home/iris/data/async-os-original-k3-baseline
```

通过时打印：

```
PASS: ... 与 manifest 身份对齐(commit=31a327dc, 20 个源文件一致)
```

校验四件事：产物存在；ELF/bin 哈希和 manifest 一致；git HEAD 等于 manifest.commit 且工作树干净（子模块内部改动除外）；manifest 里的源文件逐个哈希比对。任何一项不过都拒绝连接，防止符号错位。

`boot_golden_flow.sh` 的 preflight 会自动调 `verify_artifacts.sh` 做这个校验。

### 6.2 重新解析 rust_entry 地址

每次重编译内核，`rust_entry` 地址可能漂移。用下面任一方法取函数首条指令地址：

```bash
# 方法一：objdump 找符号
riscv64-unknown-elf-objdump -d <ELF> | grep -A1 'rust_entry17h'

# 方法二：gdb 按源码行解析（mod.rs 第 6 行是 rust_entry 定义）
gdb-multiarch -batch -ex 'file <ELF>' -ex 'break mod.rs:6' -ex 'info break'
```

本基线实测：函数首条指令 `0xffffffc14000406e`（`addi sp,sp,-32`），gdb 跳过 prologue 后的源码断点在 `0xffffffc14000407e`。两者都在 `rust_entry` 内，预埋触发用函数首地址 `0xffffffc14000406e`。

注意 ELF 里没有全局 `rust_entry` 符号（release 下是局部符号），`info address rust_entry` 会报无符号。要用 objdump 的 mangled 名或 gdb 的源码行解析。

### 6.3 重建后必做

重编译后：重跑校验脚本；重新解析 `rust_entry` 地址并更新第 4 步的触发命令；如果改了 launch 配置里的地址，同步更新。manifest 会记录新的 commit 和哈希，工作区 HEAD 也要跟着走到新 commit。

## 7. 排障速查

| 现象 | 原因 | 处理 |
|------|------|------|
| OpenOCD 报 `JTAG scan chain interrogation failed: all ones` | 起早了，FSBL 还没复用 JTAG 引脚 | P1 之后再起 OpenOCD |
| OpenOCD 报 `No J-Link device found` 或 `Sending data to device timed out` | J-Link USB 掉线（板子上电浪涌） | 拔插 J-Link USB，重启 OpenOCD。P2 触发已使内核自停，重新 F5 即接管 |
| VS Code 连上但 OS 已跑远 | 旧调试会话吃掉了 rust_entry 暂停 | F5 前停掉所有旧会话 |
| gdb 反复连查 pc，启动冻在半路 | 每次 gdb 连接都停住 CPU，detach 不自动恢复 | 查状态用单次连接，记得 `monitor resume` |
| 暂停点被跳过，U-Boot 直接 booti | 残留 release 文件 | 状态机已自动清；手动跑时先 `rm -f /tmp/k3_pause_release_booti` |
| 板子灯灭、风扇不转（非下载模式） | 12V/1.5A 适配器功率不足，PMIC 闭锁 | 换 12V/5A 适配器，重插电源圆孔恢复 |
| 校验报 HEAD 不一致 | 工作区 HEAD 不等于 manifest.commit | checkout 到基线 commit，或重编译并更新 manifest |
| 校验报某源文件不一致 | 源码改过没重编译 | 重跑 `k3_host_dwarf_build.sh` |

## 8. 已知边界

- **只覆盖内核态。** 用户态协同跟踪有待修 bug（提案 T1）：K3 调试模块只有 4 个硬件断点，用户态大量插桩超限。内核态协程调试不受影响。
- **旧 debug FSBL，4GB DDR。** 新官方 FSBL（8GB）的 SPL 在 fastboot 下载 ITB 后挂死，根因未确认，当前绕过。旧 FSBL 稳定但 DDR 容量受限。
- **SMP=1，JTAG 100 kHz。** 只开 cluster0 的 core0。更快或多核在当前固件下不稳定。多核调试不在本手册范围。
- **P2 地址随构建变化。** 手册里的 `0xffffffc14000406e` 只对 coroutine_test 基线（`31a327d`）有效。重编译必须重新解析。
- **ITB 不含 RCPU 固件。** 含 RCPU 的 ITB 会让 booti 后 JTAG 失效（全 1），调试路径用旧版不含 RCPU 的 ITB 绕过。
