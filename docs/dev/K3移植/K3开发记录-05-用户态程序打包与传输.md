# K3 开发记录 05:用户态程序(pipetest)在 K3 上的打包与传输

- **日期**:2026-11-10
- **面向读者**:完全没学过硬件也能看懂(概念先行,步骤在后,术语表在最后)

## 这篇记录解决什么问题

我们之前在 K3 上跑通的 `coroutine_test` 是**内核态**程序——它整个生活在内核内部,不需要从"磁盘"上读任何文件。

但真正的用户态测试程序 `pipetest` 不一样:它是个独立的程序文件(ELF 可执行文件,5.9MB),内核要先**从某个"磁盘"里把这个文件读出来**,才能启动它。问题是:K3 板子上我们能用到的"磁盘"在哪里?——这就是这篇记录要解决的:把测例文件送到内核手里。

## 先把概念讲清楚(每个都用大白话)

### 1. 内核态 vs 用户态

- **内核态**:程序直接跑在系统最底层,能碰任何硬件,权限最高。coroutine_test 就是这种。
- **用户态**:普通程序,权限受限,想用硬件(比如读文件、输出文字)必须"举手"向内核申请(syscall 系统调用)。Linux 里你运行的所有程序、手机上的 App,都是用户态。pipetest 是用户态。

### 2. 块设备 = 按"页"存取的大本子

U 盘、硬盘、SD 卡、以及 K3 板子上焊着的 UFS 存储芯片,都是同一类东西:里面存数据,但**不能按字节随便读,必须一"块"一"块"地读**(一块 = 512 字节,像一页纸)。这类设备统称**块设备**。

### 3. 块设备驱动 = 唯一会"翻本子"的手

内核自己不认得任何具体的存储硬件。**块设备驱动**就是教内核操作某一种硬件的"翻译官":"给我读第 1000 块"、"把这块写到第 2000 块"。没有驱动,内核就算把 U 盘插上了也读不出一个字。

### 4. 文件系统 = 本子里的"目录和页码索引"

块设备只是一页一页的纸,纸上是死数据。**文件系统**(FAT、ext4 之类)负责把这些页组织成"文件":在开头记一张目录表——"`pipetest` 这个文件从第 300 页到第 12000 页"。内核说"打开 /pipetest",文件系统查目录、算出页码、再叫驱动去翻页。

### 5. 镜像(image)= 把"本子"整个复印成一个文件

`disk.img` 就是一张"虚拟的本子":一个普通文件,内容按块设备的格式排好。反过来,把这个文件塞进内存,内核就能把它当真正的磁盘来用。

### 6. RamDisk = 用内存假装出来的磁盘

内存本来就按字节随便读写,我们可以**把一片内存假装成块设备**(写个小驱动,把"读第 N 块"翻译成"去内存某个地址取 512 字节")。做出来的这个东西叫 **RamDisk(内存盘)**。它的好处:不需要任何真实硬件的驱动,是纯软件。

## 我们的处境:K3 上没有能用的"磁盘"

- 真实硬件:板上有 UFS 芯片(128GB),但我们的内核**没有 UFS 驱动**,碰不了它。
- 虚拟硬件:qemu 模拟器会给内核一个"假的磁盘"(virtio-blk),但**真板 K3 上没有这个**,这个口是空的。

所以之前 qemu 上"挂磁盘读文件"的办法在 K3 上完全行不通。K3 平台上连一个可用的块设备都没有。

## 解法:把测例"烤"进内核镜像(自带干粮)

既然运行时没有磁盘,那就**在构建时**把测例文件直接打进内核二进制里,内核启动后把这段数据搬进内存做成 RamDisk,再在 RamDisk 上挂文件系统。这套机制代码里已经现成,叫 `img` 特性,工作流程:

```
make ... FEATURES=img
  └─ 编译时:把 disk.img 原样嵌进内核二进制(.incbin,相当于 C 的 include)
  └─ 启动时:内核把这段数据映射到测试内存区(K3 上是 0x180000000)
  └─ 启动时:把它整个拷贝成一个 RamDisk(内存假磁盘)
  └─ 启动时:在 RamDisk 上挂载 FAT 文件系统 → 根目录里就有 pipetest 了
```

### 两个必须注意的坑

1. **镜像不能超过 64MB**:K3 的配置里测试内存区只有 64MB(`testcase-memory-size = 0x400_0000`)。而默认脚本 `build_img.sh` 做出来的镜像是 **120MB**——用它直接开机就会在拷贝时读越界、崩溃。所以必须自己做小镜像。
2. **构建时需要环境变量 `AX_WORK_DIR=<仓库根目录>`**:嵌入文件的路径靠它定位。

## 步骤一:做一张 20MB 的 FAT16 镜像(全程不需要 root)

本机没有 sudo 密码、没有 pip、没有 mcopy,但 **`apt-get download` + `dpkg -x` 可以把工具包解压出来用,不需要 root**:

```bash
# 1. 弄到 mcopy/mdir 工具(往镜像里放文件、列文件用)
cd /tmp && apt-get download mtools && dpkg -x mtools_*.deb mtools-x/

# 2. 做一个 20MB 的空镜像,格式化成 FAT16 文件系统
cd async-os-original
truncate -s 20M disk.img && mkfs.vfat -F 16 disk.img

# 3. 把需要的测例文件放进镜像
/tmp/mtools-x/usr/bin/mcopy -i disk.img -s \
  testcases/riscv64_linux_musl/hello_world \
  testcases/riscv64_linux_musl/pipetest \
  testcases/riscv64_linux_musl/busybox \
  testcases/riscv64_linux_musl/libc.so \
  testcases/riscv64_linux_musl/etc ::/
chmod 777 disk.img
```

- 为什么只放这几个文件:hello_world 和 pipetest 是要跑的测例;busybox 和 libc.so 是内核启动时会给它们建"快捷方式"(软链接)的对象,不放会报错;etc/ 里有环境变量文件。
- 为什么选 FAT16 而不是 FAT32:20MB 的 FAT32 簇数低于规范下限,工具会警告,解析代码还可能认错格式。FAT16 没这个问题(块设备里的 FAT 系统对内核代码是透明的,选个稳的就行)。

## 步骤二:构建内核(绕过会失败的两个前置步骤)

`make build` 默认会先做两件事:重编用户程序(本机**没有** riscv64-linux-musl-gcc 交叉编译器,必失败)、重做 120MB 镜像(需要 sudo,必失败)。测例在 10-21 已经编好放在 `testcases/` 里了,所以直接构建最终产物:

```bash
cd async-os-original
AX_WORK_DIR=$PWD make apps/user_boot/user_boot_riscv64-k3.bin \
  A=apps/user_boot PLATFORM=riscv64-k3 ARCH=riscv64 MODE=release SMP=1 LOG=info FEATURES=img
```

产物:`apps/user_boot/user_boot_riscv64-k3.bin` = 22,352,000 字节 ≈ 20MB 镜像 + 1.3MB 内核。

## 步骤三:传上板子(adb 坏了,走串口 xmodem)

### adb 为什么坏了(一句话版)

`adb devices` 一直挂起的根因:adb 服务程序每次启动都会在初始化早期**崩溃**,崩溃后卡在系统的错误转储流程里变成"僵尸进程"永远不退,还把端口 5037 占死了。这类进程 kill 不掉,只能重启电脑。所以我们暂时绕开 adb,纯串口操作。

### 串口流程

1. 断电重启 → U-Boot 的打断窗口只有上电后 1~2 秒(本 BSP 没有 "Hit any key" 提示,但会打一行 "Autoboot in 5 seconds")。我写了个自动拦截脚本 `/tmp/k3-uboot-storm.sh`:盯着串口日志,一看到新 U-Boot 就每 50ms 发一个 `s`,看到 `=>` 提示符立刻停。要点:**发的 s 越少越好**——发多了会堵在输入队列里,把后面的命令搅成乱码(早上 200 个 s 堵了 40 秒;下午 19 个 s 还是和第一条命令混成了"未知命令",多发一次就好)。
2. 进 U-Boot 后:`loadx 0x140000000` → 看到 `## Ready for binary (xmodem) download`
3. ⚠️ **先停掉后台的串口捕获进程**(那个 cat 会抢读字节,把传输协议搅坏),然后:

```bash
stty -F /dev/ttyUSB0 115200 raw -echo -crtscts
sx -v user_boot_riscv64-k3.bin > /dev/ttyUSB0 < /dev/ttyUSB0
```

4. 21.3MB 在 115200 波特率下约 **31 分钟**(这是纯串口方案最大的痛点;adb 修好后 push 到 UFS 再 `load scsi` 只要几秒)
5. 传输完重启捕获,然后:`load scsi 0:2 0x138000000 k3.dtb` → `booti 0x140000000 - 0x138000000`

## 术语速查表

| 词 | 一句话解释 |
| --- | --- |
| 内核态 / 用户态 | 程序权限的高低两种身份;用户态要"举手"(syscall)才能用硬件 |
| 块设备 | 按 512 字节一"块"存取的存储设备(U 盘、硬盘、UFS 芯片) |
| 块设备驱动 | 教内核操作某一种存储硬件的代码 |
| 文件系统(FAT) | 把块设备里的死数据组织成"文件+目录"的格式 |
| 镜像 disk.img | 把一块"磁盘"原样复印出来的普通文件 |
| RamDisk | 用内存假装出来的磁盘,纯软件,不需要硬件驱动 |
| ELF | Linux 下可执行文件的标准格式 |
| 波特率 | 串口每秒传多少"位";115200 ≈ 每秒 11KB |
| xmodem | 一种老式串口传文件协议,带校验,慢但可靠 |
