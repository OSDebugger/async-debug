# 在 K3 真板上运行 async-os:全景讲解与工作计划

> 本文档回答两个问题:
> 1. 前面讨论里出现的那些"黑话"(BootROM、FSBL、JTAG、APLIC……)都是什么、有什么用;
> 2. 把 async-os 跑上 K3 真板并用 async-debug 调试它,一共要做哪些工作、每一步为什么。
>
> 面向完全没接触过硬件的读者。所有数字都来自官方手册、前人博客(k3gdb)和仓库代码,有把握才写;没把握的标了【待确认】。

# 第一部分:概念讲解

## 1. 三个主角

| 名字 | 是什么 | 在这次任务里的角色 |
| --- | --- | --- |
| **async-os** | 你自己写的异步 Rust 内核。内核 = 操作系统的核心,直接管 CPU、内存、外设。它平时跑在 qemu(模拟器)里,qemu 会假装自己是一台 RISC-V 电脑 | 被移植的对象,最终要跑在真板上 |
| **async-debug** | 一个 VS Code 扩展,专门调试异步 Rust 内核。核心能力:看内核里 Future 之间的 poll 关系(Inspector、白名单、Trace、History、Snapshot) | 最终目标:让它调试真板上的 async-os |
| **K3 COM260 Kit** | SpacemiT(进迭时空)K3 芯片 + COM260 模组 + 载板,香蕉派 BPI-SM10。RISC-V 64 架构,8 个大核(X100)+ 8 个 AI 核(A100) | 真板:真正的硬件 |

**qemu 和真板的差别,就是"移植"的全部内容**:qemu 是一台假想的、按教科书搭的机器;K3 是一台具体的、地址和外设都不同的机器。async-os 的 riscv64 代码大部分不用动,要动的是"平台相关"的那一小层(第四节讲)。

## 2. 启动链:板子怎么一步步活过来

板子上电后不是一步进入内核,而是一场接力赛,每级程序叫醒下一级:

```
BootROM → FSBL → OpenSBI → U-Boot → 内核(async-os)
   (芯片里固化)   (引导)    (底座)    (搬运工)   (主角)
```

### 每个概念是什么

**BootROM**:芯片出厂时烧死的一小段程序,上电第一个执行。它除了正常启动,还能进 **Recovery 下载模式**:按住板上的 FORCE_RECOVERY 再上电,芯片就变成一个 fastboot 设备,等着电脑传固件。这是调试的"总入口"——因为后面每一级固件都可以通过它临时"灌"进板子,**不需要烧写、断电就还原**,非常安全。

**strap**:芯片上电的一瞬间,某些引脚的电平会被读成配置,决定"从哪启动"(TF 卡 → UFS 等)。可以理解为板子上的拨码开关。前人验证用的是 TF 卡 → UFS 这条链。

**FSBL**(第一级引导程序):BootROM 加载它。它负责初始化内存(DDR)——内存没初始化之前,后面谁都干不了活。前人改过一版 **Debug FSBL**,多干一件事:把 TF 卡槽引脚切给 JTAG(第五节),这是打开调试后门的关键。

**OpenSBI**:RISC-V 世界的标准底座。它跑在最高特权级(M 态),给内核提供标准服务:定时器、核间通信、跨态切换。qemu 里也有它。async-os 的时钟目前就是通过 SBI 接口用的,所以这部分 K3 上也能直接复用。

**U-Boot**:功能强大的引导器,有自己的命令行(提示符 `=>`)。它就是我们口中的"搬运工":通过 fastboot 接收内核镜像放进内存,再执行 `booti` 指令跳过去启动。它还能初始化 UFS(板载存储)、扫描磁盘。

**FIT**:一种打包格式,把多个镜像(比如 OpenSBI+U-Boot)打成**一个文件**,里面写明每个部件该加载到哪个地址、带校验和。前人的 FIT 文件名是 `k3-jtag-ram-opensbi-uboot.itb`——一个文件搞定两级固件。

**fastboot**:一种 USB 下载协议。BootROM 的 Recovery 模式是 fastboot 设备,U-Boot 也能进入 fastboot 模式。电脑端的 `fastboot` 命令就是和它对话的工具。

**UFS**:板载存储芯片(相当于电脑的硬盘)。官方固件就躺在它的分区里,布局是:

```
env | bootinfo | fsbl | esos | opensbi | uboot | ESP | bootfs | rootfs
```

**关键结论:官方 FSBL/OpenSBI/U-Boot 本来就在 UFS 里,正常上电就能走到 U-Boot 命令行。** 前人只替换了 rootfs 分区。所以第一次实验不需要任何额外固件。

**内核镜像 + DTB**:U-Boot 通过 fastboot 把内核传到内存 `0x140000000`、设备树传到 `0x138000000`,然后 `booti 0x140000000 - 0x138000000` 启动。

**DTB / 设备树**:给内核的"硬件清单"文件——UART 在哪、内存多大、中断怎么接,全写在里面。每块板子硬件不同,所以每块板子一份。K3 的设备树前人已经做好(在 tgoskits 仓库里,连编译好的 .dtb 都有)。

**串口 / UART**:板子的"嘴"。芯片把文字日志按位从两根线发出来,电脑用 **USB-TTL 模块**(我们这块是 CH340 芯片)翻译成 USB。约定 115200 波特率(每秒发多少位)。K3 的调试串口在 12Pin 排针的第 3/4/7 针(板子 RX←模块 TX、板子 TX→模块 RX、GND 共地)。电脑上看到的设备节点是 `/dev/ttyUSB0`,用 minicom 之类的工具看它输出。

### 前人把整条链做成了一键脚本

脚本叫 `boot_golden_flow.sh`(启动状态机)。核心思想:**不靠 sleep 猜时间,而是看串口上真实出现的标志才进行下一步**:

```
BootROM 就绪(version-brom: 1.0)
  → fastboot 上传 FSBL.bin
  → 看到 SPL 横幅
  → fastboot 上传 k3-jtag-ram-opensbi-uboot.itb
  → 看到 U-Boot 横幅
  → fastboot continue(坑!U-Boot 会自己再进一次 fastboot)
  → U-Boot 提示符 => 出现
  → 敲 scsi scan,看到 KINGSTON(UFS 就绪)
  → fastboot 传内核到 0x140000000
  → fastboot 传 DTB 到 0x138000000
  → booti 启动
```

前人踩过的四个坑(脚本都处理了):① BootROM 的 fastboot 序列号是乱码 `????????????`,判据要用 `getvar version-brom` 返回 `1.0`;② U-Boot 起来后还会自己再进一次 fastboot,要再 `continue` 一次;③ U-Boot 有 5 秒 autoboot 倒计时,要发字符打断——**打断键是字母 `s`**(SpacemiT 把标准"按任意键停止"改成了密码协议,源码 `configs/k1_defconfig`:`CONFIG_AUTOBOOT_KEYED=y`、`CONFIG_AUTOBOOT_STOP_STR="s"`;回车/ESC/Ctrl-C 都不认,已实测验证);④ 每级固件接管 USB 时设备会消失重来,不能靠固定延时。

> 注意:这份真状态机在 git 历史 `638f7a9` 里,async-integration 分支的当前版本已被改写成"委托外部工作区"的空壳,我们后面要把它恢复出来。

## 3. 调试链:怎么"停住"真板上的 CPU

启动链让内核跑起来;调试链让我们能**看到并暂停**内核。链路:

```
VS Code(async-debug 扩展)
  → GDB(调试器)
    → OpenOCD(翻译层,localhost:3333)
      → J-Link(USB 调试探针)
        → K3 芯片的 Debug Module(硬件调试部件)
          → 板上运行的内核
```

### 每个概念是什么

**JTAG**:CPU 的硬件调试"后门",四根信号线(TCK/TMS/TDI/TDO)。它能无条件暂停 CPU、读寄存器、改内存、下断点——操作系统管不着它。async-debug 要调试真板,靠的就是它。

**K3 最大的坑:JTAG 和 TF 卡槽共用引脚**。芯片默认把这组引脚给 TF 卡用,JTAG 是关闭的。前人查官方手册才发现,解法是**改过的 Debug FSBL 在启动时把引脚切给 JTAG**,成功后串口会打印 `Debug JTAG enabled on MMC1 pins`。物理上,TF 槽里插一张 **Debug 扩展卡**(套件自带),把 JTAG 信号引出来接到 **J-Link** 探针上。

**OpenOCD**:电脑上的"翻译层"。GDB 不懂 JTAG 电信号,OpenOCD 把 GDB 的调试请求翻译成 JTAG 信号发给芯片。前人验证过的稳定参数:**100 kHz 速率、只开 cluster0 的 core0(单核)**。它监听三个端口:3333(GDB 连这里)、4444(telnet 管理)、6666(tcl)。K3 还有个出厂安全机制 SECJTAG,连接后要先 `irscan 0x98` 解锁,真正的 JTAG 链才放出来。

**GDB**:调试器,负责"停在哪、看什么、下断点"。`gdb-multiarch` 是支持多种 CPU 架构的版本(本机已装好)。

**ELF / 符号 / DWARF**:编译产出的 ELF 文件里除了机器码,还带"符号表"(函数名和地址的对照)和 **DWARF 调试信息**(机器指令 ↔ 源码文件行号的对照)。GDB 能报出"停在 `time.rs:119`",靠的就是 DWARF。

**Host-DWARF**:前人真板调试的核心方法。调试信息会膨胀镜像、还会改变编译优化行为,所以:**板上跑 release 版内核(不带调试信息),电脑端加载同一次构建的 ELF(带完整符号和源码信息)**。两边身份靠 ELF 的 SHA256 对齐,对不上断点就乱套。

**白名单 / Inspector / Trace**:async-debug 的核心玩法。流程:暂停目标 → **Gen Whitelist**(扫描 ELF 生成函数清单)→ 勾选要观察的 crate、选 **Async only** → **Apply**(给这些函数的 poll 装"探针")→ 选一个函数做 **Trace**(观察根)→ 下用户断点 → 继续运行 → 板上触发异步任务(比如 shell 里 `sleep 1`)→ 看 **History**(执行历史)、**Observer Tree**(Future 之间的 poll 关系树)、**Snapshot**(暂停瞬间的快照)。

## 4. 移植要改什么:平台概念

### 平台配置文件 platforms/*.toml

async-os 的每个平台是一份配置文件 + 一小撮平台代码。以 riscv64-qemu-virt.toml 为例,它写明了:

- **内存布局**:物理内存从 `0x8000_0000` 开始、128M;内核加载地址 `0x8020_0000`;虚拟地址映射偏移
- **MMIO 区域**:外设寄存器在哪些地址段(UART 在 `0x1000_0000`、PLIC 在 `0x0c00_0000`……)
- **定时器频率、用户态地址范围**

K3 需要新写一份:内存从 `0x102000000` 开始(约 8G),内核加载地址是 `0x140000000`(和 U-Boot 约定的地址一致)。

### MMIO:外设就是"魔法地址"

CPU 和外设(串口、中断控制器)通信的方式是:**外设的寄存器就是内存里的特定地址**,往某个地址写一个字节 = 让串口发出一个字符。比如 K3 的调试串口寄存器在 `0xd4017000`(从设备树里查到的)。所以"串口驱动"就是正确操作这一小段地址的代码。

### UART 驱动:16550 是"行业标准"

16550 是一个经典串口芯片的寄存器标准,后来很多串口(DesignWare DW APB UART、K3 的 PXA UART)都兼容这套寄存器。async-os 里现成有一份 `dw_apb_uart.rs`(aarch64 平台在用),K3 串口大概率改基址、改时钟就能用。

**一个更省事的发现**:async-os 的 qemu-virt 控制台目前根本没用 UART 驱动,而是走 **SBI 控制台服务**(OpenSBI 已经把串口初始化好了,内核直接调用它)。K3 上 OpenSBI 同样在,所以**第一阶段 async-os 甚至可以先白嫖 SBI 控制台**先跑起来说话,真 UART 驱动放第二步。

### 中断控制器:PLIC vs APLIC

中断控制器是外设"举手"的集合点:外设(比如定时器)有事件时向它发信号,它汇总给 CPU。qemu-virt 用 **PLIC**(老标准);K3 用 **APLIC**(RISC-V AIA 新标准,前人的 tgoskits 仓库里有现成驱动)。async-os 的异步调度器要靠定时器中断来"到点叫醒任务",所以 APLIC 最终要做;但**第一阶段可以先绕开**:串口用轮询(CPU 不停查"有字来了吗"),先让内核活着说出话,中断放第二阶段。

# 第二部分:工作全景——要做什么、为什么

按顺序做,每步都有一句"为什么"。里程碑 = 做完能验证出一个可见结果。

## 第 0 步:放开串口权限(环境打通)

**做什么**:在你自己的终端窗口执行 `sudo chmod a+rw /dev/ttyUSB0`,或 `sudo usermod -aG dialout iris`(后者要重开终端才生效)。

**为什么**:串口是我们在这次任务里唯一的"眼睛"——看启动日志、操作 U-Boot、验证内核输出,全走它。没有它,后面每一步都是盲操作。

## 第 1 步:第一次上电(里程碑:看到板子的启动日志)

**做什么**:正常上电(**不按** FORCE_RECOVERY),打开 minicom 看 `/dev/ttyUSB0`。

**为什么**:一次验证三件事——① 板子活着、接线正确(能看到日志 = 串口通路 OK);② 板上固件现状(官方链 BootROM → FSBL → OpenSBI → U-Boot 是否完整);③ 为下一步操作 U-Boot 做准备。

## 第 2 步:验证 U-Boot 通路(里程碑:进入 `=>` 命令行)

**做什么**:看到 "Autoboot in 5 seconds" 时往串口发字母 `s` 打断 → 进入 `=>` → 敲 `scsi scan` 看到 KINGSTON(证明 UFS 可用)。

> ✅ 已验证(2026-11-03):倒计时真实存在([2.219] 打印 → [7.242] 才开始启动,整 5 秒);发 `s` 在 12ms 内即打断,`=>` 提示符出现,`version` 命令执行成功。

**为什么**:U-Boot 是搬运工,async-os 要靠它加载进内存。这一步确认官方固件完好、搬运工可指挥。**到此为止不需要任何自备固件。**

## 第 3 步:async-os 的 K3 平台移植(核心工作)

参考代码:tgoskits 仓库的 K3 板级支持(串口、APLIC、设备树都在里面)。分四小步,复杂度递增:

| 小步 | 做什么 | 为什么 |
| --- | --- | --- |
| 3.1 平台配置 | 新建 `riscv64-k3.toml`:内存基址 `0x102000000`、加载地址 `0x140000000`、MMIO 区域(串口 `0xd4017000` 等),链接脚本同步 | 内核必须知道自己被加载在哪、硬件在哪,否则一启动就崩 |
| 3.2 控制台 | 先用 SBI 控制台(零成本),再移植 PXA/16550 串口驱动改基址 | 先让内核"说出话"——有了输出,后面每一步 bug 都看得见;这是最低成本的第一块里程碑 |
| 3.3 时钟 | 复用 qemu-virt 的 SBI 定时器代码 | 异步调度器靠定时器;好在 SBI 已经屏蔽了硬件差异 |
| 3.4 APLIC 中断 | 移植/实现 APLIC 驱动,接上定时器中断 | 异步任务"到点被叫醒"依赖中断;轮询串口能撑过第一阶段,调度器要真正跑起来这步逃不掉 |

**为什么这个顺序**:说话 → 计时 → 中断,每一步都能单独验证,问题好定位。

## 第 4 步:U-Boot 启动 async-os(里程碑:串口出现 async-os 的输出)

**做什么**:把 async-os 编成裸机镜像 → U-Boot 里 fastboot 传到 `0x140000000`(DTB 先传前人的现成版到 `0x138000000`)→ `booti` 启动。

**为什么**:这是"移植成功"的验收标准——内核在真板上自己跑起来。DTB 先用前人的,async-os 暂时只读它里面的时钟频率(现有代码就这用法),其余硬件信息硬编码在平台配置里。

## 第 5 步:合并 async-integration 分支

**做什么**:把前人的 14 个提交合进 `feat/k3-board-adapter`,并恢复 `638f7a9` 版本的真启动状态机脚本。

**为什么**:① remote launch 是 async-debug 连真板 OpenOCD 的能力,没有它后面调试无从谈起;② 启动状态机把"手工敲 fastboot 命令"变成一键脚本,出错率低得多;③ 你的 79 个提交(多核跟踪)必须保住,所以要小心合、测试过再算完。

## 第 6 步:打开 JTAG 链(里程碑:GDB 能停住真板 CPU)

**做什么**:解决 Debug FSBL/FIT 资产来源(见第三部分风险)→ 走 FORCE_RECOVERY 流程上传 Debug FSBL → OpenOCD 启动(`irscan 0x98` 解锁)→ `gdb target remote localhost:3333` → `info registers` 能读出寄存器。

**为什么**:调试的定义就是"能停住 CPU"。async-debug 的一切能力(断点、白名单探针、快照)都建立在 GDB 能停住目标之上。这一步是调试链的验收标准。

## 第 7 步:async-debug 接上 async-os(最终目标)

**做什么**:给 async-os 做 Host-DWARF 构建(板上 release 镜像 + 电脑端同次构建的 ELF)→ 双窗口启动扩展 → launch.json 配 `remote: localhost:3333` → Gen Whitelist → Apply → Trace → 下断点 → 板上触发异步任务 → 看 History/Observer/Snapshot。

**为什么**:这就是本项目的最终形态——用你自己的调试器,调试你自己内核的异步执行,在真板上。

## 第 8 步:收尾

- **风扇**:裸机没有系统管风扇,长时间运行要提前处理(把风扇接常电,或每次运行控制在几分钟)。⚠️ 插调试卡时板子进 USB 下载模式、风扇必停,取电点注意别用 40Pin 5V,详见《K3开发记录-04-风扇不转根因与对策》。
- **文档回写**:把验证结果更新进 `docs/`,修正本文档中标【待确认】的地方。

# 第三部分:风险与开放问题

| 风险 | 现状 | 备选方案 |
| --- | --- | --- |
| **固件资产缺失**(最大风险) | 开 JTAG 需要 `FSBL.bin`(Debug FSBL)和 `k3-jtag-ram-opensbi-uboot.itb`(OpenSBI+U-Boot 合体),本机全盘搜过没有 | ① 问团队/前人要备份;② 从官方 SDK 重新构建(工作量大,前人干过);③ 注意:第 1–5 步(串口启动 async-os)**不需要**这些固件,只有第 6 步 JTAG 才需要 |
| 板子当前固件状态未知 | 官方 UFS 固件链是否完好,第一次上电才知道 | 若 UFS 固件缺失,需要官方刷写流程恢复 |
| sudo 受限 | 本会话环境禁 sudo,串口权限要你在自己终端处理 | 你的终端里跑 chmod/usermod |
| 分支合并冲突 | 两边改动了不同区域,预计冲突不大,但要逐个检查 | 合完跑一遍现有多核跟踪测试 |

# 术语速查表

| 术语 | 一句解释 |
| --- | --- |
| BootROM | 芯片出厂固化、上电第一个跑的程序 |
| Recovery 模式 | 按住 FORCE_RECOVERY 上电,芯片变成 fastboot 设备等待下载 |
| FSBL | 第一级引导,初始化内存;Debug 版还会打开 JTAG |
| OpenSBI | RISC-V 标准底座,给内核提供定时器等服务 |
| U-Boot | 有命令行的引导器,负责加载并启动内核 |
| FIT | 多镜像打包格式,内含各部件加载地址与校验 |
| fastboot | USB 下载协议,BootROM 和 U-Boot 都会说 |
| UFS | 板载存储,官方固件分区所在地 |
| DTB | 设备树,给内核的硬件清单 |
| UART | 串口,板子的"嘴" |
| JTAG | CPU 硬件调试后门,四根信号线 |
| J-Link | SEGGER 的 USB 调试探针 |
| OpenOCD | GDB 与 JTAG 之间的翻译层 |
| Host-DWARF | 板上跑 release、电脑端留同次构建 ELF 的调试方法 |
| MMIO | 外设寄存器 = 内存特定地址 |
| PLIC / APLIC | 老/新两种 RISC-V 中断控制器标准 |
| 白名单 | async-debug 选定要装探针观察的函数清单 |
| 状态机 | 看串口真实标志决定下一步的启动脚本思想 |
