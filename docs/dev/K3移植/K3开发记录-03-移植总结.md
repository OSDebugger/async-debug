## 二、背景知识:看懂这些坑的最小工具箱

只讲后面会用到的东西。更完整的背景去看《K3 真板调试零基础入门》和《K3 工作全景讲解》。

### 2.1 内存地址与十六进制(0x)

内存可以想象成一排带编号的格子,每个格子装一个字节(8 个 bit)。**地址就是格子的编号**。

编号用二进制写会非常长(比如 5368709120 = 100000000000000000000000000000000),所以计算机世界用**十六进制**缩写它:`0x` 开头的数字就是十六进制。规律:**每 4 个二进制位 = 1 个十六进制位**,所以十六进制天生和内存对齐。

常用基准值(记这几个换算直觉,看地址一眼就知道大小):

| 十六进制 | 十进制 | 含义 |
| --- | --- | --- |
| 0x1000 | 4096 | 4KB,一页 |
| 0x100000 | 1,048,576 | 1MB |
| 0x10000000 | 268,435,456 | 256MB |
| 0x100000000 | 4,294,967,296 | 4GB(2³²) |
| 0x140000000 | 5,368,709,120 | 约 5GB,K3 上内核的加载地址 |

### 2.2 程序怎么"放"进内存:链接与 PC-relative 寻址

程序编译好之后,**每个函数、每个变量都有一个"预定地址"**,是在链接(编译的最后一步)时定死的。程序内部的跳转指令(`la`、`call`、`jal` 等)大多不是"跳到绝对地址 X",而是"**从当前位置往前/往后跳 N 字节**"(这叫 PC-relative 寻址,PC = 程序计数器 = 当前执行到哪)。

**相对跳转不怕整体平移,怕的是"写死的绝对地址"。**

跳转指令里存的不是"目标地址",而是"目标与当前指令的差值"(链接时算好、固化在指令里)。整体平移 N 字节后,当前指令和目标指令**一起**平移 N,差值不变,照样跳对(坑 1 的复盘里有具体数字例子)。真正怕平移的是:链接时把地址常数固化下来的场合——绝对寻址指令序列、GOT 表(存绝对地址的表)、数据里的函数指针表——这些常数不随平移走,平移后指向旧位置。

所以更准确的原则是:**凡是代码里写死了地址的地方,都要问一句"这个地址在运行时还成立吗"**——包括别人按约定地址找你的时候(入口地址)。

### 2.3 启动链(简版)

板子上电后是接力赛,每一级程序叫醒下一级:

```
BootROM → FSBL → OpenSBI → U-Boot → 内核(async-os)
```

- **BootROM**:芯片出厂烧死的固定程序,上电第一个跑。
- **FSBL**:第一级引导,负责把内存(DDR)初始化起来。
- **OpenSBI**:RISC-V 世界的"物业服务层",跑在最高特权级。给内核提供标准服务:定时器、核间通信、开关中断等。**注意:不同版本的服务菜单不一样**(坑 3 与此有关)。
- **U-Boot**:引导加载程序,相当于 PC 上的 GRUB。职责是"搬运工 + 检查员":把内核文件从硬盘读进内存、检查文件身份、然后交棒。**它会挑文件格式**(坑 1)。
- **内核**:主角。

### 2.4 串口与 UART:调试的眼睛

- **电脑侧**:板子通过 USB 转串口连电脑,电脑上执行 `cat /dev/ttyUSB0` 就能实时看到板子打印的日志。**这是没有 JTAG 之前唯一的视线。**
- **板子侧**:UART(通用异步收发器)是板子上的"嘴"。它暴露为一组**寄存器**——一串固定的内存地址,往某个地址写一个字节,字符就从串口发出去。K3 的 UART0 在地址 `0xd4017000`。
- **轮询发送**:写字符之前要先检查"发送缓冲区空了没",查另一个寄存器 LSR(行状态寄存器)的 THRE 位(位 5)。空了才能写,否则字符会丢。

### 2.5 MMU 与虚拟内存:两个地址世界

**物理地址**:内存芯片上格子的真实编号。
**虚拟地址**:CPU 执行程序时"以为"自己在用的地址。
**MMU(内存管理单元)**:CPU 内部的一个翻译器,把虚拟地址翻译成物理地址。

为什么内核要开 MMU?因为内核**链接时就把地址定在很高的虚拟区域**(K3 上是 `0xffffffc0_...` 开头),而物理内存实际从低处开始(0x100000000)。开 MMU 后,CPU 用虚拟地址走路,MMU 负责把每一步翻译回真实的物理格子。

翻译靠**页表**——一张"对照表",放在内存里。SV39 是 RISC-V 的一种页表格式,它的最顶层**按 1GB 的大块做对照**(1GB = 2³⁰ 字节),每块占表里的一项,表一共 512 项。

两个关键寄存器:

- **satp**:告诉 CPU"页表放在哪、要不要开启翻译"。写它 = 开 MMU。
- **stvec**:"翻车救援电话"。翻译失败(页错误)时,CPU 会跳到 stvec 指定的错误处理程序。**如果没设置它,翻车 = 直接坠毁(死机)**,没有任何输出。

坑 5 就是这两个寄存器的故事。

### 2.6 程序文件的内部结构:段

编译出来的程序按用途分成几"段":

| 段名 | 装什么 | 特点 |
| --- | --- | --- |
| .text | 代码(指令) | 有内容 |
| .rodata | 只读常量 | 有内容 |
| .data | 有初值的全局变量 | 有内容 |
| .bss | **没写初值的全局变量** | 约定为 0,但**不占文件空间** |

**关键点**:C/Rust 的约定是"全局变量默认是 0",但这个约定**不是天然的**——总得有人真的把那段内存写成 0。

另外有两个文件格式:
- **elf**:完整格式,带段表、符号、调试信息,给人/工具看。
- **bin**:纯二进制,只有字节,给"搬运工"(U-Boot)看。用 objcopy 从 elf 转出来。

**坑 7 的根源**:objcopy 转 bin 时省略了 .bss(它本来就没内容),于是 bin 里没有 .bss,加载后那段内存是 DRAM 里残留的垃圾值——但程序假设它是 0。

### 2.7 内核管理物理内存:bitmap 分配器

内核需要"记账":内存哪些页(4KB 一块)被用了、哪些空闲。**bitmap(位图)**是最朴素的记法:**用 1 个 bit 代表 1 页**,0 = 空闲,1 = 占用。

记账本有固定容量,能记录的范围叫**窗口**。async-os 用的分配器默认档位窗口是 256MB(65536 页 × 4KB)。**qemu 只配了 128MB 内存,记账本够用;K3 有 8GB,账本直接爆掉**——坑 6。

"爆掉"是怎么体现的?代码里有**断言(assert)**:一个检查点,条件不满足就 panic(内核崩溃,打印报错信息后停住)。

## 三、七个坑逐个讲

每个坑的结构:【现象】→【原因】→【解决】→【学会什么】。

### 坑 1:U-Boot 拒绝加载我们的内核 —— 镜像头

**【现象】** U-Boot 里执行 `booti` 启动内核,报错 `Bad Linux RISCV Image magic!`,拒绝启动。

**【原因】**
- U-Boot 的 `booti` 命令只认 **Linux 格式**的镜像。它检查文件开头 64 字节的"**文件头**":第 0x38 字节处必须是固定暗号 `0x05435352`,第 0x10 处必须是非零的数字(image_size)。
- **magic(魔数)** = 文件格式的暗号。很多格式都在固定位置放固定数字,读取方先对暗号再解析。我们的内核是裸 bin,没这个头,被当成"不是 Linux 镜像"拒绝。
- 头的另一个字段 **text_offset**(第 0x08 处)告诉 U-Boot"要把内核搬到哪":目标 = 内存起点 + text_offset。我们填 `0x3e000000`,算出来恰好就是内核当前的加载地址 0x140000000,意思是"**原地不动**"。

**【第一版解法(失败,当时的归因错了)】**
写了个 python 脚本,在 bin 前面**拼** 64 字节的头。上板结果:启动早期就死(探针 A 出现、B 不出现)。

当时的推断:拼接让内核整体后移 64 字节 → 相对跳转全部错位 → 第一个函数调用跳飞。**这个推断后来被推翻**(见复盘)。

**【最终解法】**
把 64 字节头**内嵌进内核入口函数 `_start` 的开头**——头参与链接,链接地址和运行时地址天然一致。内嵌是对的、也是更好的做法,但原因见复盘。

**【复盘:那次挂死的真正原因】**
改成内嵌头之后,上板还是死在**同一个 A→B 区间**——当天就意识到了,但教训却写错了。事实是:64 字节平移根本不是死因。按 2.2 节的原理,启动代码全是纯相对寻址,整体平移本该安然无恙(事后反汇编也证实:所有跳转都是 `auipc+jalr`,所有取地址都是 `auipc+addi`,连页表初始化访问全局变量都是相对算出来的)。真凶是**坑 5 的页表索引错误(0x35)**,它从第一版起就藏在代码里,两种头方案下都会死在同一个地方。

内嵌方案仍然是对的,理由是这样三条:
1. **入口约定**:U-Boot 跳到"加载地址 = 文件开头"。外置头时文件开头是头、不是代码,要靠头里那条 `jal +64` 跳到真正的入口——多一环约定就多一个出错点;内嵌后文件开头就是入口。
2. 头字段(text_offset 等)和实际布局出自同一份链接信息,不可能出现"头说 A、实际是 B"的错位。
3. 少一个构建后处理脚本。

头里的 `jal x0, +64` 本身就是"相对跳转不怕平移"的活例子:外置版本里它从文件开头跳过 64 字节落到入口,内嵌版本里它做同样的事,两种布局下都跳对。

**【学会什么】**
1. 给裸程序加"格式头",**内嵌(参与链接)仍是推荐做法**,但理由要写对(入口约定 + 头布局一致性),不是"相对跳转会错位"。
2. 整体平移真正会破坏的只有三类东西:**链接时写死的绝对地址**(GOT 表项、数据里的函数指针表、超出相对寻址范围时的绝对序列)、**入口约定**、**对齐**(平移量不是 4 的倍数时)。
3. **死因推断要经得起"换掉变量后现象是否消失"的检验**。当时"64B 错位"这个推断没通过检验(内嵌后照样死),却被写进了结论——这次就是被历史记录抓出来的。没有手段直接验证的推断,要标注"待验证",不要当结论传播。
4. 看到 `Bad ... magic!` 类报错,说明对方在检查文件身份,找到它检查的字段和偏移就行(这次是 0x38 和 0x10)。
5. 写文件头时每个字段都要明白含义——text_offset 不是装饰,它决定 U-Boot 要不要搬内核。

**符号**:`.word`/`.dword` = 汇编里"在此处放一个 4/8 字节的数"。

### 坑 2:头拼对了,magic 还是错位 —— 指令被压缩

**【现象】** 坑 1 的最终解法里,头的第一项要放一条"跳过头部 64 字节"的跳转指令。写了 `jal x0, 64` 之后,检查发现 magic 不在 0x38 而在 0x36,差了 2 字节。

**【原因】**
- RISC-V 有 **C 扩展**:一部分常用指令有"压缩版"——同样干一件事,完整版 4 字节,压缩版只要 2 字节,省空间。
- 汇编器默认开了压缩:**看到 `jal x0, 64`,它"自作主张"用了 2 字节的压缩版 `c.j`**。头里第一条指令少了 2 字节,后面所有字段整体前移 2 字节,magic 错位,U-Boot 又不认了。

**【解决】**
不写汇编指令,直接写**机器码**:`.word 0x0400006f`。

- **机器码**才是 CPU 真正读的东西(一串数字);汇编是给人看的文本,由汇编器翻译成机器码。
- `0x0400006f` 就是"无条件跳 +64"这条指令的完整 4 字节编码。直接写数字,汇编器没法压缩,字节布局钉死。

**【学会什么】**
1. 对**字节级精确**的场合(文件头、内存布局),要么直接写机器码,要么写完后**实际检查二进制**——不能只看汇编文本。
2. 排障时怀疑布局错位,直接 `xxd` 或 python 读二进制,和期望值逐字节对。
3. **`naked_asm!` 里的注释活在 Rust 字符串里**:双引号、反斜杠都会破坏字符串。2026-11-04 亲历:改注释时写了 `"第一个 call 跳飞"`,编译直接报 `prefix 跳飞 is unknown`——双引号把字符串截断,后面的中文被当成了 Rust 代码。教训:在内嵌汇编字符串里写注释,永远不用英文引号。

**符号**:**LE(小端)** = 多字节数字在内存里"低位在前"的存放方式。比如 0x0400006f 在文件里存成 `6f 00 00 04`。读二进制时别把字节序看反。

### 坑 3:启动完全静默 —— 连报错都看不见

**【现象】** 内核启动后串口一个字都没有。

**【原因】(两个原因叠加)**
1. **DTB 被搬家了**。DTB(设备树二进制文件)= 硬件说明书:时钟频率、外设地址全记在里面。U-Boot 把 DTB 从我们约定好的地址(0x138000000)搬到了它自己附近(约 0x2fbd5a000),然后才把新地址传给内核——但我们代码里读的是旧指针,而且旧地址此时还没做内存映射,一读就死。
2. **输出通路本来就断了**。我们原来的打印走 OpenSBI 的"帮我打印"服务(legacy console)。但板载的 OpenSBI 是新版(2026),**把这个老服务删了**,调用静默无效。

两条路都断,所以一个字都看不到。

**【解决】**
1. 时钟频率不从 DTB 读了,直接写死 24MHz(这个值本来就来自 DTB,写代码时查文档确认的)。
2. 打印改走 **UART 寄存器轮询**(2.4 节):直接读写 0xd4017000 的寄存器,不经过任何中间服务。

**【学会什么】**
1. **没有输出时,先怀疑输出通路本身**,别只怀疑业务逻辑。打印通道 = 软件 + 硬件 + 中间服务,每一环都可能断。
2. "拿到的指针"可能是**过期的**——中间人(U-Boot)可能已经把数据搬走了。凡是跨程序传递的地址都要警惕。
3. 依赖外部服务(如 SBI)前,先确认**这个服务的版本菜单里还有没有这道菜**。

### 坑 4:在 U-Boot 里直接验证 UART 硬件 —— 二分排除法

**【现象】** 怀疑 UART 驱动写得不对,但没法区分"驱动错"还是"硬件/地址错"。

**【方法】**
U-Boot 命令行本身就有读写内存的命令:
- `md.b 0xd4017014 1` —— 读 UART 的 LSR 寄存器,得到 0x20(THRE 位=1,缓冲区空)
- `mw.b 0xd4017000 0x4b` —— 往发送寄存器写一个字节('K' = 0x4b)

**串口立刻出现字符 'K'** → 硬件没问题、寄存器布局没错、地址没错 → 问题一定在内核代码的执行本身。

**【学会什么】**
1. **把"硬件问题"和"软件问题"切开**,是最有效的第一步。U-Boot 是现成的硬件调试器,读内存、写内存就是它的强项。
2. 以后遇到"XX 外设不工作",第一反应应该是:去 U-Boot 里直接读写它的寄存器,先证明硬件通路是通的。

### 坑 5:MMU 开启后挂死 —— 本次最难的一个坑

**【现象】** 在入口代码里埋了两个**探针**(在关键位置直接往 UART 寄存器写一个字符):探针 A 在开 MMU 之前,探针 B 在开 MMU 之后。结果:串口只出现 A,没有 B。

结论:程序死在"开 MMU 之后、第一次用虚拟地址访问外设"的路上。

**【排查方法:探针二分法】**
没有 JTAG(硬件调试器)时,唯一的视线就是串口。**在程序的关键节点写一个字符到 UART,看输出停在哪**,然后缩小范围再插探针。这是裸机调试的基本功。

**【原因】**
开 MMU 之后,访问 UART 要走"虚拟地址 → 页表 → 物理地址"。结果**页表里没有 UART 的对照项**——翻译失败(页错误),CPU 去找救援电话 stvec,发现没设置,直接坠毁(2.5 节)。

页表项为什么没写对?**索引算错了**:
- SV39 顶层页表是 **1GB 一块**(下标 = 地址 ÷ 2³⁰)
- UART 在 0xd4017000,正确下标 = `0xd4017000 >> 30` = **3**(块 0xc0000000)
- 当初却按 **64MB 一块** 算:0xd4000000 ÷ 0x4000000 = 0x35,写进了第 0x35 项——错项
- 结果虚拟地址 0xffffffc0_d4017000 查表落空 → 死

**【解决】**
索引改成 `(0xd401_7000 >> 30) & 0x1ff`(`& 0x1ff` = 取低 9 位,因为表只有 512 项,防止越界)。另外在排查过程中还领悟了一个设计要点:**MMU 刚打开的那一刻,CPU 手里还是物理地址**,所以页表里要同时有"物理地址直通"的恒等映射,让切换瞬间能续命——这也是当时埋的另一个隐患。

**【学会什么】**
1. **页表 = 对照表,表错一项 = 那一块区域全部无法访问 = 死**,而且死得毫无痕迹(输出停在探针之间)。
2. **大单位换算永远用位移算**(`>> 30` = ÷1GB),不要用除法心算——0x35 就是按 ÷64MB 算出来的错。这个 bug 同时是坑 1 里"外置头挂死"的真凶:两种头方案死在同一个区间,当时却把锅甩给了 64B 偏移。
3. 开 MMU 是调试的分水岭:**探针插在"开 MMU 前/后"**,能立刻把死点二分成两个世界的问题。
4. stvec 是坠毁前的安全气囊,正式内核要尽早设置,至少死也要死得"有话说"。

**符号**:`>>` = 右移(除以 2 的幂)、`&` = 按位与(取低位)、**VPN** = 虚拟页号(地址的高位部分,查表用)、**PPN** = 物理页号(表里填的内容)、0xef = 页表项末尾的权限位组合(有效 + 可读可写可执行 + 已访问已修改 + 全局)。

### 坑 6:内存分配器 panic —— bitmap 窗口溢出

**【现象】** 启动日志跑到 "Initialize global memory allocator" 时 panic:
```
assertion failed: end <= Self::CAP
```
(panic = 内核崩溃。它会打印一条信息后停住,比无声挂死友好得多。)

**【原因】**
- 2.7 节讲过:bitmap 记账本有窗口上限。默认档位 256MB,账本容量 = 65536 个 bit = 65536 页。
- K3 有 8GB 内存,内核自己占在 0x140000000 附近,往后要记的页数约 183 万页,远超 65536。断言 `end <= Self::CAP`(结束位置 ≤ 账本容量)不成立 → panic。
- **qemu 为什么没事**:qemu 那台"假电脑"只配了 128MB 内存,账本绰绰有余。

**【解决】**
把分配器库改成本地 patch(在 Cargo.toml 里把依赖指向本地目录 `modules/allocator`),把默认档位改成 **64GB 窗口**。代价:记账本本身占内存约 2.4MB(体现在 .bss 变大——呼应坑 7)。

**【学会什么】**
1. **看到 panic,先读断言里的条件和数字,再动手算**——这个 panic 自己把原因写在脸上了。
2. **"qemu 能跑" ≠ "真板能跑"**:虚拟机的内存大小、设备配置经常比真板小/简单。凡是和"容量、大小、范围"有关的代码,上板前想想真板的数量级。
3. **依赖库的默认配置(feature)也可以改**,patch 到本地是常用手段;改完记得把原因写进注释(否则后人不知道为什么改了默认值)。

### 坑 7:全局变量是垃圾值 —— .bss 没清零

**【现象】** 修完坑 6 后,程序行为异常——依赖"全局变量初始为 0"的逻辑全乱。

**【原因】**
- 2.6 节讲过:bin 文件里没有 .bss 段(objcopy 转换时省略了 NOBITS 段——"没内容"的段)。
- U-Boot 把 bin 加载进内存时,那段内存里是 **DRAM 上电后的残留旧数据**,不保证是 0。
- 但所有代码都默认"全局变量初始是 0"(C/Rust 的语言约定)。
- qemu 里为什么没事:qemu 的"内存"从零开始模拟,天然是 0;真板的 DRAM 有历史残留。

**【解决】**
在 `_start` 入口最前面(开 MMU 之前)加一段循环:从 `_sbss` 到 `_ebss`,每 8 字节写一个 0。`_sbss`/`_ebss` 是链接脚本定义的"界碑"符号,标出 .bss 段的起止地址。

**【学会什么】**
1. **约定不是天然的**:"变量初始是 0"这个约定背后得有人干活。裸机启动代码的固定三件事:设栈、清 bss、初始化设备。
2. **凡是"默认值"都要问一句:谁负责把它设置成默认值?**加载器?固件?还是程序自己?
3. 调试"变量值莫名其妙不对"时,优先怀疑初始化环节,而不是变量被谁改了。

## 四、上板操作手册(流程速查)

### 4.1 标准流程

```bash
# 1. 构建(代理必须带,否则 cargo 直连外网很慢)
cd ~/data/async-os-original
CARGO_HTTP_PROXY=http://127.0.0.1:12450 make build \
  A=apps/coroutine_test PLATFORM=riscv64-k3 ARCH=riscv64 \
  MODE=release SMP=1 LOG=info

# 2. 推送内核到板端(Bianbu 系统还活着时)
adb push apps/coroutine_test/coroutine_test_riscv64-k3.bin /boot/asyncos.bin

# 3. 先挂 s 键风暴,再重启(否则错过 U-Boot 的 5 秒等待窗口)
#    后台循环:每 200ms 往串口发一个 's',持续 90 秒
#    然后 adb reboot

# 4. 进入 U-Boot 后,三条命令:
#    load scsi 0:2 0x140000000 asyncos.bin   ← 把内核从硬盘读进内存
#    load scsi 0:2 0x138000000 k3.dtb        ← 把设备树读进内存
#    booti 0x140000000 - 0x138000000         ← 检查身份、交棒启动

# 5. 电脑侧挂串口捕获看日志
cat /dev/ttyUSB0 > ~/data/k3-serial.log
```

### 4.1b 一键脚本(2026-11-04 新增)

async-os-original 仓库 `scripts/k3flash.sh`,自动完成上面 2~5 步:push → s 键风暴 → reboot → 等 U-Boot `=>` → 发三条命令 → 前台跟日志。错过 U-Boot 窗口会自动等板子回 Bianbu 后重试(默认 2 轮)。

```bash
cd ~/data/async-os-original
scripts/k3flash.sh                  # 默认推 apps/coroutine_test/coroutine_test_riscv64-k3.bin
scripts/k3flash.sh 路径/xxx.bin      # 或指定 bin
# 选项:-s 串口设备(默认 /dev/ttyUSB0)-l 日志(默认 ~/data/k3-serial.log)-r 重试次数
# 直接模式:板子已在 U-Boot => 提示符(不用再 push/重启),scripts/k3flash.sh -u
```

前提:板子在 Bianbu 状态(adb 在线)、板端已有 /boot/k3.dtb;**跑脚本时不要同时开 minicom/picocom**(两个读端会抢串口输出,导致脚本等不到提示符)。

**常见坑:串口写权限(2026-11-04 实测踩到)**。`/dev/ttyUSB0` 默认属主 `root:dialout`,当前用户不在 dialout 组时,读日志没问题、**写 's' 会被拒**(表现为脚本永远等不到 `=>`)。一次性修复:

```bash
sudo usermod -aG dialout $USER     # 加入 dialout 组(需要重新登录生效)
# 或当前终端立即生效:newgrp dialout
```

脚本现在会在启动时预检写权限,没权限会直接给出这条提示,而不是转两轮超时才失败。

**常见坑:串口日志是"二进制流",grep 匹配到却"没输出"(2026-11-04 实测踩到)**。串口裸数据里混着非文本字节(比如风暴打断时 U-Boot 响铃的 `^G` 等控制字节)。grep 检测到这种内容后会把整个流当二进制处理:**明明匹配到了 `=>`,却只在 stderr 打一行 `binary file matches`,stdout 是空的**。脚本拿 stdout 判"等到提示符没有",结果误判"错过窗口",转去重试——而板子其实已经停在 U-Boot 了。

修复:grep 加 `-a`(--text)标志强制按文本处理。**凡是对串口日志做 grep,一律带 `-a`**。这个坑很阴:报错看起来是 grep 自己打的("binary file matches"),但真正的症状在别处(脚本误判超时、无限重试)。

### 4.2 实战经验

- **串口传输(xmodem)和日志捕获不能同时进行**:后台 `cat` 会抢读串口字节,破坏传输协议。传输前先停掉捕获。
- **挂死的板子不会自己复位**:U-Boot 交棒给内核后就不喂看门狗了(喂狗是它的活),内核挂死 = 永久挂死。**唯一解法:物理断电再上电**。
- **错过 U-Boot 窗口的补救**:如果板子直接进了 Bianbu(串口看到 login),用 adb 通道(`adb shell` 是 root 权限),先挂风暴再 `adb reboot`,让重启恰好撞进 5 秒窗口。
- **adb 设备号**:COM3K3081280112(团队这块板)。

### 4.3 出问题的标准排查顺序

```
挂死(无声)          → 探针二分法(坑 5):在关键节点写字符到 UART,确定死点
                    → 死点附近查:地址映射?页表项?stvec 有没有设?
panic(有报错)       → 先读断言条件和数字,算一遍(坑 6 就是这么破的)
                    → 追调用链:谁触发的、参数是什么数量级
变量值不对          → 先查初始化:清零做了吗?谁负责的?(坑 7)
外设不工作          → 先去 U-Boot 直接读写寄存器,切开硬件/软件问题(坑 4)
文件被拒绝加载      → 查格式头:magic 在哪、偏移对不对、有没有被压缩(坑 1/2)
完全没有输出        → 先查输出通路本身:打印走的是什么服务?地址映射了吗?(坑 3)
```

## 五、符号速查表

| 符号/词 | 含义 |
| --- | --- |
| `0x...` | 十六进制数。0x1000 = 4KB,0x10000000 = 256MB,0x100000000 = 4GB |
| `>>` / `&` | 右移(÷2ⁿ)/ 按位与(取低位)。`x >> 30` = x ÷ 1GB |
| `la` / `call` / `jal` | 汇编里的跳转/调用指令,多为"相对当前位置跳" |
| PC-relative | 相对寻址:目标 = 当前位置 + 偏移,前提是程序位置和链接时一致 |
| `.word` / `.dword` | 汇编指令:在此处直接放一个 4 字节 / 8 字节的数字 |
| 机器码 | CPU 真正执行的数字;汇编文本是给人看的,由汇编器翻译 |
| LE 小端 | 多字节数"低位在前"的存放方式,读二进制时注意字节序 |
| magic 魔数 | 文件格式在固定位置的固定暗号,读取方先对暗号 |
| text_offset | Linux 镜像头字段:U-Boot 把内核搬到"内存起点 + 它",填对 = 不搬 |
| DRAM | 内存芯片(易失的,断电即失) |
| UART | 串口控制器,一组寄存器;写一个寄存器 = 发一个字符 |
| LSR / THRE | 行状态寄存器 / "发送缓冲空"位:写字符前先查它 |
| DTB | 设备树二进制文件:硬件的说明书(时钟、外设地址) |
| OpenSBI / SBI | RISC-V 的"物业服务层":定时器、核间通信等服务;新版删了老控制台服务 |
| U-Boot / booti | 引导加载程序 / 它加载 Linux 格式镜像的命令(检查 magic) |
| MMU / 页表 | 虚拟→物理地址翻译器 / 翻译用的对照表 |
| satp | 寄存器:页表位置 + 是否开 MMU |
| stvec | 寄存器:页错误时 CPU 跳去哪(救援电话,不设 = 直接死) |
| VPN / PPN | 虚拟页号(查表用)/ 物理页号(表内容) |
| SV39 | RISC-V 页表格式,顶层按 1GB 块对照 |
| 1GB 块 | 2³⁰ 字节,`>> 30` 即按此分块 |
| .text / .data / .bss | 代码段 / 有初值数据段 / 未初始化数据段(约定 0,不占文件空间) |
| NOBITS / PROGBITS | "无内容"段(.bss)/"有内容"段;objcopy 转 bin 时省略 NOBITS |
| _sbss / _ebss | 链接脚本定义的界碑符号:.bss 段的起止地址 |
| bitmap | 位图记账:1 bit 管 1 页内存是否空闲 |
| 断言 / panic | 代码里的检查点 / 内核崩溃(会打印原因后停住) |
| feature / patch | 依赖库的可选配置 / 把依赖指向本地目录以修改它 |
| adb | Android 调试桥:板子跑 Bianbu(Linux)时的管理通道,`adb shell` 是 root |
| qemu | 虚拟机/模拟器:一台"假电脑",配置常比真板小,跑通 ≠ 上板跑通 |
| 探针 | 在关键位置写一个字符到 UART,用来定位死点;二分插探针 = 裸机基本排障法 |
