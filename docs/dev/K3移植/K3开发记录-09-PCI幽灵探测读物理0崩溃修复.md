# K3 开发记录 09:PCI"幽灵探测"读物理 0 崩溃的根因与修复

- **日期**:2026-11-10
- **面向读者**:完全没学过硬件也能看懂(概念先行,步骤在后,术语表在最后)

## 这篇记录解决什么问题

修好前两个坑之后(记录 07 幽灵内存区、记录 08 撞大页),内核一路走到了**设备初始化**,都成功注册了 ramdisk(测例硬盘),却在下一步崩溃:从"物理地址 0"读数据时踩空。这篇记录讲清:谁在没事找事地读物理 0、为什么 qemu 上没事、怎么修的。

## 先讲三个概念(每个都用大白话)

### 1. PCI = 电脑的"扩展卡插槽"系统

台式机主板上有一排插槽,插显卡、网卡。这套插槽系统的技术标准叫 **PCI**。开机时,内核会**挨个插槽敲门**:插槽里有没有卡?卡是什么型号?这套"敲门流程"叫 **PCI 总线探测**。

### 2. ECAM = 敲门用的"传呼地址"

PCI 的敲门方式很特殊:不是走到插槽前,而是**读写一段专门的内存地址**。这段地址的起点叫 **ECAM 基址**——把基址加上偏移,就能"隔空"访问某个插槽上卡的配置信息。

关键点:这台机器**有 PCI 插槽系统,ECAM 基址才指向真实硬件**;没有的话,这个基址就是摆设,读它等于读空气。

### 3. 页错误 = 走到不存在的地址(和记录 07 同一个概念)

CPU 访问"没有真内存/真硬件"的地址时,硬件立刻报警。K3 板子的**物理地址 0 附近什么都没有**(它的内存从 0x100000000 才开始),读物理 0 必踩空。

## 现象(崩溃时发生了什么)

内核顺利走到设备初始化,注册了测例硬盘 ramdisk,然后:

```
Unsupported kernel trap LoadPageFault @ 0xffffffc1400ebb4a:
    sepc: 0xffffffc1400ebb4a
    scause: 0xd
    stval: 0xffffffc000000000   ← 踩空的地址 = 物理 0
```

- `LoadPageFault` = 想读数据时踩空
- `stval: 0xffffffc000000000` = 踩空的正是**物理地址 0**(0xffffffc0 开头是虚拟地址写法,指物理 0)

## 排查过程(怎么证明是这个原因)

1. **查"是哪条指令踩空的"**:把报警里的指令位置翻译回代码(工具 addr2line),结果是 `read_volatile`(读内存的底层函数),调用者是 `probe_bus_devices` —— **"探测 PCI 总线"的函数**。实锤:是 PCI 敲门流程在作怪。
2. **查它敲的是哪扇门**:代码里 ECAM 基址来自平台配置 `pci-ecam-base`。K3 的配置是 `"0"` —— **ECAM 基址 = 0**。PCI 探测从基址 0 开始读 → 读物理 0 → 踩空。
3. **为什么 K3 配置里写 0?**:0 是"没配 PCI"的默认占位值(这套配置系统的出厂默认就是 0;两块同样没有 PCI 的板子 bsta1000b、rk3588j 干脆把这行注释掉,注释掉也是 0)。
4. **为什么那两块板子没炸?**:它们的**内存恰好从物理 0 开始**,读物理 0 读到的是内存里的垃圾数据,敲门没人应,探测结束,一切正常。K3 的内存从 0x100000000 才开始,物理 0 是**真空**,一敲就踩空。
5. **为什么 qemu 上没事?**:qemu 的配置把 ECAM 基址指向 0x30000000,那是 qemu 里真实存在的"插槽传呼区"(模拟的 PCI 硬件),敲门有真实应答。
6. **为什么之前的 coroutine_test 没炸?**:那个测例不需要测例硬盘,**设备初始化这一步根本没执行**,PCI 探测代码从来没跑到。

一句话根因:**K3 没有 PCI,配置里 ECAM 基址是默认占位值 0;但设备初始化流程不检查"有没有 PCI",照常从基址 0 开始敲门,而 K3 的物理 0 是真空,一敲就踩空崩溃。**(这个坑在上游 axdriver 项目里同样存在,只是上游从没在"内存不从 0 开始"的板子上跑到过设备初始化。)

## 修复(两小步)

### 第一步:把 axdriver 收编进仓库(和 kernel_guard、allocator、axhal 一样的做法)

axdriver 原来是**外部依赖**(github 上的第三方包),仓库里改不了它。仓库早有先例:kernel_guard、allocator、axhal 三个外部包都被"收编"进了 `modules/` 目录,通过根 `Cargo.toml` 的 `[patch]` 规则替换。这次照抄同一套做法:

- 把 axdriver 源码复制到 `modules/axdriver/`
- 根 `Cargo.toml` 加一行:

```toml
[patch."https://github.com/Starry-OS/axdriver.git".axdriver]
path = "modules/axdriver"
```

### 第二步:给 PCI 探测加一个"没有 PCI 就别敲"的守卫

文件:`modules/axdriver/src/bus/pci.rs`,函数开头加:

```rust
// PCI_ECAM_BASE == 0 是"没配 PCI"的哨兵值(K3 就是这种)
if axconfig::PCI_ECAM_BASE == 0 {
    return;
}
```

意思:**ECAM 基址是 0(没配 PCI),探测直接跳过**。对 qemu、x86 这类有真实 ECAM 基址的平台,这个判断恒为假,行为完全不变;对 K3,整段探测代码在编译期就被优化掉(基址是常量 0,编译器直接算出"必跳过")。

## 验证方式

静态检查:新内核里 `probe_bus_devices` 这个符号**彻底消失**(守卫生效,整段代码被编译器折叠掉了),img 镜像符号完好。

上板验证:重新构建 → 上板启动。预期:设备初始化不再崩溃,继续挂载测例文件系统,跑起 pipetest。

## 术语速查表

| 词 | 一句话解释 |
| --- | --- |
| PCI | 扩展卡插槽系统的技术标准(显卡、网卡那套) |
| PCI 总线探测 | 开机时挨个插槽敲门,看有没有卡、什么型号 |
| ECAM 基址 | 敲门的"传呼地址"起点;没有 PCI 时它是占位值 0 |
| 物理地址(PA) | 内存芯片上真实的位置编号;K3 的物理 0 是真空 |
| 虚拟地址(VA) | 程序看到的地址;0xffffffc0 开头对应物理地址 |
| LoadPageFault | 读数据时踩空的硬件报警 |
| stval / sepc | 崩溃现场记录:踩空的地址 / 出错指令的位置 |
| addr2line | 把"指令位置编号"翻译回"代码哪一行哪个函数"的工具 |
| [patch] | 仓库根 Cargo.toml 里"用本地目录替换外部包"的规则 |
| 哨兵值 | 一个特殊取值,含义是"没有/无效"(这里 0 = 没配 PCI) |
