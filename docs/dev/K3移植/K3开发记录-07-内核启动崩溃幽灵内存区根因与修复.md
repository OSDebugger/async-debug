# K3 开发记录 07:内核启动崩溃("幽灵内存区")的根因与修复

- **日期**:2026-11-10
- **面向读者**:完全没学过硬件也能看懂(概念先行,步骤在后,术语表在最后)

## 这篇记录解决什么问题

我们把用户态测例打包进内核(记录 05 的做法)后第一次上板,内核启动到一半**崩溃**(术语叫 panic,类似程序遇到无法处理的错误直接报错退出)。这篇记录讲清楚:崩溃时发生了什么、为什么、怎么查出来的、怎么修的。

## 先把三个概念讲清楚(每个都用大白话)

### 1. 内存区域清单 = 内核的"地契"

内核启动后第一件事,是弄清楚"这台电脑哪些内存是真的、可以随便用"。它会打出一张**内存区域清单**,每一行写着:从哪个地址到哪个地址、这段内存是干什么的、能不能用来存数据。

类比:就像拿到一栋楼的地契,知道哪几层是自己的、哪几层是别人的、哪几层其实是"纸上写的但实际不存在"。

崩溃前的清单里就有这么一行(问题就出在这行):

```
[PA:0xa0000000, PA:0x1a0000000) extend free memory (READ | WRITE | FREE)
```

翻译:内核相信"从地址 0xa0000000 到 0x1a0000000 有 4GB 内存,可以随便用"。**但 K3 板子上这个地址范围根本没有内存芯片**,这是一条假地契。

### 2. 内存分配器 TLSF = 仓库管理员

内核里有一个"仓库管理员"(叫 TLSF 分配器),它拿着地契清单,给各个程序分配内存。

管理员有一个工作习惯:分出去一块内存之前,要**亲自走到那块内存的位置,在开头写下几行账目**(这块多大、上一块在哪、下一块在哪)。这些账目就写在内存自己身上。

### 3. 页错误(page fault)= 走到不存在的地址

CPU 访问一个"没有真内存"的地址时,硬件会立刻报警,把现场信息(哪个地址、哪条指令干的)交给内核。内核一看自己处理不了,就 panic。

类比:管理员照着假地契走到"第 10 层",想进门记账——但那层楼根本不存在,一脚踩空。

## 现象(崩溃时发生了什么)

内核打印内存清单后,立刻崩溃,报警信息的关键内容:

```
panicked at modules/trampoline/src/lib.rs:48:21:
Unsupported kernel trap StorePageFault @ 0xffffffc1400fc5d6:
    stval: 0xffffffc0a0000000   ← 踩空的地址
```

- `StorePageFault` = 想往里写东西时踩空
- `stval: 0xffffffc0a0000000` = 踩空的正是那条假地契的**第一个字节**(0xa0000000,前面一串 f 是地址的"楼层编号"写法,指的就是物理地址 0xa0000000)

时间顺序完全对得上:内核刚打完内存清单 → 管理员(TLSF)开始清点 → 按清单走到 0xa0000000 记账 → 踩空 → panic。

## 排查过程(怎么证明是这个原因)

1. **看崩溃时的"值班记录"**:崩溃信息里有 32 个寄存器的值(CPU 干活时用的小本子)。其中三个都指着 0xa0000000,一个写着 4GB——正好是假地契的范围。
2. **查"是哪条指令踩空的"**:把报警里的地址翻译回代码(工具 addr2line),结果是 `Tlsf::insert_free_block` ——**正是管理员记账的动作**。实锤:不是别的代码,就是分配器在给假地契记账。
3. **查假地契从哪来**:代码里有一条硬编码(写死的)规则,叫 `extend_free_regions`(翻译:追加一块空闲内存),它不问硬件、直接宣称 [0xa0000000, 0x1a0000000) 是可用的。
4. **为什么早上跑的 coroutine_test 没事?**:这条硬编码规则只在 `monolithic` 这个开关打开时才生效。coroutine_test 不用这个开关;而我们这次给内核塞了测例镜像(img 特性),它必须打开这个开关 → 假地契第一次生效 → 崩溃。
5. **假地契是谁的?**:git 历史显示,K3 的内存清单代码是前人从 **qemu 模拟器**版本**原样抄过来**的。在 qemu 上,0xa0000000 附近确实有内存(qemu 的测例区就在 0x90000000),所以那条规则在 qemu 上没错。但 **K3 板子的真内存从 0x100000000 才开始**(8GB,到 0x300000000),0xa0000000 在真内存**下面**,是空的。

一句话根因:**K3 的内存清单照抄了 qemu 的写法,把 qemu 上有效、K3 上不存在的一段地址当成了可用内存;一旦打开 img 所需的开关,管理员就照着假地契踩空了。**

## 修复(只改一个文件,删掉抄来的那行)

文件:`modules/axhal/src/platform/riscv64_k3/mem.rs`

修法:内存清单只列真实内存,不再追加那段 qemu 专用的假地契。改完后的逻辑一句话:**K3 只有真内存 0x100000000 起步那一块**,其余一律不信。

为什么删掉是安全的:K3 的测例区(0x180000000)本来就在真内存范围内,img 需要的 64MB 内存照常能从真内存里拿到,**不需要**任何追加。

## 验证方式

重新构建内核 → 重新传上板 → 启动。预期:内存清单里不再出现 `extend free memory` 那行,内核继续往下走,挂载测例文件系统,跑起 pipetest。

构建产物里也做了静态检查:新内核里已经搜不到 "extend free memory" 这行字的痕迹,说明假地契代码确实被删干净了。

## 传输提速实验的最终结论(2026-11-10 三次上板实测)

想给 22MB 传输提速,试了两条路,结论如下:

| 方案 | 结果 | 结论 |
| --- | --- | --- |
| `setenv baudrate 921600` 改环境变量提速 | 被 U-Boot 拒绝:"Baudrate 921600 bps not supported"(460800/230400/576000 等也全部拒绝) | 这条路走不通,U-Boot 只认标准速率表,最高就是 115200 |
| `loady 0x140000000 921600`(loady 命令自带波特率参数,绕过了上面的校验) | **传输本身成功且飞快**(22MB 约 4~5 分钟,校验通过),但**传输一结束 U-Boot 就永久卡死**,控制台在任何波特率下都不回应。两次上板 100% 复现;拔插 USB 串口线、盲发命令均无法救回,只能断电重启,内存里的镜像也丢了 | 这条路也不能用:高速接收完成后 U-Boot 恢复控制台的环节有缺陷(BSP bug) |

**最终结论:22MB 内核的传输只能用 115200 的老路(xmodem 约 31 分钟)。** 提速只能靠以后修好 adb(推送到 UFS 后 `load scsi` 只要几秒)。

排查小记:第一次高速传输后控制台失联,先怀疑是主机侧 USB 串口芯片(CH340)卡死——做了"拔插 USB 串口线"的对照实验,失联依旧,才确认是板子侧 U-Boot 的问题。这种"先排除主机侧、再怪板子"的顺序值得保留。

## 术语速查表

| 词 | 一句话解释 |
| --- | --- |
| panic | 内核遇到无法处理的错误,打印现场信息后停住(类似程序崩溃) |
| 内存区域(region) | 内核的"地契清单"条目:一段地址范围 + 用途 |
| 物理地址(PA) | 内存芯片上真实的位置编号;0xa0000000 这种数字 |
| 虚拟地址(VA) | 程序看到的地址;内核用"0xffffffc0 开头"的写法对应物理地址 |
| TLSF | 内核的内存分配器,"仓库管理员",把内存按需分块借出 |
| 页错误(page fault) | CPU 访问不存在的地址时触发的硬件报警 |
| 寄存器 | CPU 干活时记中间值的小本子,崩溃时会被打印出来 |
| stval / scause / sepc | 崩溃现场的三个关键记录:踩空的地址 / 错误类型 / 出错指令的位置 |
| addr2line | 把"指令位置编号"翻译回"代码第几行哪个函数"的工具 |
| monolithic | 内核的一个构建开关;img 特性必须打开它 |
| 波特率(baud) | 串口每秒传多少位,决定传输快慢;921600 比 115200 快 8 倍 |
