#### 关键问题

##### 1. 问题现象

内核能正常启动，日志输出到：

```
arch = riscv64
platform = riscv64-qemu-virt
user_boot
load app args: ["hello_world"]
Page fault address VA:0x7f not found in memory set
handler signal: 11 → Terminate process: 2
Shutting down...
```

**所有用户程序（含零依赖的 `hello_world`）一进入用户态就崩溃**，因此调试器里的断点从未命中、调用树始终为空。

确认与调试器无关：纯 QEMU 启动（无 `-s -S`、无 gdb 附加）现象完全相同。

##### 2. 排查过程

- **假设 A**：`Gen Whitelist` 只扫内核 ELF，用户 crate 进不了白名单
  - 实验：patch `gen_whitelist.py` 增加磁盘 ELF 扫描
  - 观察：204 crates 出现了 `pipetest`，但断点仍不命中 → 不是唯一原因
- **假设 B**：用户程序缺调试信息，断点无法绑定
  - 实验：`-O0` + `debuginfo` 重编用户程序
  - 观察：断点变红，但仍不命中 → 有进步，不是根因
- **假设 C**：`tp`（TLS 指针）未初始化
  - 实验：GDB 在 trap 入口读寄存器
  - 观察：首次用户态 trap 时 `tp = 0`，`sp`、`gp` 正常
  - 补充实验：反汇编 musl 的 `__init_tls` / `__copy_tls` / `__init_tp`，确认 musl 会自己设置 `tp`
- **假设 D**：内核 trap 返回时破坏寄存器
  - 实验：对比连续两次用户态 trap 的 trapframe 内容

  - 观察：

    ```
    TRAP #1: s0 = 0x687f8
    TRAP #2: s0 = 0x0000000000000007     ← 等于 TRAP#1 的 t0
    ```

  - 结论：寄存器发生了整体错位

##### 3. 根因

**两个独立的缺陷叠加：**

**缺陷一：`TrapFrame::user_return()` 的寄存器恢复槽位与结构体布局不一致**

`GeneralRegisters` 的真实布局是（`gp`/`tp` 在 2/3 位）：

```
0 ra | 1 sp | 2 gp | 3 tp | 4 t0 | 5 t1 | 6 t2 | 7 s0 | 8 s1 | 9 a0 | ...
```

但 `user_return()` 的恢复序列沿用了一套**不含 `gp`/`tp`** 的旧布局：

```asm
ld  t0, 1*8(sp)      // 槽位 1 实际是 sp
ld  s0, 4*8(sp)      // 槽位 4 实际是 t0   ← 错位来源
ld  a0, 6*8(sp)      // 槽位 6 实际是 t2
```

后果：每次内核→用户返回，每个寄存器都拿到另一个寄存器的值。实测 `t0` 的值（`0x7`）被写进 `s0`，随后 `__init_tp` 执行 `sd a5, 120(s0)`，即写 `0x7 + 120 = 0x7f`，与 `stval=0x7f` 完全吻合。

**缺陷二：首次 exec 用户程序时 `regs.tp` 从未初始化**

`executor::init_user` 调用 `TrapFrame::init_user_context(entry, user_sp)`，该函数只设置 `sp`/`sepc`/`sstatus`/`a0`/`a1`，**不设置 `tp`**。`set_tls()` 只在 `clone(CLONE_SETTLS)` 路径被调用。

RISC-V musl 的 `__copy_tls` 通过 `tp + 偏移` 访问 `__libc` 等 TLS 变量，`tp = 0` 时读到地址 0 附近的垃圾，`__copy_tls` 返回错误指针 `0x7`，直接导致上述崩溃。

##### 4. 解决方式

**修复一**：`modules/taskctx/src/arch/riscv/mod.rs` 的 `user_return()`，按 `GeneralRegisters` 真实布局重排恢复序列：

```asm
ld  ra,  0*8(sp)
ld  s0,  7*8(sp)
ld  s1,  8*8(sp)
ld  a0,  9*8(sp)
...
ld  t6, 30*8(sp)
ld  t0,  4*8(sp)
ld  t1,  5*8(sp)
ld  t2,  6*8(sp)
ld  sp,  1*8(sp)
```

**修复二**：`modules/executor/src/executor.rs` 的 `init_user`，在创建首个 trapframe 后分配 TLS 区并设置 `tp`：

```rust
let mut tf = TrapFrame::init_user_context(entry.into(), user_stack_bottom.into());
const TLS_AREA_SIZE: usize = 4096;
tf.set_tls(heap_bottom.as_usize() + TLS_AREA_SIZE);
```

**修复三（调试器侧）**：`async_rust_debugger/static_analysis/gen_whitelist.py` 增加 `_scan_user_program_elfs()`，用 `gdb -batch` 直接解析 `user_apps/target/*/release/` 下的 ELF 并合并进白名单。

> 踩坑：`glob` 在 GDB 内嵌 Python 里匹配为空，改用 `os.listdir` 手工遍历；`gdb -batch` 传文件路径不会解析调试符号，必须用 `-ex "file <path>"` 显式加载。

#### 知识沉淀

- **寄存器保存/恢复必须和结构体布局严格对齐**。这类错误不会在编译期暴露，表现为"某个寄存器莫名变成另一个寄存器的值"。用"连续两次 trap 对比"可以快速定位错位。
- **RISC-V musl 静态程序会自己建立 TLS**（`__init_tls` → `__copy_tls` → `__init_tp`），但**前提是 `tp` 已经指向一块可写内存**。内核不需要填 TLS 内容，但必须给一个有效地址。
- **`stval` 是排查缺页的金标准**。把 `stval` 减去故障指令里的立即数偏移，就能反推出是哪个寄存器坏了（本例 `0x7f - 120 = 0x7`）。
- **调试器/内核要分层排查**：先用纯 QEMU 确认"不调试也崩"，立刻就能把问题从调试器层剥离开。
- **GDB 内嵌 Python 的坑**：`glob` 行为异常、`-batch` 模式下不自动解析符号，两者都要绕。
