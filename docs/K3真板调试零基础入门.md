# K3 真板调试零基础入门

## 结论

这份文档写给第一次接触硬件的同学。读完并动手做完文中的实验,你能完成四件事:给 K3 板子正确上电、用串口看到板子的启动日志、看懂它的完整启动链条、把 async-debug 调试器接到真板上。

文档里的事实都有出处,用三个标记区分可信度:【官方】来自《K3 CoM260 Kit 用户使用指南 V2.1》(2026/07/16);【已验证】来自团队前人 2026 年 7–10 月的真板操作记录(见 k3gdb 博客,链接在文末);【待验证】是推断,还没有真板验证。做实验时如果发现文档与实物不符,以实物为准,回来更新这份文档。

## 一、这块板子是什么

### 1.1 三个名字别混:芯片、模组、载板

板子的官方型号是 SpacemiT K3 COM260 Kit,是三层结构:

- **SoC(芯片)**:进迭时空(SpacemiT)的 K3 芯片。SoC 就是把 CPU、内存控制器、各种外设集成在一颗芯片上。K3 里有 8 个 RISC-V 架构的 X100 大核(跑操作系统和程序)和 8 个 A100 AI 核(跑 AI 计算)。
- **模组(COM260)**:把 K3 芯片、LPDDR5 内存、存储焊在一块小板上,做成可插拔的模块。模组上压着散热器和风扇。
- **载板**:你手里那块大板。模组插在载板上,载板提供电源口、USB 口、网口和排针。

**RISC-V** 是一种 CPU 指令集——CPU 能听懂的那套命令的规范。x86 和 ARM 之外,RISC-V 是第三家,而且开源。K3 的 X100 核符合 RVA23 标准,和我们之前用的 QEMU riscv64 虚拟机同门,所以 async-os 的 RISC-V 代码大概率能跑,但要适配硬件细节(第七节)。

### 1.2 板子上的接口

| 接口 | 干什么用 | 注意 |
| --- | --- | --- |
| DC 圆孔电源 | 给整板供电 | 19V/2.37A 或 12V/5A |
| 12Pin 排针 | 调试用:串口、开机、复位、下载 | 串口从这里接,但它**不是** JTAG |
| 40Pin 排针 | 通用 GPIO/SPI/I2C 扩展 | 树莓派风格,调试初期用不到 |
| TF 卡槽 | 插 TF 卡 | 有隐藏身份:JTAG 信号复用它的引脚(第五节) |
| USB-C | 数据、固件升级、fastboot 下载 | **不能给板子供电** |
| USB-A ×4 | 接外设 | — |
| RJ45 网口 | 千兆有线网 | — |

### 1.3 三个最容易搞错的点

1. **USB-C 不能供电**。板子必须用 DC 圆孔电源。Type-C 插电脑只能传数据和刷固件。
2. **12Pin 排针不是 JTAG 接口**。它只有串口、开机、复位、下载信号,没有 JTAG 的四根线(TCK/TMS/TDI/TDO)。
3. **JTAG 藏在 TF 卡槽的引脚里**。K3 让 JTAG 信号和 TF 卡(MMC1)共用引脚,默认给 TF 卡用,JTAG 是关的。第五节讲怎么打开。

## 二、实验零:上电、开机、风扇

### 2.1 上电与开关机

结论:插 DC 电源前先核对适配器电压;板子的开关机逻辑在 12Pin 排针上。

- 电源规格【官方】:19V/2.37A 或 12V/5A,DC 圆口。官方文档另一处写的是 12V/6A,两处不一致,以适配器标签和载板丝印为准。
- 12Pin 排针相关定义【官方】:12 号针 SLEEP/WAKE 是开机/关机,8 号针 PMIC_RST_Out 是复位,10 号针 FORCE_RECOVERY 是强制进入下载模式。
- 如果你的载板带电源按键:5 号针 BMCU_ACOK 与 6 号针 AUTO_ON_DIS 短接,即配置成按键开机。

### 2.2 风扇

结论:先把风扇线接到载板的风扇排针(丝印一般标 FAN),上电后看转不转。转就正常;不转先别慌,可能是系统起来后才受控。

- 载板的风扇接口是 4Pin 调速风扇接口【官方】:四根线里除 5V/GND 外,还有 PWM(调速)和 TACH(测速)两根,转速由软件控制,系统没起来时可能不转。
- 跑 Linux 系统时,系统的温度管理(thermal)自动调速,不用手动管。
- **跑裸机(async-os)时**:没有系统管风扇,4 针风扇可能全程不转。K3 满载功耗 18–35W,没风扇几分钟就过热。对策:调试初期把风扇电源接到常电 5V(如 40Pin 排针的 5V/GND),或者每次裸机运行控制在几分钟内;后期在 async-os 里加 PWM 风扇驱动。
- 前人日志的原文提醒:"start the fan as early as possible"(风扇尽早开)。

## 三、实验一:串口——让板子开口说话

### 3.1 串口是什么

**串口(UART)** 是板子最基础的"嘴":芯片把一行行文字从两根线里发出来。电脑开机时黑底白字的 BIOS 输出就是串口日志。我们看启动日志、操作 U-Boot、敲 OS 的 shell,全靠它。

- **波特率 115200**:串口没有时钟线,收发双方必须约定"每秒发多少位"。K3 的调试串口用 115200。
- **TTL 电平 3.3V**:板上信号是 0V/3.3V。电脑 USB 不直接认,需要一个 **USB-TTL 模块**(几块钱的小板)把 USB 转成串口。
- **TX/RX 交叉**:芯片的"发(TX)"接到模块的"收(RX)",反过来也一样。
- **GND 必须共地**:两块板的地线连一起,信号才有参照。
- **VCC 不要接**:USB-TTL 的 3.3V 输出电流很小,不是用来给开发板供电的。

### 3.2 接线表

【官方】12Pin 排针里串口是三根:

| 12Pin 针号 | 信号 | 接到 USB-TTL 模块 |
| --- | --- | --- |
| 3 | UART0_RXD(板子收) | 模块的 TX |
| 4 | UART0_TXD(板子发) | 模块的 RX |
| 7 | GND | 模块的 GND |

接反了只是收不到输出,不会烧板;但 VCC 接错可能烧。接好后先别急着上电,核对一遍再插 DC 电源。

### 3.3 怎么看输出

macOS:

```bash
ls /dev/cu.usbserial-*    # 找到 USB-TTL 对应的设备节点
picocom -b 115200 /dev/cu.usbserial-xxxx
```

Linux:

```bash
ls /dev/ttyUSB*
minicom -o -D /dev/ttyUSB0 -b 115200
```

上电后屏幕滚动启动日志 = 实验一成功。退出:picocom 按 Ctrl-A 再 Ctrl-Q;minicom 按 Ctrl-A 再 Q。

### 3.4 前人踩过的坑:输出不是纯文本

【已验证】串口输出里混着 **ANSI 颜色控制码**(比如 `\x1b[96m`)。人眼看是彩色文字,程序看到的却是一堆转义字符。人肉看无所谓;写脚本自动判断"出现 Welcome to Starry OS!"时,必须先清洗掉 ANSI 序列再匹配。前人在这上面卡过一次 180 秒超时。

## 四、板子的启动链:它怎么一步步活过来

### 4.1 每一环在干什么

结论:板子上电后不是一步进入 OS,而是接力赛,每级程序叫醒下一级,一级比一级能干。

```
BootROM → FSBL → OpenSBI → U-Boot → 内核(StarryOS / async-os)
```

- **BootROM**:芯片出厂固化的小程序,上电第一个执行,负责把下一级程序从存储里读出来。它还能进 Recovery 下载模式(4.3 节),那是我们调试的"入口"。
- **FSBL**(第一级引导程序):BootROM 加载它。它初始化内存(DDR),再加载 OpenSBI。
- **OpenSBI**:RISC-V 世界的标准底座,给操作系统提供 SBI 标准接口,管定时器、中断转发、核间通信。我们之前在 QEMU 里也有它。
- **U-Boot**:功能强大的引导器,有交互命令行(提示符 `=>`)。上传内核镜像、指定启动地址都在这里做。
- **内核**:最后的主角。

### 4.2 strap:板子上的"拨码开关"

【官方】芯片刚上电时,一些引脚的电平会被读成配置,这叫 **strap**。K3 用它选择启动介质和下载方式:

- Boot SEL(Strap1/Strap0):决定从哪启动。`11` = TF 卡 → UFS(前人验证用的就是这条路)。
- Download SEL(Strap2):`0` = USB 下载,`1` = UART 下载。
- JTAG SEL:决定 JTAG 路由,具体配置方式还没完全公开【待验证】。

这些 strap 在载板上有拨码开关或跳线帽,动手改之前先拍照记下默认状态。

### 4.3 前人验证过的启动流程(Golden Flow)

【已验证】前人 2026 年 9 月把整条启动链跑通并做成一键脚本。人工流程:

1. **完全断电**;按住/短接 12Pin 的 10 号针 **FORCE_RECOVERY**;上电,进入 BootROM 下载模式。
2. 电脑用 USB-C 连板子,`fastboot` 命令能看到设备(BootROM 的 Recovery 模式就是一个 fastboot 设备)。
3. 依次上传 **Debug 版 FSBL**(改过的 FSBL,它会把 TF 槽引脚切给 JTAG,见 5.2 节)→ 上传 **OpenSBI + U-Boot 合体镜像(FIT)**。
4. 串口出现 U-Boot 提示符 `=>`,敲 `scsi scan`,看到 **KINGSTON**(UFS 硬盘枚举成功)。
5. 让 U-Boot 进入 fastboot,上传内核到 0x140000000,上传设备树 DTB 到 0x138000000。
6. 敲 `booti 0x140000000 - 0x138000000` 启动内核,串口出现 `Welcome to Starry OS!`。

**设备树(DTB)** 是给内核的"硬件清单"文件:UART 在哪、内存多大、中断怎么接,都写在里面。内核拿到它才知道自己在什么硬件上。

### 4.4 一键脚本与启动状态机

【已验证】这条人工流程被前人写成 `boot_golden_flow.sh`,内部是个状态机:

```
BOOTROM_READY → SPL_READY → FULL_UBOOT_READY → UFS_READY
→ KERNEL_LOADED → DTB_LOADED → STARRYOS_READY
```

状态机的思想:**看到板子真的进入下一状态,才执行下一步**,不靠 sleep 猜时间。每一步的成功判据都是串口上的真实标志(比如看到 `KINGSTON` 才算 UFS 就绪)。

这套脚本目前在 async-debug 仓库的 `origin/async-integration` 分支:`testcases/k3-starryos/`(6.5 节细说)。

### 4.5 启动过程里前人踩过的四个坑

【已验证】全部来自真板日志:

1. **BootROM 的 fastboot 序列号是乱码** `????????????`。`fastboot -s ???? ...` 会失败。判断设备就绪要用 `fastboot getvar version-brom` 返回 `1.0`,而不是看序列号。
2. **Full U-Boot 起来后还会自己再进一次 fastboot**,需要再执行一次 `fastboot continue` 才真正进入 U-Boot 命令行。这一层藏得很深,人工操作时靠"下意识"完成,做自动化才暴露出来。
3. **U-Boot 有 5 秒 autoboot 倒计时**(`Hit any key to stop autoboot: 5`)。不按键它就跑去启动官方系统了。脚本会自动发一个字符打断它。
4. **USB 设备会反复重新枚举**。每级固件接管 USB 时设备都会消失重来,不能靠固定 sleep。

## 五、实验二:JTAG——打开 CPU 的调试后门

### 5.1 JTAG 是什么

结论:JTAG 是 CPU 的硬件调试"后门",能无条件暂停 CPU、读寄存器、改内存、下断点。async-debug 要调试真板内核,靠的就是它。

- **JTAG**:芯片调试/测试接口标准,四根核心信号线:TCK(时钟)、TMS(状态)、TDI(数据进)、TDO(数据出)。
- **Debug Module(DM)**:RISC-V 芯片内部响应 JTAG 的调试部件。K3 的设备树里有 `riscv,debug-v1.0.0` 描述【已验证】。
- **J-Link**:SEGGER 公司的 USB 调试探针,一头插电脑,另一头接 JTAG 信号。前人选它。
- **OpenOCD**:电脑上的软件"翻译层"。GDB 不懂 JTAG,OpenOCD 把 GDB 的调试请求翻译成 JTAG 信号,通过 J-Link 发给芯片。
- **hart**:RISC-V 里"一个硬件执行流"的称呼,类似"核"。

### 5.2 K3 最大的坑:JTAG 和 TF 卡槽共用引脚

【已验证】这是前人卡得最久的一步:J-Link 正常、OpenOCD 正常,但死活连不上 K3。查官方手册才发现:**K3 的 JTAG 信号和 TF 卡(MMC1)的引脚复用**,默认配置给 TF 卡用,JTAG 关闭。

引脚复用关系【已验证,来自 U-Boot SPL 源码】:

| TF 卡(MMC1)引脚 | 复用的 JTAG 信号 |
| --- | --- |
| DAT0 | TCK |
| DAT1 | TMS |
| DAT2 | TDO |
| DAT3 | TDI |

前人的解法:**修改启动固件(FSBL/SPL),让它在启动时把这组引脚切给 JTAG**。改完后串口出现一行字:

```
Debug JTAG enabled on MMC1 pins
```

从这以后 J-Link 才识别到 K3。所以接 JTAG 探针前,先确认板子跑的是"开过 JTAG"的启动固件。

物理接线有两种:
- **官方方案**:TF 卡槽支持插一张 **Debug 扩展卡**【官方】,卡上引出 JTAG 接口,直接连调试探针。我们的套件就带了这张卡和配套仿真器,不需要自己买 J-Link。
- **DIY 方案**:用 microSD 转接板插进 TF 槽引出引脚飞线。引脚图和照片见 k3gdb 博客、官方 JTAG 调试指南和社区仓库 ganboing/K3-Docs。

### 5.3 OpenOCD 的已验证配置

【已验证】前人固定下来的稳定参数:**JTAG 速率 100 kHz、只开 cluster0 的 core0(单核)**。更快或更多核在当时固件版本下不稳定。

启动后 OpenOCD 监听三个端口:

| 端口 | 服务 |
| --- | --- |
| 3333 | GDB 连接口(调试器连这里) |
| 4444 | OpenOCD 的 Telnet 管理口 |
| 6666 | OpenOCD 的 Tcl 接口 |

验证 GDB 通路的最小命令:

```bash
gdb-multiarch            # 或 riscv64-unknown-elf-gdb
(gdb) target remote localhost:3333
(gdb) info registers     # 能读出寄存器 = 通路已通
```

配置文件在 async-debug 仓库 `testcases/k3-starryos/openocd/`(interface/jlink.cfg 和 target/spacemit-k3.cfg,目前在 async-integration 分支)。后者值得看的地方:

- `TARGET acpu` 选 X100 大核;`rcpu` 是协处理器。
- **SECJTAG=0** 时,要先通过 post tap 的 `irscan 0x98` 解锁,K3 才放出真正的 JTAG 链(芯片出厂的安全机制)。
- 全部展开是 16 个 target:`k3.x100.0~7` 和 `k3.a100.8~15`,对应 4 个 cluster × 4 核。

## 六、实验三:async-debug 接上真板

### 6.1 完整链路

结论:async-debug 不直接碰硬件,它指挥 GDB,GDB 连 OpenOCD,OpenOCD 通过 J-Link 控制芯片。

```
VS Code(async-debug 扩展)
  → GDB(gdb-multiarch)
    → OpenOCD(localhost:3333)
      → J-Link
        → K3 芯片的 Debug Module
          → 板上的内核
```

### 6.2 Host-DWARF:板上跑"瘦"内核,符号留在电脑上

【已验证】前人真板调试的核心方法:板子上运行 release 编译、不带调试信息的内核镜像;电脑端加载**同一次构建**产出的 ELF,里面带完整调试信息(符号表、源码行号)。两边身份必须一致,否则断点对不上。

- 板子跑:release bin
- 电脑加载:同一次构建的 ELF(符号 + 源码位置)
- 判断是否同一次:比对 ELF 的 SHA256

### 6.3 调试配置

【已验证】工作区(VS Code 窗口 B)的 `.vscode/launch.json` 长这样:

```json
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "K3 StarryOS N Host-DWARF ARD",
      "type": "ardb",
      "request": "launch",
      "program": "${workspaceFolder}/artifacts/starryos.elf",
      "cwd": "${workspaceFolder}",
      "remote": "localhost:3333",
      "gdbPath": "/usr/bin/gdb-multiarch",
      "enableOsDebug": false
    }
  ]
}
```

`remote` 指向 OpenOCD 的 GDB 端口;`program` 是 Host-DWARF ELF。注意这是 **launch** 请求(启动 GDB 并连已有远端),不是 attach——这条 remote 路径是前人在 async-integration 分支加的,main 上没有(见 6.5 节)。

### 6.4 双终端 + 双窗口工作流

【已验证】前人验证过的分工:

| 位置 | 职责 |
| --- | --- |
| 终端 T1 | 串口:启动板子、在 OS shell 里敲命令 |
| 终端 T2 | 跑 OpenOCD,保持运行 |
| VS Code 窗口 A | 打开 async-debug 仓库,F5 启动扩展开发宿主 |
| VS Code 窗口 B | 打开工作区,选调试配置,操作 Async Inspector |

最小验证实验(在板上 shell 执行 `sleep 1`,触发异步定时任务):

1. 暂停目标 → Inspector 里 **Gen Whitelist**(扫描 ELF 生成可观察函数清单)
2. 勾选要观察的 crate(前人示例是 StarryOS 的 ax_task,async-os 的 crate 名不同,方法一样)→ 勾 **Async only** → **Apply Whitelist**(只装异步函数探针)
3. 选一个 async 函数点 **Trace**(设为观察根节点)
4. 在对应 poll 函数源码处下用户断点
5. Continue,在 T1 敲 `sleep 1`
6. 命中断点后看 History(执行历史)、Observer Tree(关系树)、Snapshot(暂停快照)

**我们实验室的物理拓扑**:板子接在本机 Mac,async-debug 跑在云服务器(x86)上,调试口通过 ssh 隧道打通。这个拓扑不影响上面任何步骤,唯一要求:OpenOCD 必须跑在**物理连接 J-Link** 的那台机器上。

## 七、我们的现状:async-os 与前人 StarryOS 的差异

结论:硬件链、启动链、调试链全部可以复用前人成果;我们真正要新做的是 async-os 的 K3 平台适配和代码合并。

相同(直接继承):

- 板子接线、供电、串口、JTAG 打开方式
- boot_golden_flow.sh 启动状态机(把最后的 StarryOS 镜像换成 async-os 的)
- OpenOCD 配置、Host-DWARF 调试方法

不同(要新做):

1. **async-os 没有 K3 平台**。目前 riscv64 只有 qemu-virt。要新增平台配置(内存布局、加载地址)、串口驱动(K3 用 PXA/dw-apb-uart,16550 兼容,大概率复用 qemu-virt 驱动改基址即可)。
2. **中断控制器是 APLIC,不是 PLIC**。qemu-virt 用 PLIC;K3 是 AIA 体系。第一阶段可以先只跑单核 + 串口轮询,外部中断放第二步。
3. **把 origin/async-integration 合进来**:remote launch 支持 + testcases/k3-starryos 脚本。

## 八、术语表

| 术语 | 一句解释 |
| --- | --- |
| SoC | 把 CPU、内存控制器、外设集成在一颗芯片上 |
| RISC-V | 开源的 CPU 指令集家族,x86/ARM 之外的第三家 |
| 模组/载板 | 模组是核心电路小板,载板是提供接口的大板 |
| UART/串口 | 芯片把文字日志按位从两根线发出来的接口 |
| 波特率 | 串口双方约定的传输速率,这里是 115200 |
| TTL 电平 | 板上 0V/3.3V 的数字信号电平 |
| USB-TTL | 把电脑 USB 转成串口的小模块 |
| BootROM | 芯片出厂固化、上电第一个跑的小程序 |
| FSBL | BootROM 加载的第一级引导,负责初始化内存 |
| OpenSBI | RISC-V 给操作系统提供的标准底座接口 |
| U-Boot | 有交互命令行的引导器,提示符 `=>` |
| FIT | 把 OpenSBI+U-Boot 等多个固件打包成一个镜像的格式 |
| DTB(设备树) | 给内核的硬件清单文件 |
| fastboot | 一种 USB 下载协议,U-Boot 用它接收镜像 |
| strap | 上电瞬间引脚电平读成的硬件配置 |
| JTAG | 芯片调试接口标准,TCK/TMS/TDI/TDO 四根线 |
| Debug Module | 芯片内部响应 JTAG 的调试部件 |
| OpenOCD | GDB 和 JTAG 硬件之间的翻译层软件 |
| hart | RISC-V 的一个硬件执行流,类似"核" |
| cluster | 一组核的集合,K3 有 4 个 cluster |
| UFS | 板载高速存储芯片(金士顿 128/256GB) |
| Host-DWARF | 板上跑 release 镜像、调试信息留在电脑 ELF 的方法 |
| 白名单 | 选定要观察的函数清单,poll 函数装探针用 |
