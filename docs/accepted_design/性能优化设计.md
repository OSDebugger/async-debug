# 性能优化设计

日期：2026-10-20
状态：Accepted

## 概述

async-debug 调试器对被调试程序存在严重的时序侵入。OS 模式下，调试开销达到程序自身工作量的 4.3 倍。本文档包含三部分：问题的理论分析和实验量化（§1–§2）、方案设计（§3–§4）、实施状态（§5）。

## 1. 问题分析

### 1.1 暂停次数

调试器在三个位置触发暂停：

- **PollEntryBP（协程入口断点）**：每个要跟踪的协程函数入口放一个断点。协程每唤醒、往前推一轮（一次 poll），程序就停一次。异步程序中协程推进极其频繁，该断点是时间开销的主要来源。
- **CallSiteBP（调用指令断点）**：第一次进入协程函数时，反汇编整个函数，给每条 call 指令装断点。之后每一轮 poll 执行到任何一条调用就停一次。实际插桩的 122 个调用指令中，有效调用仅 8 次——绝大多数停顿是无效拦截。
- **_PopOnReturnBP（返回断点）**：入口断点命中后在函数返回位置挂断点，返回时再停一次。开销较小。

一次 poll 的停止次数：入口 1 次 + 内部调用 N 次 + 返回 1 次。

### 1.2 每次暂停的时长

按预估耗时从高到低：

- **每次暂停写文件**：每命中一次断点追加一行记录到日志文件（打开→写入→关闭），次数极多，输出量极大。
- **call 断点命中时现场反汇编**：每次 call 断点命中，现场把当前指令翻译回汇编（每次重新翻译），解析出被调函数地址，再用 GDB 命令查询地址属于哪个函数。每命中一次执行一次。
- **协程入口命中时读寄存器、查类型、读内存**：入口命中后读寄存器拿协程实例地址，按函数名拼类型名，向 GDB 查类型定义（无缓存，每次重新查），按类型结构读内存遍历字段。每次入口命中是一串几十次 GDB 内部查询。
- **白名单地址表一次性构建**：第一次命中时，把白名单里每个函数名逐个解析成地址，每个名字一次 GDB 查询，几百个名字就是几百次查询。一次性开销，但发生在第一次停止时，明显拉长首次停止时间。

### 1.3 OS 模式下的两个大头

**内核↔用户切换**。每次特权级切换（进内核/出内核）触发一次组切换，期间整个虚拟机冻结，串行执行七个步骤：

| 步骤 | 描述 |
|------|------|
| 保存跟踪状态 | 一条 GDB 命令，把全部跟踪状态序列化 |
| 逐个删断点 | 删掉旧组所有断点 |
| 卸载/加载符号文件 | GDB 解析整个文件的调试信息，秒级 |
| 逐个重插断点 | 重新插入新组断点 |
| 恢复跟踪状态 | 重新装所有跟踪断点 |
| 重建白名单 | 扫描全部符号→写白名单文件→加载→给用户程序异步函数逐个装断点 |

一次切换冻结数秒，每次进出内核都发生。

**特权级切换的逐条单步**。为判断"是否已进到内核/回到用户"，逐条单步执行指令——每执行一条停一次、读一次寄存器、再执行下一条，直到到达目标。切换过程通常单步几十条指令。

## 2. 实验证据

### 2.1 实验 A：高频断点暂停开销

测试对象：testcases/minimal（小异步示例程序），launch 模式。

三组对照：

| 测试 | 说明 |
|------|------|
| baseline | 不装跟踪断点，用 Linux time 计时 |
| run | 装断点，开启总统计 |
| detail | 装断点，开启分段统计 |

**Run 结果**：

- poll_entry：21 次命中，avg=1870.2 μs，max=14855.5 μs，total=0.039 s
- call_site：122 次命中，avg=833.2 μs，max=2530.7 μs，total=0.102 s
- 全部 143 次停止，Python stop() 总时间=0.141 s

CPU 时间差：baseline 0.65 s → debug 0.93 s，跟踪让 CPU 多干了 0.28 s。其中 0.14 s 是 Python 记录代码，剩下约 0.14 s 是 GDB 自身处理断点的固定开销——每次暂停成本约一半在 Python、一半在 GDB。

**Detail 结果**：

poll_entry 内部分段（21 次）：

| 步骤 | 平均 | 总耗时 | 说明 |
|------|------|--------|------|
| callsite_install | 624.7 μs | 0.013 s | 检查函数装过断点否，未装则反汇编全函数 |
| coro_setup | 443.6 μs | 0.009 s | 读函数名、寄存器拿协程身份，都是 GDB 接口，步骤必须 |
| log_poll | 308.0 μs | 0.006 s | 追加一行记录到日志文件 |
| awaitee | 6.2 μs | ~0 | 读"等待的子协程"信息，本次几乎为 0 |

call_site 内部分段（122 次）：

| 步骤 | 平均 | 总耗时 | 说明 |
|------|------|--------|------|
| asm+resolve | 487.5 μs | 0.059 s | 反汇编当前指令，查看调用者 |
| callee_lookup | 240.8 μs | 0.029 s | 查询被调函数是否在开发者关心的名单里 |
| log_call | 336.3 μs | 0.003 s | 8 次有效调用才写日志，122 次只有 8 次命中 |

**实验 A 结论**：

- 单次停止平均约 1 ms（本机），OS 模式经 QEMU 只会更贵。
- Python 和 GDB 各占一半——优化 Python 只能省一半，另一半要靠减少停止次数。
- 122 次 call_site 停顿中仅 8 次有效，源头过滤空间极大。
- asm+resolve 累计 0.059 s（现场反汇编），callsite_install 累计 0.013 s（首次全函数反汇编）——前者是后者的 4.5 倍，重复劳动可通过前置解析消除。

### 2.2 实验 B：OS 模式组切换开销

测试对象：async-os 依次运行 hello_world 和 pipetest 两个用户程序，QEMU 环境。

两组对照：

| 测试 | 跑法 |
|------|------|
| baseline | QEMU 直接运行，不启动调试器（make justrun） |
| debug | VS Code 里以 ardb 启动调试，源代码插桩计时 |

**Baseline**：CPU 时间合计 74.5 s，两个用户程序正常跑完，OS 自动关机。

**Debug**：382 次组切换（hello_world 73 次往返、pipetest 118 次往返），总耗时 303.7 s，平均每次 795 ms。

按方向拆开：

| 方向 | 次数 | 平均每次 | 主要开销 |
|------|------|----------|----------|
| 内核→hello_world | 73 | 1058 ms | 重建白名单 830 ms |
| 内核→pipetest | 118 | 1404 ms | 重建白名单 946 ms |
| hello_world→内核 | 73 | 203 ms | 卸载符号 107 ms |
| pipetest→内核 | 118 | 390 ms | 卸载符号 297 ms |

七个步骤总占比：

| 步骤 | 总耗时 | 占比 |
|------|--------|------|
| 重建白名单 | 172.2 s | 56.7% |
| 卸载符号 | 42.9 s | 14.1% |
| 恢复状态 | 31.7 s | 10.4% |
| 加载符号 | 27.7 s | 9.1% |
| 重插断点 | 20.7 s | 6.8% |
| 保存状态 | 5.6 s | 1.8% |
| 删断点 | 3.0 s | 1.0% |

特权级单步：191 段、698 步，总耗时 13.9 s，平均每步 19.9 ms。全部发生在内核→用户方向。每段步数：1 步×145 段、12 步×45 段、13 步×1 段。

总开销：组切换 303.7 s + 单步 13.9 s = 317.5 s，是程序自身 CPU 时间（74.5 s）的 4.3 倍。

**实验 B 结论**：

- 组切换占总开销 96%，其中重建白名单一项占 56.7%。每次跨入用户态，程序冻结 1–1.4 s，约七成花在重建白名单。
- 符号表装卸占 23.2%，且随程序增大而增加（pipetest 是 hello_world 的近 3 倍）。
- 单步单价高（19.9 ms，是实验 A 的 20 倍），但步数比预判少（平均每次进入用户态 3.7 步），占总开销 4%。

## 3. 解决方案 1：白名单重建优化与 call 指令精准插桩

### 3.1 设计依据

讨论中确认的关键事实：

1. **四连大部分是冗余劳动**。`ardb-restore-trace-state` 本身就会恢复白名单集合并按保存的 poll_entries 重装所有入口断点。四连在"切回已保存过状态的组"时，其产出与 restore 几乎完全重复。
2. **地址表被无谓作废**。同一进程存活期间基址不变，但 restore 强制清空地址表（`_WHITELIST_ADDR_READY=False`），下一次 poll 命中时用 N 次 GDB 查询从零重建（每符号一次 `gdb.lookup_global_symbol`，失败再 `info address`）。
3. **组切换后 CallSiteBP 不会被重装**。restore 只重装入口断点（PollEntryBP），把 `_CALLSITE_INSTALLED_FOR_FN` 恢复为保存值，导致切换后 poll 命中时跳过重扫——call 断点在首次切换后永久消失。
4. **RISC-V 的 callsite 覆盖存在缺口**。`CALL_MNEMONIC_RE` 匹配 `call` 开头的助记符；binutils 的 RISC-V 反汇编默认显示伪指令，`call` 正是 `auipc ra + jalr ra` 对的伪指令名。`jal`/`jalr`（及压缩形式）需补齐。
5. **多用户组交替时 JSON 互相覆盖**。磁盘上只有一份 `poll_functions_grouped.json`，gen 会覆盖它——hello_world 和 pipetest 交替时，一份 JSON 无法同时服务两个 ELF。

### 3.2 方案

**第一层：切换链条瘦身**。TS 侧维护 `initializedGroups: Set<string>`，记录已完成首次初始化的组。首次进入某用户组：跑完整四连，验证成功后加入集合。后续切回该组：跳过四连，仅依赖 restore-trace-state（已恢复白名单+重装入口断点）。dirty 为全局标记：用户改过 enabled crates → 下一次组切换跑 update+load（不跑 gen）。`ardb-reset` 时清空集合与 dirty。

预期：303 次切换中约 301 次的四连被消掉，whitelist_rebuild 步骤总耗时从 172.2 s 降到仅剩首次进入成本（约 2 次×0.9 s）。

**第二层：地址表复用 + 锚点校验**。`_SAVED_STATES` 已保存 `whitelist_addr_map`，restore 时不再无条件清空。重新解析白名单中 1 个符号的当前地址（1 次 GDB 查询）：与缓存一致→整表直接复用；不一致→计算 delta，整表平移 delta（覆盖同一 ELF 换基址的情况）；解析失败→回退全量重建。多 objfile 检测：符号来自多个 objfile 时放弃复用（安全兜底）。

预期：消掉每次切回用户组后第一次 poll 命中时的 N 次 GDB 查询。

**第三层：grouped JSON 按符号组合缓存**。`ardb-gen-whitelist` 生成的 grouped JSON 按参与扫描的全部 objfile 的 (路径, mtime) 列表为键，缓存到 `temp/whitelist_cache/`。gen 时先查缓存，命中跳过 `info functions` 全量扫描。任一 objfile 变化则缓存失效重扫。`ardb-update-whitelist`/`ardb-trace-user-crate` 增加参数，指定使用哪个符号组合的 JSON。

**RISC-V callsite 适配 + 安装时过滤**。`CALL_MNEMONIC_RE` 覆盖全部调用形式——x86 `call`、RISC-V `call` 伪指令/`jal`/`jalr`/压缩形式 `c.jalr`/`c.j`（防御性包含）、AArch64 `bl`/`blr`；排除返回类（`ret`/`c.jr`）。安装时过滤：直接调用解析目标地址→与白名单比对→不感兴趣不插；间接调用全部照插，命中时再判断。callsite 保存/重装：save 时保存 `{函数名: [callsite 地址...]}` 到 saved state；restore 时锚点校验 delta==0 则直接重装 CallSiteBP（免反汇编重扫）。

### 3.3 目标与非目标

**目标**：OS 模式白名单重建开销从约 830–946 ms 降到接近零；补齐 RISC-V 缺失的调用插桩（重点是 `jalr` 间接调用）；安装时过滤直接调用，减少无效停顿；修复组切换后 CallSiteBP 消失问题。

**非目标**：符号表加载/卸载优化、特权级单步优化、断点 enable/disable 替代删插、callsite 命中时的 asm+resolve 前置缓存、日志与 IO 清理（以上独立立项）。

**反目标**：为速度牺牲正确性（锚点 delta==0 才复用缓存）；破坏 launch 模式现有行为；破坏 saved state 兼容性。

## 4. 解决方案 2：符号常驻与按程序架构

### 4.1 设计依据

实验查证的十条关键事实：

1. **GDB Inferior 方案不可行**：GDB multi-target 要求每个 inferior 独立连接，QEMU gdbstub 仅支持单连接。
2. **用户程序 VA 区间完全重叠**：hello_world 与 pipetest 均为 musl 静态链接、同基址，区间级重叠——不同程序给 A 设的断点，B 执行到同地址必然命中。
3. **`info symbol <地址>` 在符号常驻后完全歧义**：两个符号表同挂时 GDB 返回多个答案，不仲裁不报错。符号查询必须走自有名字键地址表，GDB 查询仅留兜底。
4. **QEMU gdbstub 无 non-stop**：all-stop 是唯一停止模型——命中即全机冻结，恰好与"命中就全部暂停"的目标一致。
5. **QEMU 断点按虚拟地址对全部 vCPU 生效**：断点插入传播到所有核，命中通道隔离必须由调试器自己做。
6. **async-os 具备 SMP + 多任务并发设施**：CFS/FIFO/RR/taic 调度器、per-cpu 基础设施、`-smp $(SMP)` 可配。
7. **程序身份判定已有现成机制**：hook 断点读 OS 任务结构判定"当前哪个程序在跑"。
8. **符号常驻的支撑设施已建成**（上一轮）：名字键白名单地址表、按 crate 分组的 grouped JSON + 按符号组合缓存、锚点校验的地址表复用。
9. **每个用户程序拥有独立地址空间**：`Executor::init_user` 为每个程序新建独立 `MemorySet` 与 `page_table_token`——跨程序 this_ptr 同值碰撞真实可能，协程键必须加程序维度。
10. **跨 Executor 的任务迁移是 TODO**（executor.rs:272）——暂不存在跨程序任务迁移。

### 4.2 方案

**符号常驻化**。所有符号文件永久加载、永不卸载。`breakpointGroups.ts` 的符号装卸步骤（filesToRemove/filesToAdd）删除——`loadedSymbolFiles` 退化为只增不减。连带简化：grouped JSON 缓存因符号组合固定为（内核+全部用户程序）而 gen 一次、永久命中；白名单/地址表按程序常驻内存，锚点校验保留防程序重载。残余歧义处理：`info symbol` 兜底多答案行为——`_info_symbol_name` 取第一行，错答被白名单名字过滤拦截（漏记不误记），维持现状。

预期：符号装卸（load/unload_symbols）从每次切换约 360 ms 归零。

**断点按程序插拔**。每个用户程序一个断点集合（现有 BreakpointGroups.groups 结构复用）。程序活跃判定：hook 断点命中→对每个 vCPU 独立判定其当前程序→活跃程序集合=各 vCPU 当前程序之并集。插拔动作：活跃程序集合做 Z0 批量插入、离开程序做 z0 移除；内核断点始终插入。插拔时机：hook 命中时（程序切换点），all-stop 保证期间无 vCPU 推进。

**stop 侧程序门控**（并行正确性兜底）。每个 Python 断点记录其所属程序，`stop()` 回调先核对命中 vCPU 的当前程序——不属于该断点的程序则 `return False` 静默继续。门控使"错记 0 次"与插入时机解耦。

**跟踪状态按程序常驻**。`_SAVED_STATES` 退化为每程序一份独立运行时表（白名单、地址表、callsite 表、协程表、影子栈各自成桶）。表间天然隔离——不同程序同名符号/同值 this_ptr 互不污染。程序暂停执行时不丢失状态；重新活跃时直接续用（锚点校验兜底）。内核作为特殊"程序"同样独立一桶。

**同名符号解析加固**。多个静态链接用户程序常驻后，共享符号在每份 ELF 里重名。每程序的地址表构建改用 `objfile.lookup_global_symbol(name)`（GDB Python 的 Objfile 级查找），按程序自己的 objfile 范围解析。

**影子栈键设计**。本轮为 vCPU 键：现行 async-os 任务与核亲和（每核一个 Executor，`___PERCPU_CURRENT_EXECUTOR_PTR`，跨 Executor 迁移是 TODO），vCPU 键的嵌套 poll 栈模型在现行 OS 下正确。触发条件（OS 实现跨核迁移）成立时给 `_TLS_STACK` 键加任务维度。

### 4.3 执行流归因原则

执行流按**执行上下文**（当前页表+特权级）归因、按程序分桶；代码来源（哪个 ELF）不参与归因。用户程序调内核、共享运行时代码执行、乃至跨程序直接调用，一律记入"执行者"的流。跨特权级的因果链由 snapshot 拼接（用户异步链+内核物理栈尾），分桶不破坏拼接。

### 4.4 多核并行适配

**执行控制**：step 调度锁（单步锁当前线程、continue 放行全部核）；单步序列线程锁定（过渡期间外来停止静默）；静默继续时临时禁用断点防原地重入。

**停止与判定**（all-stop 前提下）：任何 vCPU 命中断点→全机冻结→Python stop 处理器读取所有 vCPU 的 PC 与特权级→按 PC 区间判定内核/用户、按 hook 任务结构判定具体程序。命中断点归属程序=命中 vCPU 的当前程序。特权级过渡期单步：`scheduler-locking on` + vCont `s:<thread>` 只放行目标 vCPU。

### 4.5 目标与非目标

**目标**：符号加载/卸载开销归零；断点按程序插拔，内核断点常驻；统一支持单线程、多线程并发、单程序多核三种场景；执行流按程序维护，零错记。

**非目标**：特权级单步优化（独立立项）；GDB Inferior 方案（已证不可行）；RISC-V 硬件 trace（真机路线另议）；并行多用户程序（下一轮专项——现行 async-os 跨 Executor 迁移是 TODO，串行与单程序多核不受此限制）。

**反目标**：不为并行牺牲正确性（多 vCPU 下的状态判定必须有依据）；不破坏单线程场景既有行为；不引入"当前全局唯一程序"的假设。

### 6.3 剩余开销分析

两项优化后，单次组切换的剩余开销分布：

- **断点重插（reinsert_bps）**：每次 55–70 ms。这是当前最大的残留项——每次切换仍需逐个删旧断点、逐个插新断点。进一步的优化方向是 enable/disable 批量翻转替代删插，或断点按程序插拔（§4.2 方案中已设计、待实现）。
- **状态保存/恢复（save_state / restore_state）**：合计约 25–50 ms。GDB 序列化命令的内部开销，与应用逻辑无关。pipetest 方向的 restore_state 异常偏高（平均约 230 ms，hello_world 只有约 15 ms），原因未查清。
- **pipetest 进入用户态仍偏贵**：380.9 ms，其中断点重插和状态恢复两项占比最大。pipetest 是 musl 静态链接，断点数量远多于 hello_world。

### 6.4 实验 A（launch 模式）的已知局限

实验 A 的对照实验因测试程序（minimal）太小而失效——程序的执行时间（几十毫秒）被 GDB 启动固定开销（约 0.7 s）淹没，"总时间差"不可靠，只能靠 CPU 时间差估算。要使对照有效，需增大测试程序（如加循环参数，让单次运行产生几万次停止）。开发阶段以实验 B 的 OS 模式数据为主要优化依据。
- 功能回归：hello_world/pipetest 跟踪记录完整性与现状一致或更好
- 单线程、并发、单程序多核三种场景功能回归通过
- 符号常驻后调用链记录正确性：错记 0 次（漏记允许有界，白名单拦截保证）
