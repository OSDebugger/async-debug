# 符号常驻 + 按程序断点插拔 + 多核并行调试架构 — 设计文档

日期：2026-10-20
范围：性能优化报告 3.1 第二项（符号表加载/卸载开销），架构升维为多核并行调试模型

## 1. 意图与背景

上一轮优化后，每次"内核↔用户"往返仍耗时 ~689ms，其中符号卸载 226.9ms、符号加载 133.6ms、
重插断点 ~52ms×2、状态恢复 152.7ms（pipetest 异常占大头）。同时用户明确了调试器的长期目标：
支持单线程、多线程并发、多核并行的三种执行场景，跟踪单位从"进程/线程"提升为**程序**——
因为要恢复的异步逻辑执行流在 poll 跨上下文转移时断裂，恢复所需信息（影子栈、协程表）按程序
累积，与在哪个 vCPU 上执行无关。

设计讨论中通过真机实验确立的关键事实：

1. **GDB Inferior 方案不可行**（已查证）：GDB multi-target 要求每个 inferior 独立连接，
   GDB 官方测试明确"plain remote target 不能多 inferior"；QEMU gdbstub 仅支持单连接。
2. **用户程序 VA 区间完全重叠**（实验）：hello_world 与 pipetest 均为 musl 静态链接、
   同基址（0x0 附近起），区间级重叠——"相同虚拟地址很少"不成立，是结构性必然。
3. **`info symbol <地址>` 在符号常驻后完全歧义**（实验）：两个符号表同挂时，GDB 对同一
   地址返回**多个**"符号+偏移"答案（每个 objfile 一个），既不仲裁也不报错。GDB 符号查询层
   不看页表；页表只作用于断点命中通道（QEMU 按当前页表取指）。
4. **QEMU gdbstub 无 non-stop**（已查证）：vCPU 即线程、vCont 单线程 step 可用，但全停
   （all-stop）是唯一停止模型——命中即全机冻结，这恰好与"命中就全部暂停"的目标一致。
5. **async-os 具备 SMP + 多任务并发设施**（源码查证）：CFS/FIFO/RR/taic 调度器、
   per-cpu 基础设施、`-smp $(SMP)` 可配；多程序并发执行是真实目标。
6. **程序身份判定已有现成机制**：hook 断点读 OS 任务结构判定"当前哪个程序在跑"（现有
   breakpointGroups 的 hook 机制），可扩展为每 vCPU 独立判定。
7. **符号常驻的支撑设施已建成**（上一轮）：名字键白名单地址表（无歧义主路径）、
   按 crate 分组的 grouped JSON + 按符号组合缓存、锚点校验的地址表复用。
8. **每个用户程序拥有独立地址空间**（源码查证）：`Executor::init_user` 为每个程序新建
   独立 `MemorySet` 与 `page_table_token`（并切换页表根加载程序）——跨程序 this_ptr
   同值碰撞真实可能（各程序独立分配器），"协程键不加程序维度"的原有前提不成立。
9. **QEMU 断点按虚拟地址对全部 vCPU 生效**（已查证：断点插入传播到所有 vCPU）——多程序
   并行时，A 的断点会在 B 执行同 VA 时误命中；命中通道的隔离必须由调试器自己做
   （stop 回调核对命中 vCPU 的当前程序）。
10. **跨 Executor 的任务迁移是 TODO**（源码查证，executor.rs:272）——暂不存在跨程序
    任务迁移；同程序内任务跨核迁移的可能性未证实。

## 2. 目标

- 符号加载/卸载开销归零：所有符号文件常驻，切换时不再 add/remove-symbol-file。
- 断点按程序插拔：程序活跃时其断点 Z0 批量插入，切走时移除；内核断点常驻
  （高半区 0xffffffc0... 与用户低半区 0x0-0x4xxxx 天然不重叠，永不错碰）。
- 统一支持三种场景：单线程（一个程序活跃）、多线程并发（一个程序多协程/多任务）、
  多核并行（多 vCPU 同时执行，可能分属不同程序）。
- 执行流按程序维护：命中全停后，判定命中的 vCPU 所属程序，记录该程序的异步逻辑执行流。

## 3. 非目标 / 反目标

**非目标**：
- 特权级单步优化（3.1 第四项，独立立项）
- 断点 enable/disable 的进一步优化（本设计中的 Z0/z0 插拔即其形态）
- GDB Inferior / gdbserver 多路复用器（已证不可行）
- RISC-V 硬件 trace（E-Trace/N-Trace，QEMU 不支持，真机路线另议）

**反目标**：
- 不为并行牺牲正确性：多 vCPU 下的状态判定必须有依据（读 PC/satp/任务结构），不靠假设
- 不破坏单线程场景的既有行为（minimal 测试、实验 B 流程保持可用）
- 不引入"当前全局唯一程序"的假设——这是本次要消灭的概念

## 4. 约束（代码事实 + 实验证据）

- 切换流程现状（breakpointGroups.ts）：save → 删断点 → 卸/载符号 → 重插断点 → restore →
  白名单链（上一轮已瘦身）→ continue；本设计保留"切换"骨架，只去掉符号装卸、把断点删插
  改为按程序插拔。
- 断点集合按组管理（BreakpointGroups.groups + setBreakpointsArguments），hook 断点全局
  常驻（上一轮已如此）。
- 上一轮建成：`_WHITELIST_ADDR_MAP`（名字键）、`_CALLSITE_ADDRS_BY_FN`、锚点校验复用、
  grouped JSON 按符号组合缓存、`_grouped_json_path()`。
- QEMU：all-stop；vCont `s:N` 单线程 step 可用（2017 重写后正确）。
- 用户程序 ELF：同基址、区间重叠（实验证据）；内核高半区与用户低半区不重叠。
- 协程键 `(poll_sym, this_ptr)`：当前架构下跨程序碰撞不可能（串行被 save/restore 隔离；
  共享地址空间下同时存活的程序内存分配唯一）。

## 5. 已拍板的决定（用户拍板）

1. **符号表常驻**：GDB 侧符号文件永久加载，永不卸载；符号查询主路径走自有名字键地址表，
   GDB 地址查询仅留兜底（错答过不了白名单 → 有界漏记不误记）。
2. **断点按程序插拔**：程序活跃才 Z0 插入其断点，切走移除；内核断点常驻。
3. **跟踪单位 = 程序**：断点、符号、执行流（影子栈/协程表）全部按程序维护；不按进程/线程。
4. **命中即全停**：任何断点命中 → 全机冻结（all-stop）→ 判定命中 vCPU 所属程序 →
   记录该程序的异步执行流。
5. **跟踪状态按"每程序一份独立表"组织**（审查发现每程序独立地址空间后，替代原
   "协程键暂不加程序维度"的决定）：白名单/地址表/协程表/影子栈按程序成桶，表间天然
   隔离（不同程序同名符号、同值 this_ptr 互不污染），内层键不动。内核作为特殊"程序"
   同样独立一桶。
6. 不使用 GDB Inferior（单 gdbstub 硬限制）；参考国防科大 OpenOCD AMP 工作的
   "hart 即线程"思想，但跟踪单位按程序而非按核。
7. **影子栈按 (程序, task) 键**（任务会/可能跨核）：每次 poll 命中读当前 task 结构
   做键，任务跨核迁移不破坏异步调用链；task 读取依赖 async-os 的 per-CPU 当前任务
   指针（现有 hook 机制的同类依赖）。

## 6. 方案设计（标注我的提议）

### 6.1 符号常驻化【核心】

**机制**：`breakpointGroups.ts` 的符号装卸步骤（filesToRemove/filesToAdd）删除——
所有 addSymbolFile 一次完成、永不 remove。`loadedSymbolFiles` 集合退化为只增不减。

**连带简化**：
- grouped JSON 缓存：常驻后符号组合固定为（内核 + 全部用户程序），gen 一次、永久命中
  （上一轮缓存机制直接受益）；`_grouped_json_path()` 按键查找逻辑不变。
- 白名单/地址表：按程序常驻内存，不再随切换重建；锚点校验保留（防程序重载）。

**残余歧义处理**（实验已证）：`info symbol` 兜底的多答案行为——`_info_symbol_name` 取
第一行，错答被白名单名字过滤拦截（漏记不误记），维持现状即可，不额外处理。

### 6.2 断点按程序插拔【核心】

**机制**：
- 每个用户程序一个断点集合（现有 BreakpointGroups.groups 结构复用，"组"概念保留，
  但语义从"符号+断点切换"退化为"断点集合"）。
- 程序活跃判定：hook 断点命中（现有机制，读 OS 任务结构）→ 对**每个 vCPU** 独立判定其
  当前程序 → 活跃程序集合 = 各 vCPU 当前程序之并集。
- 插拔动作：对活跃程序集合做 Z0 批量插入、对刚离开的程序做 z0 移除；内核断点始终插入。
- 插拔时机：hook 命中时执行（程序切换点），all-stop 保证期间无 vCPU 推进。

**stop 侧程序门控（并行正确性兜底，我的 call）**：QEMU 断点按 VA 对全部 vCPU 生效，
多程序并行时 A 的断点必然在 B 执行同 VA 时误命中。因此每个 Python 断点记录其所属程序，
`stop()` 回调先核对**命中 vCPU 的当前程序**，不属于该断点的程序则 `return False` 静默
继续。门控使"错记 0 次"与插入时机解耦；程序切入前断点未插入的时间窗内最多**漏记**
（有界），不产生错误记录。

**实现要点**：GDB 的 Z0/z0 通过 MI 层已有 addBreakPoint/clearBreakPoints 通路；断点对象
（PollEntryBP、CallSiteBP）本身常驻 Python 内存，插拔只针对 GDB 侧（insert/remove）。

### 6.3 跟踪状态按程序常驻【核心】

**机制**：`_SAVED_STATES` 从"切换时序列化/恢复"退化为"按程序常驻累积"，形态为
**每程序一份独立的运行时表**（白名单、地址表、callsite 表、协程表、影子栈各自成桶）：
- 表间天然隔离——不同程序的同名符号/同值 this_ptr 不会互相污染（每程序独立地址空间，
  事实 8），内层键无需程序维度；
- 影子栈桶内按 **(程序, task)** 键（不再按 GDB 线程/vCPU）：每次 poll 命中读当前
  task 结构做键，任务跨核迁移不打断异步调用链；
- 程序暂停执行（切走）时不丢失状态；重新活跃时直接续用（锚点校验兜底地址有效性）；
- 内核作为特殊"程序"：其状态照常维护。

**同名符号解析加固（我的 call）**：多个静态链接用户程序常驻后，std/运行时符号在每份
ELF 里重名，`gdb.lookup_global_symbol(name)` 无 objfile 过滤。每程序的地址表构建改用
`objfile.lookup_global_symbol(name)`（GDB Python 的 Objfile 级查找），按程序自己的
objfile 范围解析——白名单以程序自身 crate 符号为主（名字本就唯一），objfile 级查找是
对共享符号的加固。

**连带简化**：上一轮的 save/restore 序列化、restore 重装 PollEntryBP 的整套机制可以
大幅简化——断点对象常驻 Python 内存后，只需 GDB 侧插拔，无需重建对象。

### 6.4 多核并行下的停止与判定【并行适配】

**机制**（all-stop 前提下）：
- 任何 vCPU 命中断点 → 全机冻结 → Python stop 处理器读取**所有 vCPU** 的 PC 与特权级
  （GDB 线程列表，QEMU vCPU 即线程）→ 按 PC 区间判定内核/用户、按 hook 任务结构判定
  具体程序。
- 命中断点归属程序 = 命中 vCPU 的当前程序；若多 vCPU 同时命中不同程序（理论上可能），
  记录以选中线程（GDB selected thread = 触发停止的线程）为准，其余命中静默 continue。
- 特权级过渡期单步：`scheduler-locking on` + vCont `s:<thread>` 只放行目标 vCPU，
  其余保持冻结；每步后读 PC 判定是否完成过渡。

**边界情况**：两个 vCPU 分属不同程序且同时命中各自断点——按 selected thread 顺序处理，
第二个命中在第一个处理期间处于冻结状态，处理完成后 continue 时该 vCPU 的 stop 事件
再被 GDB 派发（all-stop 语义下的天然串行化）。

### 6.5 UI / 检查器面板【连带】

**机制**：inspector 展示当前命中程序的执行流（按程序选择状态集，展示该程序的影子栈/
协程树）。白名单候选列表改为按程序分栏（grouped JSON 已按 crate 分组，UI 加程序维度过滤）。

## 7. 实现顺序建议

1. 符号常驻化（去装卸）+ 跟踪状态按程序常驻（save/restore 简化）→ 实验 B 复测
   （预期：load/unload_symbols 归零，往返从 689ms 降至 ~200ms）
2. 断点按程序 Z0 插拔 + hook 判定扩展（每 vCPU 判定）→ 单线程/并发场景回归 + 复测
3. 多核并行适配（全 vCPU 扫描、单步 scheduler-locking）→ smp>1 实测
4. UI 按程序展示 → 手工验证

每步独立可验证、独立可回滚。

## 8. 验收标准（提议目标，可调整）

- 实验 B 复测：unload_symbols / load_symbols 均归零；单次往返从 ~689ms 降至 <200ms
  （剩断点插拔 + 状态记录）；whitelist_rebuild 保持 ≈0
- 单线程（minimal）、并发（实验 B 流程）、并行（smp=2 起）三场景功能回归通过
- 符号常驻后调用链记录正确性：错记 0 次（漏记允许有界，白名单拦截保证）
- 真机验证项：vCont 单线程 step 行为、多 vCPU 全停语义、hook 任务结构读取在多核下的可靠性

## 9. 风险清单

- 断点插拔的 Z0/z0 批量耗时未实测（估计 <50ms/次，远低于符号装卸）
- 多程序同挂后 GDB 侧其他行为未穷尽验证（info line、源码级断点解析）——验收阶段实测
- hook 任务结构读取依赖 async-os 内部布局（现有机制，内核升级可能破坏）——已有先例风险；
  本设计将此类读取扩展到每次 poll 命中（影子栈 task 键），读取频率大幅上升，
  复测时需测量其对 poll 命中延迟的影响
- pipetest 方向 restore_state ~230ms 异常（原因未查清，可能在本设计后自然消失或放大）——
  复测时重点观察
- 协程键不加程序维度的触发条件一旦成立（每程序独立页表），需立即补维度（留注释）
