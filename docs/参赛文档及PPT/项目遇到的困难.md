# 项目遇到的困难

在项目开发中我们遇到了以下困难：

## 总体

* **技术难度大**：调试器开发涉及 GDB/MI 协议、DAP 协议、VS Code 扩展开发、Rust 异步机制等多个方面，团队在项目初期对这些内容都不熟悉，学习成本很高，前期进展缓慢。
* **目标系统适配困难**：前序工作在 rCore 等教学 OS 上验证充分，但 StarryOS 和 Async-os 在源码组织、系统调用路径、进程模型上完全不同，原有方案在它们上面逐一失效，每一次适配都要重新理解目标系统的架构。
* **遗留代码问题**：移植 code-debug 的 OS 调试功能时，我们对原代码做了完整审计，发现了 36 个问题，包括安全漏洞和崩溃级 bug。这些问题在原项目里从未暴露，移植后集中爆发，排查花费了大量时间。
* **调试调试器本身**：调试器出问题时没有现成的工具辅助定位，断点静默失效、状态机误判这类问题只能靠加日志和最小化实验逐层排查，是本项目最耗时的环节之一。

## 异步跟踪

* **追踪范围与开销**：全量插桩方式在真实项目上开销过大，程序规模一大调试启动就要等很久，需要把追踪范围收窄到目标 crate，同时保证不漏掉执行路径上的函数。
* **协程实例区分**：同一段异步代码可能同时有多个实例在运行，仅靠函数名无法区分，导致 poll 次数、等待关系全部混淆，需要设计实例级的标识方案。

## OS 调试移植

* **状态机逻辑复杂**：原实现把状态迁移和 GDB 交互耦合在一起，难以测试也难以移植。重构为纯函数式实现并补写单元测试后，才发现并修复了多处边界条件的处理缺陷。
* **断点生命周期管理**：边界断点和 Hook 断点需要在断点组切换时正确清理与恢复，任何遗漏都会导致断点残留或丢失，表现为难以复现的调试异常，排查起来非常困难。

## 跨特权级异步追踪

* **追踪状态被清空**：特权级切换会清理断点组，而异步跟踪依赖持续累积的状态，最初的尝试都以追踪数据丢失告终，最终通过保存/恢复机制解决。
* **树空问题**：协程还没被 poll 时逻辑树为空，但用户停在该位置时仍然期望看到调用上下文，需要物理栈回退机制来补上。
* **栈不跨特权级**：GDB 的栈展开无法跨栈，内核侧的协程帧进不了树。最后利用内核协程驱动用户任务这个事实，以内核锚点让用户协程挂在同一棵树上。

## 时间问题

* 由于项目周期长，加上课内学业压力，我们在开发过程中多次因为时间问题而放缓进度，决赛阶段的很多验证工作都是利用假期集中完成的。
