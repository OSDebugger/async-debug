## 性能优化报告

为了解决 async-debug 调试器对被调试程序的时序侵入性太强的问题，报告从理论预判、实验分析、优化方案三个方面记录优化工作。

#### 0. 问题表现

使用 async-debug 跟踪程序（甚至是异步OS）时，会发现：

- 程序运行明显变慢；
- OS 模式下（Qemu），每次程序进出内核都会卡很久；
- 更甚至被跟踪的异步程序的定时、调度行为被改变，一些竞态类的问题在跟踪时不再出现；

原因是因为调试器观察的方式是通过“停下来 -> 执行一段记录代码 -> 继续跑”，这个循环发生的非常频繁，并且我们观察的对象——异步任务，对时序很敏感，观察的动作很可能改变任务的运行情况。

#### 1. 理论预判

我们都知道整个调试器为了实现异步跟踪，涉及了很多次暂停和信息的维护，如果这些暂停和信息维护导致时间开销大，无非涉及两个方面：暂停数量 x 每次暂停的时长，根据代码进行具体的分析，接下来分两方面讲：

NOTE：该报告中讲得暂停是针对调试器和程序，对于用户来说是透明的。

##### 1.1 暂停次数

###### a. 协程函数的入口断点 PollEntryBP

调试器给每一个要跟踪的协程函数的入口放了一个断点，协程每唤醒、往前推一轮（一次poll），程序就停一次。由于异步程序中的协程被推进极其频繁，所以该断点可能会导致时间开销明显增大。

###### b. 函数内部每条调用指令一个断点 CallSiteBP

第一次进入某个协程函数时，会把整个函数从机器码翻译回汇编指令，找出其中每一条“调用别的函数”的指令（call 指令），逐条装上断点。在一个异步程序中，这类调用函数可能有几十上百个（每个 .await 点都会涉及好几个调用指令）。装完断点后，之后每一轮 poll 执行到任何一条调用就停一次。

###### c. 函数返回时触发的断点 _PopOnReturnBP

每次入口断点命中后，在"函数返回的位置"再挂一个断点，返回时再停一次。但是这个其实对时间开销影响不大。

总的来说，一次 poll 的停止次数是：入口 1 次 + 内部调用 N 次 + 返回 1 次。

##### 1.2 每次暂停的时长

以下是程序暂停时，GDB 执行 Python 脚本做的事，按预估耗时从高到低排列：

###### a. 每次暂停都写一次文件

每命中一次断点，就把一行记录追加写入日志文件（打开文件 → 写入 → 关闭），诊断日志同样如此，这个我感觉主要的时间开销是因为写的次数很多，输出的量级极大。

###### b. call 断点命中时现场查"被调用的函数是谁"

每次 call 断点命中，都要现场把当前指令所在的机器码翻译回汇编（每次重新翻译），解析出被调函数的地址，然后用 GDB 的命令行命令查询这个地址属于哪个函数。这个查询命令是 GDB 里比较慢的操作，而它每命中一次 call 断点就执行一次。

###### c. 协程入口命中时读寄存器、查类型、读内存

入口命中后要读寄存器拿到协程实例的地址，按函数名拼出类型名，向 GDB 查询类型定义（没有缓存，每次重新查），再按类型结构读内存、遍历字段。每次入口命中都是一串几十次的 GDB 内部查询。

###### d. 白名单地址表的一次性构建

第一次命中时，把白名单里每个函数名逐个解析成地址，每个名字一次 GDB 查询，几百个名字就是几百次查询。这是一次性开销，但发生在第一次停止时，会明显拉长第一次停止的时间。

##### 1.3 OS 模式（Qemu）下的两个大头

###### a. 内核↔用户切换：

每次特权级切换（进内核/出内核）都会触发一次，期间整个虚拟机是停着的，串行做完这些事：

1. 保存跟踪状态（一条 GDB 命令，把全部跟踪状态序列化）；
2. 逐个删掉旧组的所有断点；
3. 卸载旧符号文件（记录了函数名、行号对应关系的调试信息文件）、加载新符号文件——GDB 要解析整个文件的调试信息，这一步是秒级；
4. 逐个重新插断点；
5. 恢复跟踪状态（重新装所有跟踪断点）；
6. 如果加载了新文件：重新生成白名单（扫描全部符号）→ 写白名单文件 → 加载白名单 → 给用户程序的所有异步函数逐个装断点。

一次切换冻结数秒，而且每次进出内核都会发生。

###### b. 特权级切换的逐条单步

为了判断"是否已经进到内核/回到用户"，采用的方式是每执行一条指令就停一次、读一次寄存器、再执行下一条，直到到达目标。切换过程通常要单步几十条指令，系统在这条路径上每执行一条指令就被打断一次，不仅会大大拖慢整个 OS 的运行，还对定时和调度行为的干扰有破坏性。

#### 2. 实验分析

为了将每部分的时间开销进行量化，这里设计了两个实验。实验A测试的是1.1和1.2的开销，实验B测试的是1.3的开销。

4. **实验结论**

​	a. 单次停止的成本比预想高

在本地直接调试的情况下，每次停止平均也要1毫秒左右。这意味着在 OS 模式（经过 QEMU）下只会更贵。

​	b. GDB 断点机制的固定开销和 Python 代码各占一半

优化 Python 代码只能省一半；另一半要靠减少停止次数（少装断点）来解决。

##### 2.2 实验B

测试对象是async-os 以及它依次运行的两个用户程序hello_world和pipetest（异步管道测试），目的是量化1.3节中内核↔用户切换、特权级单步的开销。

1. **源代码增量** [commit](https://github.com/OSDebugger/async-debug/commit/dd9e591)

在源代码中加了以下内容：

- 一个计时器（src/osProfiler.ts）：组切换计时 + 单步计时，输出到调试控制台和日志文件，断开调试时打印累计报告；
- 组切换打点（src/breakpointGroups.ts）：在切换的七个步骤（保存状态、删断点、卸载符号、加载符号、重插断点、恢复状态、重建白名单）的首尾打点；
- 单步打点（src/gdbDebugSession.ts）：记录每段特权级单步的步数和耗时；

2. **实验设计**

实验B没有像实验A那样做成脚本，两组对照跑法如下：

| 测试     | 跑法                                   | 计时方式        | 目的                                         |
| -------- | -------------------------------------- | --------------- | -------------------------------------------- |
| baseline | QEMU直接运行，不启动调试器（make justrun） | Linux自带的time | 基准：两个用户程序跑完的总时间               |
| debug    | VS Code里以ardb启动调试                | 源代码插桩      | 组切换、单步各自的耗时                       |

3. **实验结果**

​	**a. Baseline**

```bash
 	User time (seconds): 52.26	// 宿主机CPU在用户态干活的时间
	System time (seconds): 22.28	// 宿主机CPU在内核态干活的时间
	Percent of CPU this job got: 123%	// CPU的利用率
	Elapsed (wall clock) time (h:mm:ss or m:ss): 1:00.25	// 现实世界的时间过去了多久
```

两个用户程序正常跑完，OS自动关机，CPU时间合计74.5秒。

​	**b. Debug**（输出较多，这里不具体展示）

- 组切换

整个调试过程共发生382次组切换（hello_world 73次往返、pipetest 118次往返），总耗时303.7秒，平均每次795毫秒。按方向拆开：

| 方向 | 次数 | 平均每次 | 主要开销 |
| -------- | -------- | -------- | -------- |
| 内核→hello_world（进用户态） | 73 | 1058 ms | 重建白名单 830 ms |
| 内核→pipetest（进用户态） | 118 | 1404 ms | 重建白名单 946 ms |
| hello_world→内核 | 73 | 203 ms | 卸载符号 107 ms |
| pipetest→内核 | 118 | 390 ms | 卸载符号 297 ms |

七个步骤的总占比：

| 步骤 | 总耗时 | 占比 |
| -------- | -------- | -------- |
| 重建白名单 | 172.2 s | 56.7% |
| 卸载符号 | 42.9 s | 14.1% |
| 恢复状态 | 31.7 s | 10.4% |
| 加载符号 | 27.7 s | 9.1% |
| 重插断点 | 20.7 s | 6.8% |
| 保存状态 | 5.6 s | 1.8% |
| 删断点 | 3.0 s | 1.0% |

​	**c. 特权级单步**

共191段、698步，总耗时13.9秒，平均每步19.9毫秒。全部发生在内核→用户方向（因为回内核方向的边界断点设在内核函数入口，命中时PC已在内核，不需要单步）。每段步数：1步 × 145段、12步 × 45段、13步 × 1段。

​	**d. 总开销**

组切换303.7秒 + 单步13.9秒 = 317.5秒。对照组的CPU时间只有74.5秒——调试开销是程序自身工作量的4.3倍。

4. **实验结论**

​	a. 开销集中在组切换，单步是小头

组切换占总开销的96%，其中重建白名单一项占56.7%。每次跨入用户态，程序被冻结1~1.4秒，其中约七成花在重建白名单上。1.3a预判"一次切换冻结数秒"被证实，且最贵的步骤是白名单重建而非符号加载。

​	b. 开销随用户程序体积增长

pipetest（musl静态链接）的符号卸载耗时是hello_world的近3倍（297 ms vs 107 ms）。用户程序越大，每次切换越贵。

​	c. 单步单价高，但步数比预判少

平均每步19.9毫秒，是实验A本地停止（约1毫秒）的20倍。但1.3b预判"切换要单步几十条指令"，实测每次进入用户态平均只需3.7步，约四分之三的切换只要1步。单步共13.9秒，占总开销的4%。【但是单步的次数很大程度以来边界断点的选择】

##### 2.3 总结

通过 A与B 两个实验的数据，可以看到整个系统的性能消耗主要集中在 **OS 特权级切换上下文重建开销**和**高频断点触发时 GDB 与 Python交互开销**。

在特权级切换方面（实验B），调试开销达到了程序自身工作量的 4.3 倍，其中组切换占了总开销的 96%。深入剖析组切换的耗时分布，重建白名单占了组切换开销的近六成（56.7%）；符号表的卸载和加载占 23.2%，并且该开销会随着用户程序的增大而显著增加；此外，简单粗暴的断点删除和重插也分别占用了 1.0% 和 6.8% 的时间。另外，特权级单步虽然总耗时占比不大，但单次步进成本很高（平均 19.9 毫秒），其总次数严重依赖于边界断点的选择策略。

在高频暂停方面（实验A），单次暂停的开销由 Python 记录逻辑和 GDB 底层处理各占一半。最核心的冗余消耗在于反汇编逻辑：入口断点触发时的首次全函数反汇编耗时仅 0.013s，而后续每次调用指令（call_site）触发时进行的现场反汇编累计耗时却高达 0.059s，这部分重复劳动完全可以通过更好的算法消除。此外，盲目插桩导致了大量的无效拦截，实际插桩的 122 个调用指令中，真正命中的有效调用仅有 8 次，说明源头上的插桩过滤有很大的优化空间。

#### 3. 优化方案

基于上述实验数据与理论分析，针对系统的两大性能瓶颈，提出以下优化方案。

##### 3.1 针对特权级切换的优化（降低组切换与单步开销）

- **白名单重建开销**

	现状：每次进入用户态时，都要重新扫描全部符号并生成白名单文件，冻结时间极长。原本设计每次重建的原因在于，若系统开启 ASLR 或目标程序是位置无关可执行文件（PIE），程序每次被加载时符号的绝对地址均会发生变化。

	优化方向：引入基于相对偏移量（Offset）或进程生命周期的持久化缓存机制以替代全盘扫描。由于程序内部函数间的相对距离在编译期即固定，可在程序首次加载时计算并缓存 `<函数名, Offset>` 的映射关系。后续跨特权级切换时：若切回同一存活进程，直接命中绝对地址缓存；若基址发生改变，仅向 GDB 查询 1 次新加载基址，并在 Python 内存中通过 `新加载基址 + 缓存 Offset` 瞬间完成所有白名单地址的重计算，将数百次缓慢的 GDB 符号查询彻底抹除。

- **符号表加载/卸载开销**

	现状：每次进出内核都会卸载旧符号文件并加载新符号文件，且耗时随程序体积增大而增加。

	优化方向：减少高频的符号卸载与加载动作，探索利用 GDB 的多符号文件共存机制，或者通过地址空间偏移量来管理不同特权级的符号。具体的想法如下：

	- 多符号文件共存：若内核空间与用户空间虚拟地址严格隔离（如高低地址分布），在用户程序首次运行时追加加载符号，后续切换时不再卸载。GDB 将利用 PC 的地址区间自动精准匹配符号，彻底清零加载/卸载耗时。
	- Inferior 上下文隔离机制（适用于地址重叠场景）：若用户态与内核态地址存在重叠，或存在多个同基址的用户进程，引入 GDB 的 Inferior（下级进程）机制。为内核及各个用户进程预先分配独立的 Inferior 空间并分别预热符号。跨特权级切换时，仅需执行 O(1) 复杂度的 Inferior 切换指令。
	- 基于 PIE/ASLR 的偏移量动态映射：若目标程序每次加载的基址动态变化，可跳过全盘的 DWARF 重新解析。仅利用一次解析固化函数间的相对偏移量，当程序在新基址运行加载时，通过覆盖修改 Objfile 的基址完成极速重定位。

- **断点管理开销**

	现状：特权级切换时采用了逐个删掉旧组断点、再逐个重新插新断点的暴力算法。

	优化方向：可以利用 GDB 的 enable/disable（启用/禁用）机制替代彻底的物理删除与重插。将内核与用户态的跟踪断点分组管理，切换时只需批量翻转断点的状态。另外，若采用上面的 Inferior 上下文隔离机制，此开销也会将被天然消除。由于各 Inferior 拥有完全独立的断点组，切换 Inferior 时，旧空间的断点会自动休眠，新空间的断点瞬间激活，彻底免除手动删插断点的开销。

- **特权级过渡期的单步开销**

	现状：为判断是否回到用户态，每次特权级切换都要单步执行十几条指令，每步耗时约 19.9 毫秒。

	优化方向：把断点精准打在内核执行特权级返回的最后一条特权汇编指令（如 `sret` / `iret`）上。断点命中时，利用 GDB 执行仅 1 次的指令级单步（`stepi`），即可瞬间降级至用户态。

##### 3.2 针对高频断点暂停的优化（降低 Python 与 GDB 交互开销）

- **运行时重复反汇编**

	现状：每次 call 断点命中时，都要现场把当前指令的机器码翻译回汇编并向 GDB 查询解析调用函数。

	优化方向：将地址解析前置。在首次进入协程函数触发 callsite_install 并进行全函数反汇编时，直接解析并构建 `<指令地址, 目标函数>` 的静态哈希表，后续调用断点触发时进行 O(1) 查表，消除运行时的反汇编成本。

- **无差别插桩导致的无效拦截**

	现状：首次翻译机器码时给每一条 call 指令都装上了断点，导致 122 次停顿中只有 8 次是开发者真正关心的。

	优化方向：结合白名单实现精准插桩。在首次全函数反汇编时增加白名单过滤逻辑，只对那些指向我们感兴趣的函数的 call 指令下断点，从物理层面减少 GDB 停止的次数。

- **日志与 I/O 机制**

	现状：写日志的次数很多，输出的量级很大，虽然开销不多，但是对于用户来说看起来没那么方便（调试控制台）。

	优化方向：清理调试器中不必要的输出内容，减少无意义的刷屏信息，让调试控制台和终端更直观，以此自然降低高频 I/O 带来的额外开销。
